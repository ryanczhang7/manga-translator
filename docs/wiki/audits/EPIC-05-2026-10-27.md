(`claude-opus-5-5`). The agent definition declares `opus`. No override was

## Scope

**The question.** If EPIC-05's production code were subtly wrong, would a test
notice? Line coverage is already 100% (the `coverage-core` gate), so every
mutant below ran on covered lines. A survivor is an assertion gap, not an
uncovered line.

**Tooling.** The `mutation` gate was not run. `mutmut` is not installed, and the
gate is waived in `.claude/harness/project.conf`. Mutants were chosen by hand
and applied one at a time with:

    bash scripts/mutate.sh FILE 'SED' -- uv run pytest -q -x -p no:cacheprovider <test files>

The named test files were the narrowest set that should catch each mutant.
Every survivor was then rerun once against all of `tests/ui` (W, 1,744 tests at
this commit) before it was classified, as the EPIC-07 audit did. Four scratch
probe files were written **in the session scratchpad, outside the
repository**, to show that the gaps found are killable and to measure the
defect in Decided 3. Each imports the fixtures of one existing test module
(`test_line_review_workspace.py`, `test_page_strip_status.py`,
`test_link_workspace.py`), or none. They are not committed, and the stories
filed below restate what they do.

**Environment.** Windows 11 Home 10.0.26200, Python 3.13.15 (`uv run`), pytest
8.4.2, pytest-qt 4.5.0, PySide6 6.9.3, offscreen Qt platform (the suite's
default). Targeted runs took 2-29 s of wall time. Wide runs took 56-87 s.

## Decided

1. **EPIC-05's tests discriminate well on the done-when behaviour.**
   - Of 125 distinct mutants, 109 were killed and 16 survived.
   - Of the 16 survivors, 5 are real gaps (4 filed, BG3 deliberately not), 7
     are equivalent and 4 are unreachable.
   - These areas have no surviving mutant: the line editor's status machine
     (Enter, Esc, `Ctrl+R`, `Ctrl+Enter`, the save timer and a failed save),
     the store round trip, the bubble/line link in both directions, the canvas
     keys, the run panel's page and step readouts, the cost readout's state
     boundaries, the strip status derivation, and remembered geometry.
   - Rests on E-1 and E-2.
2. **HIGH: text typed but not yet committed is not pinned to survive closing
   the window or changing page (filed as MT-096).** The behaviour is
   *correct today*: `TranslationColumn.flush()` clears focus first
   (`ui/workspace.py:830-831`), and that commits a dirty field the way leaving
   it would.
   - **The gap.** No EPIC-05 test types without pressing Enter and then closes
     the window or changes page. Every close test presses Enter first.
   - **What survives.** Each caller can be changed to flush the rows' editors
     directly, which skips the focus-out commit:
     - the close path (WS29) survives every EPIC-05 test;
     - the page-change path (WS30) survives all 1,744 UI tests.
   - **The effect.** "Close the app, reopen it and find their edits" fails for
     the edit in progress, which is the one the user is most likely to have
     just made.
   - **The one EPIC-06 test that notices.** `test_bake_render.py` catches a
     mutation inside `TranslationColumn.flush` itself (WS4). It does not see
     either caller changing.
   - Rests on E-2 items 1 and 2.
3. **MED: a real defect, not a survivor. Changing page with a save pending
   puts the previous page's line counts on the new page's strip row (filed as
   MT-097).** Found while classifying WS3 and measured by a scratch probe
   (E-3).
   - **Where.** `show_page` sets `self._page_ordinal = ordinal`
     (`ui/workspace.py:1079`) *before* the pending saves are flushed (`:1123`,
     and `set_rows` at `:779`).
   - **The mechanism.** Each flushed save re-renders its row, and the row's
     `linesChanged` calls `_refresh_page_progress` (`:1062-1073`). That
     function reads the *old* page's rows but writes them onto the *new*
     page's strip row.
   - **What the probe showed.** On a chapter whose pages are both `done`, it
     accepted one line on page 1 with `Ctrl+Enter` and selected page 2 within
     the 500 ms save window. Page 2's strip row went from `translated, 0 of 1`
     to `failed, 1 of 5, 1 failed`, which are page 1's counts. Nothing
     corrects it until a line on page 2 changes. Reopening the chapter does
     correct it, because the strip is then derived from the store.
   - **What it does not touch.** The store, the bake gate's unreviewed list,
     and page 1's own row are all correct.
   - **Why MED and not HIGH.** It is a misleading progress glyph, not lost
     work. The bake gate (EPIC-06) still states what is unreviewed from the
     store.
4. **LOW: two stated rules have no test at their edge (filed as MT-098).**
   - **WS17.** A row whose line has committed text but no proposal reads
     "English: not translated" under the mutant, and no test notices.
     MT-017 C-8's RED amendment says "not translated" exactly when there is
     *neither* a proposal *nor* committed text. Such a row is reachable: a
     `failed`, untranslated line the user then types into.
   - **CV12.** `_within`'s `<=` (`ui/canvas.py:577`) can become `<`. Then a
     click exactly 3 px from the press, or from the previous click, is treated
     as a drag or a new point. The tests use 2 px and 10 px only.
     `components.md` says "within 3px".
5. **Not filed.**
   - **BG3** (`ui/badges.py:113`, `<` to `<=` on the start-point tie). The
     story deliberately leaves this unpinned: MT-051's contract says "Ties -
     RED's fixtures must avoid them" and that a different first vertex "may
     legitimately change" the result. It is a real survivor, and leaving it
     untested was the design's choice.
   - **The 7 equivalent and 4 unreachable survivors** (E-2, "Equivalent and
     unreachable"). Each has its reason there.
6. **Every handoff mutation claim re-run here held** (E-4, 5 claims). **Every
   passed-on-arrival assertion sampled was earned** (E-4, 3 earns).
7. **Tests that hold less than their names say** (E-5). None is pure theatre.
   - `test_closing_the_workspace_writes_a_pending_save` and AC-6's round trip
     press Enter before closing. So "a window close never drops a pending
     save" is pinned only for an edit that was already committed.
   - The `exit 127` that `uv run pytest` returns on a *green* run of the
     run-panel test files (E-1) means an exit code alone cannot say whether
     those suites passed.

### E-2: survivors, ranked by production impact

**1. WS30 (HIGH): changing page while typing loses the typed text, and no UI
test notices.** The mutant changes `ui/workspace.py:779` (`set_rows`'s
`self.flush()`) and `:1123` (`_load_regions`'s
`self.translation_column.flush()`). Each becomes a flush of the rows' editors
that skips `TranslationColumn.flush()`'s `clearFocus()`.

    bash scripts/mutate.sh src/mangatl/ui/workspace.py '1123s/        self.translation_column.flush()/        [row.editor.flush() for row in self.translation_column._rows]/;s/^        self.flush()$/        [row.editor.flush() for row in self._rows]/' -- uv run pytest -q -x -p no:cacheprovider tests/ui
    1744 passed in 54.52s

- **Why it survived.**
  `test_changing_page_writes_a_pending_save_before_the_rows_are_replaced`
  (`tests/ui/test_line_review_workspace.py:673`) commits with `Ctrl+Enter`
  before changing page. So the save is already pending, and a plain flush
  writes it.
- **What kills it.** A scratch probe, which is not in the repository. It
  focuses row 2's editor on page 1, types `"Typed, no Enter"` with no Enter,
  calls `window.page_strip.setCurrentRow(1)`, and asserts the project file
  holds `("Typed, no Enter", "edited")` for page 0 row 2.
  - It passes on the shipped code.
  - Under WS30 it fails with
    `assert (None, None) == ('Typed, no Enter', 'edited')`, plus a
    `RuntimeError: Internal C++ object (PySide6.QtWidgets.QListWidgetItem)
    already deleted` from the focus-out that arrives after the rows are gone.
  - This is MT-096 AC-2.
- **Production effect.** On a page change, a user mid-edit loses the edit. The
  field is destroyed with its text, and nothing reaches the project file.

**2. WS29 (HIGH): closing while typing loses the typed text, and no assertion
notices.** The mutant changes `ui/workspace.py:1284` (`closeEvent`'s flush) in

  67.76 s). `-x` stopped the run at the error.
- **The error.** It is a *teardown* `sqlite3.ProgrammingError: Cannot operate
  on a closed database` in
  `tests/ui/test_theme_apply.py::test_switching_high_contrast_on_and_off_loses_no_selection_scroll_zoom_or_typed_text`.
  The focus-out commit arrives after `close()`, its 500 ms save timer fires

  pressing Enter, and reopens it to find the edit gone. That breaks the

### E-3: the strip-progress defect (Decided 3)

- **The claim, stated so it could be false.** After a commit on page A and a
  page change to B before A's save timer fires, B's strip row shows A's
  `PageProgress`.
- **The inputs.** These are the fixtures of
  `tests/ui/test_line_review_workspace.py` (`chapter_dir`, `project`, two
  pages, 600 x 800 PNGs). Page 0 has 5 regions (one `ocr_empty`) and page 1
  has 1.
- **The probe.** It is a scratch file outside the repository. It imports that
  module's fixtures and helpers and runs as follows:
  1. set both pages `done`
     (`UPDATE page SET status = 'done'`);
  2. `_showing(qtbot, project)`;
  3. `_focus` row 1's editor, then `Ctrl+Return`;
  4. `window.page_strip.setCurrentRow(1)`, then `_settle()`;
  5. read `window.page_strip.progress(1)` before and after.
- **The command.**

      uv run pytest -q -p no:cacheprovider -s --rootdir=<scratch> <scratch>\test_probe_ws.py -k glyph_done

- **The result, on the shipped code.**

- **A second variant.** With both pages left `pending` and every line of
  page 0 accepted in turn, `progress(1)` went from `(pending, 0, 1, 0)` to
  `(pending, 4, 5, 1)`.
- **A third variant, on MT-097's own fixture.** This used
  `tests/ui/test_page_strip_status.py`'s `reviewing` project (four pages:

## What would have to be true for this to be wrong

- **That `-x` never hid a kill.** A mutant that "survived" at `-x` printed `N
  passed` with no failure, so `-x` could not have hidden one there. A mutant
  that was "killed" at `-x` might have been killed by an unrelated assertion,
  and the failing assertion was read for the survivors' neighbours, not for
  every kill.
- **That the offscreen Qt platform delivers focus-out, Leave and Enter as a
  real desktop does.** WS11's unreachability and the focus-out commit behind
  WS29 and WS30 both depend on it.
- **That the 500 ms save timer did not fire between the commit and the page
  change** in the E-3 probe. `_settle()` runs only two `processEvents()`
  calls, but on a much slower machine the timer could fire first, and then
  the probe would pass.
- **That exit 127 on the run-panel files is a process-teardown artefact, not a
  hidden failure.** The pytest summary line, not the exit code, was taken as
  the verdict.

- **No tool-generated mutant set.** These 125 are a hand selection, weighted
  toward the done-when behaviour. Not tried systematically: string literals
  in every rendered sentence (the run banner and the summary copy, for
