## Context

The other half of the batch: a submitted job is collected into the **same**
store path the per-page call writes - `write_proposed` per page, one ledger
row per page at the batch tier, the glossary's terms marked seen - and
collection survives the app being closed: a project with a pending
`batch_job` (MT-103) is collected when it is next opened for a run.

Nothing is guarded here (EPIC-09 PO-5): the batch was judged whole before
submission and the bill is already incurred; collection records what it cost.
A page whose item failed (MT-110 `BatchItemError`) gets no proposal and its
lines read `failed` with the item's message as the reason, the status the
review already renders for an untranslated line (`domain/line.py`
`_REASON_UNTRANSLATED`).

The collector is a `Callable` bound by `compose` (pipeline may not import
`translate`); it answers with a state or with the results.

Required gates: `unit`, `coverage`.

## Acceptance criteria

- **AC-1** - Given a pending job and a fake collector answering `pending`,
  `collect_volume` emits `BatchWaiting(job_id, state="pending")`, writes
  nothing, and the job stays pending.
- **AC-2** - Given a pending job of three pages and a collector answering
  with three results, `collect_volume` writes each page's proposals, marks
  the glossary's terms seen per page, writes one ledger row per page with
  `pricing "batch"`, `request_id == f"{job}#{ordinal}"`, the item's usage
  priced at the batch row, and `page_id` the page's; emits `CallPriced` per
  page in ordinal order and then `BatchCollected(job_id, pages_done=3,
  pages_failed=0)`; and `pending_job(project)` is `None` with the job read
  back `collected`.
- **AC-3** - With the middle item a `BatchItemError`, pages 1 and 3 are
  written as in AC-2, page 2's lines read `failed` with the error text, page
  2 has no ledger row, and `BatchCollected(pages_done=2, pages_failed=1)` is
  emitted.
- **AC-4** - With the collector answering `failed`/`cancelled`/`expired`,
  the job is marked failed with that state, nothing is written, and
  `BatchFailed(job_id, state)` is emitted.
- **AC-5** - `collect_volume` on a job already `collected` raises
  `AlreadyCollected` before calling the collector; a second collection of
  the same job can never write a second bill.
- **AC-6** - `mangatl-run FOLDER` on a project with a pending job collects
  once and prints the job's state in one line (`pending`, or `collected n
  pages`), running no stage and submitting nothing; with `--sync` it refuses
  in one line naming the pending job rather than translating pages twice.

## Contract

**Writes:** `src/mangatl/pipeline/batch.py`, `src/mangatl/domain/batch.py`, `src/mangatl/domain/events.py`, `src/mangatl/store/lines.py`, `src/mangatl/compose.py`, `src/mangatl/cli.py`, `tests/core/test_batch_collect.py`, `tests/core/test_cli.py`, `tests/core/test_compose.py`

```python
# domain/batch.py
@dataclass(frozen=True)
class BatchPending_:    # RED names it; a state answer
    state: Literal["pending", "failed", "cancelled", "expired"]
@dataclass(frozen=True)
class BatchResults:
    results: Mapping[int, TranslationResult | BatchItemFailure]    # BatchItemFailure(ordinal, message) in domain
BatchAnswer = BatchPending_ | BatchResults

# domain/events.py
@dataclass(frozen=True) class BatchWaiting:   job_id: int; state: str
@dataclass(frozen=True) class BatchCollected: job_id: int; pages_done: int; pages_failed: int
@dataclass(frozen=True) class BatchFailed:    job_id: int; state: str

# pipeline/batch.py
BatchCollector = Callable[[str, Sequence[BatchPageInput]], BatchAnswer]
class AlreadyCollected(Exception): ...
def collect_volume(project: Project, job: BatchJob, collect: BatchCollector, emit: Callable[[RunEvent], None]) -> BatchAnswer

# store/lines.py: a way to mark a page's lines failed with a reason, if none exists - RED checks `mark_failed`-like helpers first
# compose.py: for gemini binds collect = partial(<adapter: batch_state then collect_batch>, client)
# cli.py: pending-job branch before any stage is built; --sync refusal
```

The page inputs for `collect_batch` are rebuilt from the store (OCR lines)
so the parse knows each page's region indices; images are **not** re-read.
RED fixes whether `BatchPageInput.page_image` is optional for collection or a
narrower input type exists. Oracle partition: all **mechanical**.
