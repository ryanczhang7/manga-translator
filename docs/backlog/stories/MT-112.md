## Context

The other half of the batch: a submitted job is collected into the **same**
store path the per-page call writes - `write_proposed` per page, one ledger
row per page at the batch tier, the glossary's terms marked seen - and
collection survives the app being closed: a project with a pending
`batch_job` (MT-103) is collected when it is next opened for a run.

Nothing is guarded here (EPIC-09 PO-5): the batch was judged whole before
submission and the bill is already incurred; collection records what it cost.
A page whose item failed (MT-110 `BatchItemError`) gets no proposal and its
lines read `failed` with the item's message as the reason, the status the
review already renders for an untranslated line (`domain/line.py`
`_REASON_UNTRANSLATED`).

The collector is a `Callable` bound by `compose` (pipeline may not import
`translate`); it answers with a state or with the results.

Required gates: `unit`, `coverage`, `coverage-core` (`domain/batch.py` and `domain/events.py` are under its 100 % branch floor). All `required`; a broken collector fails `unit`.

## Acceptance criteria

*Reworked 2026-11-04 at PLANNED for several jobs per volume (MT-137: `pending_jobs`,
each job over its own page range) and for what the store can hold (PO-1).*

- **AC-1** - Given a pending job and a fake collector answering a state of
  `"pending"`, `collect_volume` emits exactly `[BatchWaiting(job_id,
  state="pending")]`, writes nothing (no proposal, no ledger row, no page
  status change), and the job is still in `pending_jobs`.
- **AC-2** - Given a pending job over pages `0..2` of a three-page project
  with OCR lines and a glossary, and a collector answering three
  `TranslationResult`s, `collect_volume`: writes each page's proposals
  (`write_proposed(ordinal, result.lines)` - batch answers are keyed by
  reading index because MT-111 sent every stored line, PO-2); folds each
  page's `proposed_terms` into the glossary and marks its terms seen
  (`merge` then `mark_seen`, as the translate stage does); writes one ledger
  row per page against the **job's** `run_id` with `pricing == "batch"`,
  `request_id == f"{provider_job_id}#{ordinal}"`, the item's usage priced at
  the batch row (`price(model_id, usage, pricing="batch")`) and `page_id` the
  page's; marks each page `done`; emits `CallPriced(ordinal, spent, ceiling,
  projection)` per page in ordinal order, then `BatchCollected(job_id,
  pages_done=3, pages_failed=0, failures=())`; and afterwards
  `pending_jobs(project) == ()` with the job read back `collected`. The
  collector was handed the job's pages as `BatchPageInput(ordinal,
  page_image=b"", ocr_results=read_lines(ordinal), context=EMPTY_CONTEXT)`
  - no image is re-read (PO-3).
- **AC-3** - With the middle item a `BatchItemFailure(1, "quota")`: pages 0
  and 2 are written as in AC-2; page 1 gets no proposal and no ledger row,
  is marked `done`, so its lines read `failed` with the existing untranslated
  reason (PO-1); `BatchCollected(job_id, pages_done=2, pages_failed=1,
  failures=((1, "quota"),))` carries the message. Two `CallPriced`, for
  pages 0 and 2.
- **AC-4** - With the collector answering a state of `"failed"`, `"cancelled"`
  or `"expired"`: the job is marked failed with that state as its `failure`
  text, nothing is written to any page or the ledger, and exactly
  `[BatchFailed(job_id, state)]` is emitted.
- **AC-5** - `collect_volume` on a job whose `state` is not `"submitted"`
  raises `AlreadyCollected` naming the job before the collector is called -
  a second collection of one job can never write a second bill.
- **AC-6** - `mangatl-run FOLDER` on a project with pending jobs builds no
  stage and submits nothing: it collects each pending job in page order
  through `build_batch_collector(selection)`, and prints one line,
  `batch: {pages_done} pages collected, {pages_failed} failed,
  {still_pending} jobs still pending`, exit 0; with no Gemini selection it
  refuses in one line (a pending batch needs the key that submitted it).
  A new `--sync` flag means "the per-page run": with pending jobs it refuses
  in one line naming the first pending job's provider id rather than
  translating pages twice; with none it is today's run, unchanged. A project
  with no pending jobs and no `--sync` is also today's run, unchanged.

## PO decisions (2026-11-04, lead-po on Claude Fable 5.1)

- **PO-1 - a failed item's reason is carried by the event, not the line.**
  The `line` table has no failure-reason column (`status` admits only the
  three user acts; `failed` is *derived*: no proposal on a page marked
  `done`, `domain/line.py` `derive_status`), so "lines read `failed` with the
  item's message" cannot be stored without a schema change. Decided: the page
  is marked `done` with no proposal, so the review shows its lines as
  `failed` with the existing reason ("no translation was returned"), and the
  item's message rides `BatchCollected.failures` for MT-113 to show and log.
  If the per-line reason is wanted in the review, that is a small schema
  story (v12: `line.failure_reason`), not this one. **Reported to the user
  before GREEN.**
- **PO-2 - batch answers are keyed by reading index.** MT-111 sends every
  stored line of a page (`read_lines`), unlike the per-page stage, which
  sends only the non-excluded regions and maps the answer back (MT-118 C-4).
  So a batch item's `lines` keys ARE reading indices and `write_proposed`
  takes them as they are. Consequence worth knowing: **a region excluded
  before submission is still sent and translated in a batch** - it costs
  tokens and gets a proposal the review hides as `excluded`. Not this story's
  to fix (MT-111 is closed); noted for a follow-up: MT-111's input builder
  should drop excluded regions and MT-112's writer map indices back, as the
  stage does. **Reported to the user.**
- **PO-3 - no image is re-read at collection.** `collect_batch` reads only
  `ocr_results` (for the region count); `BatchPage.page_image` is `b""` and
  `context` is `EMPTY_CONTEXT`. Cheap and honest about what the parse needs.
- **PO-4 - `--sync` is introduced here with one effect.** It refuses when a
  batch is pending; otherwise it is today's per-page run. Whether a plain
  `mangatl-run` on a Gemini selection with no pending job *submits a batch*
  (EPIC-09 Q-3 says Start does; nothing says the CLI does) is MT-113's
  question, not changed here.
