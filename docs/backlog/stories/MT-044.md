## Context

**This story exists because of a split made at MT-013's PLANNED→RED boundary,
decided by the user on 2026-09-21.** MT-013's criteria as planned described a
pure-domain budget module *and* the run-level behaviour that makes it bite.
Those are two RED→GREEN cycles, and the second one is this story. MT-013's
`## Amendments` records the split; MT-013 AC-3 and AC-4 are this story's AC-1
and AC-2 verbatim.

**The seam this story closes has been deferred twice, by two different stories,
and that is the reason it is a backlog item rather than a third docstring.**

1. **MT-011 shipped `TranslateStage` wired to nothing.** `pipeline/translate_stage.py`
   names MT-013 as the wiring story (C-8, PO-6), and MT-011's own close-out
   repeats it: *"`TranslateStage` is built and wired to nothing. MT-013 adds it
   to `build_stages`."*
2. **MT-012 shipped `record_call` wired to nothing.** `rg record_call src/`
   returns only its own definition. Nothing in production writes a ledger row.

The consequence is the one that matters, and it is why MT-013 alone does not
finish EPIC-04's budget clause: `store.ledger.chapter_total()` reads the ledger,
so with nothing writing rows **`spent` is permanently $0 and the guard is inert
in the running app**, however correct its arithmetic. MT-013 builds a correct
scale; this story puts something on it.

**Which required gate would fail if this story's artifact broke:** `unit` and
`coverage` — `src/mangatl/pipeline/**` and `src/mangatl/store/**` are covered by
both (`covers | unit | src/mangatl/**`), and both are `required`. Verified
against `bash scripts/gates.sh --list` on 2026-09-21. `coverage-core` does
**not** reach `pipeline` or `store`; it covers `domain`, `typeset` and `bench`
only, so it is MT-013's gate and not this story's.

## Acceptance criteria

<!-- AC-1 and AC-2 are MT-013's AC-3 and AC-4, moved here unchanged. -->

- **AC-1** — Given a refusal, when the run ends, then it emits
  `RunAborted(reason="budget")` naming the page it stopped before, and every
  page already translated is persisted with its lines intact.
- **AC-2** — Given a refusal, when the ledger is read, then **no `llm_call` row
  exists for the refused page** — the call was never made.
- **AC-3** — Given a permitted page, when the translate stage completes, then
  exactly one `llm_call` row exists for it, priced from the response's own
  usage by `domain.rates.price`.
- **AC-4** — Given a chapter walked end to end, when the stage list is built,
  then it contains the translate stage after detect and OCR, and a run produces
  proposed English for every page with regions.
- **AC-5** — Given a chapter row carrying a ceiling, when the guard is
  constructed for a run, then it uses that ceiling rather than the default; and
  given a chapter row with no ceiling, it uses `DEFAULT_CEILING`.
- **AC-6** — Given `mangatl-run --no-translate`, when the stage list is built,
  then it holds detect and OCR only, no `Anthropic` client is constructed, and
  the run completes over a chapter on a machine with no API key. *(Added
  2026-09-22 by the user at the GATES boundary — see `## Amendments` A-1.)*

**AC-2 is the one that can pass vacuously and the suite must not let it.** An
implementation that records nothing for *any* page satisfies "no row for the
refused page" trivially. AC-3 is therefore not decoration: it is AC-2's positive
control, and the two must be asserted against the same fixture so that "no row
here" is only true because "one row there" is.

### C-1 — `PageContext` gains `run_id: int`, required, no default

`src/mangatl/pipeline/stage.py`.

```python
@dataclass(frozen=True)
class PageContext:
    project: Project
    page: Page
    run_id: int
```

Third and last, after `project` and `page`. **No default.** A default of `0`
would let a stage record a ledger row against a run that does not exist, and
`llm_call.run_id` is a NOT NULL foreign key to `run(id)` — so a wrong value is
caught only if no run happens to have that id, and run 1 always does. All nine
construction sites in `## Caller inventory` already pass `project=` and `page=`
by keyword, so the ripple is an added keyword and not a re-ordering.

`DetectStage`, `OcrStage` and `PassThroughStage` do not read `run_id`. They do
not need to: the field is on the context because the context is what the runner
hands every stage, and a second context type for one stage would be worse.

### C-2 — `BudgetRefused`, in `pipeline/stage.py`

```python
class BudgetRefused(Exception):
    """The budget guard refused the call this page was about to make."""

    def __init__(self, decision: Decision) -> None:
        super().__init__(decision.reason)
        self.decision = decision
```

`__all__` becomes `["BudgetRefused", "PageContext", "PassThroughStage", "Stage"]`.

**`stage.py` and not `translate_stage.py`**, because `runner.py` must catch it
and already imports `stage.py`; a runner importing `pipeline.translate_stage` to
name an exception would put the translate stage into the import graph of every
run, including the zero-stage ones `tests/core/test_pipeline.py` uses.

**An exception and not a return value**, although `domain/budget.py`'s docstring
says a refusal "is a `Decision` with `permitted=False`, not an exception". That
is a rule about the *domain guard* and it still holds — `Budget.check` returns a
`Decision` here as everywhere. This exception is the *pipeline's* way of turning
that decision into a stop, and `Stage.run` returns `None`: there is no other
channel out of it. The `Decision` travels on the exception so MT-018 can render
the three numbers that justified the refusal.

`stage.py` therefore imports `Decision` from `mangatl.domain.budget` — down the
layers, and legal.

### C-3 — the runner maps `BudgetRefused` to `reason="budget"`

`src/mangatl/pipeline/runner.py`.

```python
#: `RunAborted.reason` for a budget refusal. AC-1 pins this exact string.
BUDGET = "budget"
```

Added to `__all__` beside `RUN_ABORTED` and `RUN_FINISHED`, for the reason those
two are there: AC-1 asserts the value and a test should not re-spell it.

In `_run_page`, a `BudgetRefused` arm **before** the general `except Exception`:

```python
try:
    stage.run(ctx)
except BudgetRefused:
    progress.reason = BUDGET
    progress.ordinal = ordinal
    return False
except Exception as error:
    progress.reason = f"{type(error).__name__}: {error}"
    progress.ordinal = ordinal
    return False
```

Order is load-bearing: `BudgetRefused` **is** an `Exception`, so the general arm
placed first swallows it and produces
`reason="BudgetRefused: the projected next call of …"` — a plausible string that
fails AC-1 on an exact comparison and passes any substring check.

**Everything else about the abort already works and must not be re-implemented.**
`return False` breaks the page loop *before* `progress.pages_done += 1`, so the
refused page does not count; `_mark_done` is never reached for it, so
`page.status` stays what it was; every earlier page committed its own writes in
its own transaction, which is AC-1's "persisted with its lines intact"; and
`_end_run` writes `outcome='aborted'`, `aborted_reason='budget'`.

`src/mangatl/domain/translation.py`.

`domain/translation.py` is inside `coverage-core`'s `--cov-fail-under=100` with

### C-7 — `TranslateStage.run`: guard, call, record, write — in that order

```python
def run(self, ctx: PageContext) -> None:
    ocr_results = ctx.project.read_lines(ctx.page.ordinal)
    budget = budget_for(ctx.project)
    projection = budget.project(chapter_call_costs(ctx.project), pages_remaining(ctx))
    decision = budget.check(chapter_total(ctx.project), projection)
    if not decision.permitted:
        raise BudgetRefused(decision)
    image_bytes = (ctx.project.chapter.source_dir / ctx.page.filename).read_bytes()
    result = self.translate(image_bytes, ocr_results)
    if result.call is not None:
        record_call(
            ctx.project, ctx.run_id, ctx.page.ordinal,
            result.call.request_id,
            price(result.call.model_id, result.usage),
        )
    ctx.project.write_proposed(ctx.page.ordinal, result.lines)
```

RED may amend this block's shape. The four **orderings** below are the substance
and are not shape:

1. **The guard is before `self.translate(...)`.** This is AC-2 and the whole of
   D6: "a guard that notices the overrun after paying for it has not guarded
   anything" (`domain/budget.py`). This is **DV-1**.
2. **`record_call` before `write_proposed`.** Both open their own transaction and
   `Project.transaction()` is not reentrant (MT-005 PO-5), so they are two
   commits with a window between them, and a crash in that window resolves
   differently depending on the order. Proposals-first loses the *bill*: the page
   reads `is_done` on the next run, is never re-translated, and the spend is
   missing from `chapter_total` **for the life of the chapter** — the guard goes
   quietly inert, which is the exact failure this story exists to end.
   Ledger-first loses the *proposals*: the page is re-translated and billed
   twice, and both bills are in the ledger. Over-reporting spend is recoverable;
   under-reporting it is not.
3. **`price(...)` sits inside the `record_call` argument list, so an
   `UnknownModel` raises before either write.** A page whose model cannot be
   priced writes nothing and aborts the run through the runner's general arm.
   Accepted, with the trade-off named: a paid-for translation is lost. `rates.py`
   already decided this — "AC-5's *and nothing is recorded* follows from that".
4. **No transaction is opened in `run`.** Unchanged from MT-011 and for its
   reason.

`translate_stage.py` acquires imports of `mangatl.domain.budget`,
`mangatl.domain.rates` and `mangatl.store.ledger` — all down the layers. It still
may not import anything under `mangatl.translate` (MT-011 C-1), and nothing above
requires it to.

### C-12 — schema version 4: `budget_ceiling_micro_usd INTEGER`

**This block is the one with measured traps in it. Read all of it.**

`src/mangatl/store/schema.py`:

- Extract the `chapter` table into `CHAPTER_DDL`, exported beside `LLM_CALL_DDL`
  and concatenated into `DDL`, for MT-012 RED-A5's reason: two callers — a fresh
  file and the migration — and a migrated table must be the same table as a fresh
  one.
- In it, `budget_ceiling_usd REAL` becomes `budget_ceiling_micro_usd INTEGER`,
  **in the same column position** (sixth), so a `SELECT *` behaves the same on a
  migrated file as on a new one. Still nullable: `create_project` still has no
  business inventing a ceiling (MT-005 PO-8), and AC-5's second half is the NULL
  case.

`src/mangatl/store/project.py`: `SCHEMA_VERSION: int = 4`, a `_MIGRATE_TO_V4`
step, and `(4, _MIGRATE_TO_V4)` appended to `_MIGRATIONS`.

**`chapter` is a *parent* table with three cascading children — `page`, `run` and
`glossary`. MT-012's `llm_call` rebuild recipe applied here destroys the project,
in two different ways, neither of which raises.** Measured on sqlite 3.53.1,
2026-09-21, on a fixture with 1 chapter, 2 pages and 1 run:

| recipe | child FK after rename | pages | runs | `PRAGMA foreign_key_check` |
|---|---|---|---|---|
| A — rename + rebuild with the pragmas `_connect` leaves (`foreign_keys=ON`) | `REFERENCES "chapter_v3"` | **0** | **0** | `[]` |
| C — `foreign_keys=OFF` only | `REFERENCES "chapter_v3"` | 2 | 1 | **3 violations** (see correction below) |
| D/E — `foreign_keys=OFF` **and** `legacy_alter_table=ON` | `REFERENCES chapter` | 2 | 1 | `[]` |

- Without `foreign_keys = OFF`, `ALTER TABLE chapter RENAME TO chapter_v3`
  repoints every child at `chapter_v3`, and the `DROP TABLE chapter_v3` then
  **cascades and deletes every page and every run in the project**. Recipe A is
  the literal translation of MT-012's migration and it silently empties the file.
- Without `legacy_alter_table = ON`, the rows survive but every child still names
  a table that no longer exists. Recipe C's row counts are identical to D's:
  **a migration test that counts rows passes against the broken recipe.**
  `PRAGMA foreign_key_check` is the only thing that separates them, and RED must
  assert it. This is **DV-2**.

**Correction to the table above, raised by RED and reproduced independently by
lead-po on 2026-09-21.** RED measured **4** violations for recipe C where the
table says 3, and was right: the count is one per surviving child row, so it is a
property of the *fixture*, not of the recipe. The orchestrator's fixture had no
`glossary` row; RED's had one. Reproduced on a third, deliberately different
fixture — 1 chapter, **3 pages, 2 runs, 2 glossary rows**, without reusing RED's
script:

```
A both pragmas absent          {'page': 0, 'run': 0, 'glossary': 0}  fk_check=0  PRAGMA foreign_keys=1
C legacy_alter_table absent    {'page': 3, 'run': 2, 'glossary': 2}  fk_check=7  PRAGMA foreign_keys=0
D/E pinned recipe              {'page': 3, 'run': 2, 'glossary': 2}  fk_check=0  PRAGMA foreign_keys=0
```

Seven violations on that fixture, three on the orchestrator's, four on RED's.
**A test must therefore assert that `foreign_key_check` is empty, never that it
has a particular length.** The finding the table exists for — C violates and D
does not, while their row counts agree exactly — reproduces unchanged.

**And a second correction, also RED's, also reproduced above: metric 4 does not
discriminate the recipe.** `PRAGMA foreign_keys` reads `1` after recipe A (which
never turned it off) and `0` after both C and D (which did). So metric 4 is
evidence about **the restore's placement** and about nothing else, and C-12's
four metrics are a conjunction of which no proper subset is sufficient: row
counts miss C, `foreign_key_check` misses A, and the pragma read misses both.

So `_MIGRATE_TO_V4` opens with both pragmas as the first statements inside the
script (measured working as recipe E, with `executescript` committing first so
neither pragma lands inside a transaction):

```sql
PRAGMA foreign_keys = OFF;
PRAGMA legacy_alter_table = ON;
ALTER TABLE chapter RENAME TO chapter_v3;
-- CHAPTER_DDL
INSERT INTO chapter (id, source_dir, output_dir, created_at, schema_version,
                     budget_ceiling_micro_usd, model_id, rate_table_version)
SELECT id, source_dir, output_dir, created_at, schema_version,
       CAST(ROUND(budget_ceiling_usd * 1000000) AS INTEGER), model_id,
       rate_table_version
FROM chapter_v3;
DROP TABLE chapter_v3;
```

`CAST(ROUND(... * 1000000) AS INTEGER)` is MT-012's conversion and its reason: the
value still *is* a double at that point, and rounding to the nearest micro-dollar
is what turns it back into the exact decimal it was written from. A NULL ceiling
arithmetics to NULL and stays NULL, which is what AC-5's second half needs.

**And the restore. `_migrate_to_current` must put both pragmas back *after*
`connection.commit()`, not before it.** Measured 2026-09-21:

```
restore before commit ->  0      # silent no-op; still 0 after the commit
  after commit        ->  0
restore after commit  ->  1
```

`project.py`'s own docstring already records the general form — "the pragma set
*inside* an explicit transaction is a silent no-op that reads back `0`" — and the
`UPDATE chapter SET schema_version = ?` on the line above opens exactly such a
transaction under sqlite3's legacy isolation handling. So:

```python
    connection.execute("UPDATE chapter SET schema_version = ?", (SCHEMA_VERSION,))
    connection.execute(f"PRAGMA user_version = {SCHEMA_VERSION:d}")
    connection.commit()
    # After the commit, and measured: before it both of these read back
    # unchanged. `_connect` turned foreign keys on because every cascade in
```

**What it asserts now.** `_migrated()` is re-expressed on top of a new
