## Context

EPIC-13 priority 4 (cleaning). The benchmark's worst residual-ink region is
p011 region 0 at **0.4352**, against `RESIDUAL_INK_MAX = 0.0100`: white
narration over a photo, 70 x 629 px, which came out as a grey smear. Its
neighbour in the ranking, p008 region 1 at 0.0329, is 190 x 514 px. Both are
taller than `512 - 2 x MIN_CONTEXT_PX = 448`, so `clean_page` sends them down
the **downscale path**. That path shrinks the crop to 512 on its long side,
inpaints, and grows it back, so a 629 px column is reconstructed at about
0.8x and interpolated up. The module calls this path "a correctness fallback:
no component on the fixture pages takes it". On the benchmark,
**10 of 264** truth regions have a long side over 448 px.

A component that is long in one direction only can be cleaned at native
resolution in overlapping windows along its long axis. Each window is cut
from the working result, so the part already filled is context for the next
one. The seam failure MT-002 DV-1 names comes from cutting a hole across a
tile boundary that was filled independently. Sequential windows over the
working result fill each hole pixel once, with real context on both sides.
DV-2 checks that claim on real pages.

Required gates: `unit`, `coverage`. The real-model quality check is DV-2.

## Acceptance criteria

All with a recording fake `InpaintSession` that fills holes with a known
value and records every call's image and mask:

- **AC-1** - Given a 60 x 1000 px hole on a 1414 x 2000 page, when
  `clean_page` runs, then:
  - every session call receives a 512 x 512 window whose non-hole pixels are
    a byte-exact native crop of the working page, with no resize;
  - every hole pixel is written exactly once;
  - the calls advance down the long axis.
- **AC-2** - Consecutive windows on one component overlap by at least
  `STRIP_OVERLAP_PX` along the long axis, and each call's mask is only the
  part of the hole not yet filled.
- **AC-3** - *(control: the fallback is still there)* Given a 600 x 600 hole,
  long on **both** axes, then the downscale path runs as today, and the
  session sees a resized crop.
- **AC-4** - A component that fits the native window (at most 448 on both
  axes) is cleaned exactly as today, with one call. AC-4 of MT-019 (nothing
  outside the mask changes) holds for every case above.
- **AC-5** - A horizontal 1000 x 60 hole is cleaned the same way along x.

### C-2 Which path a component takes

Decided per 8-connected component, from its bounding box `(bw, bh)`, with
`LIMIT = 512 - 2 x MIN_CONTEXT_PX = 448`:

| `bw` | `bh` | Path |
|---|---|---|
| at most 448 | at most 448 | **native**, as today: one call |
| above 448 | at most 448 | **strips** along x |
| at most 448 | above 448 | **strips** along y |
| above 448 | above 448 | **downscale**, as today: one call |

Components are still processed in ascending label order, each from the
working result.

### C-3 The strips path

Call the long axis `t`. The component's bbox covers `[b, b + L)` on it, and
the page is `N` long on it. Write `LEAD = MIN_CONTEXT_PX + STRIP_OVERLAP_PX`
(64) and `TRAIL = MIN_CONTEXT_PX` (32).

- **The short axis** is one span for every window of the component:
  `_native_span` of the bbox on that axis, as the native path computes it.
- **The windows.** A cursor `c` starts at `b`. Until the component is filled:
  1. `lo = clamp(c - LEAD, 0, max(N - 512, 0))` and `hi = min(lo + 512, N)`.
     The window is `[lo, hi)` on `t`, by the short-axis span.
  2. If `b + L <= hi - TRAIL`, or `hi == N`, this is the last window and
     `end = b + L`. Otherwise `end = hi - TRAIL`.
  3. **The call's mask** is every pixel of this component inside the window
     with `t >= c`. That is the whole unfilled part in the window, including
     the part past `end`. So no unfilled hole pixel is ever shown to the
     model as context, and no filled pixel is ever masked again.
  4. **The write-back** is the component's pixels with `c <= t < end`, from
     this call's patch. Then `c = end`.
- **What follows from that**, and what the tests may pin:
  - Away from the page ends a window is 512 long, the cursor advances by
    `512 - LEAD - TRAIL = 416` per call, and consecutive windows overlap by
    `LEAD + TRAIL = 96`, which is at least `STRIP_OVERLAP_PX`.
  - Every window is a byte-exact crop of the working result, with no resize.
    On a page axis shorter than 512 it is edge-padded, as `_inpaint` does today.
  - Every component pixel is written exactly once. A pixel in the `TRAIL`
    band of a window that is not the last is masked in two calls and written
    from the second.
  - From the second window on, the first `LEAD` rows of the window on `t`
    hold pixels the earlier calls wrote, where the component covers them.
  - AC-1's case, a hole on `y = [500, 1500)`, is three calls: windows
    `[436, 948)`, `[852, 1364)`, `[1268, 1780)`, writing `[500, 916)`,
    `[916, 1332)`, `[1332, 1500)`.
- The write-back stays the one line ending `# write-back`, or one such line
  per path if GREEN cannot share it. Nothing outside the erase mask is
  written on any path.

## Notes

- **PO-1 (PLANNED, 2026-11-16): how a strip window fills.** The story said
  windows step by `512 - 2 x MIN_CONTEXT_PX - STRIP_OVERLAP_PX` and that each
  call's mask is the unfilled part of the hole. Two readings fit that. In
  one, a call writes everything it masks, up to the window's far edge. In the
  other, a call writes all but the last `MIN_CONTEXT_PX` it masks, and the
  next call fills those again with them in the middle of its window. C-3 pins
  the second. The reason: in the first, the pixels at each window's far edge
  are reconstructed with the hole running off the edge of the model's input,
  which is where a seam would show. The step formula's two `MIN_CONTEXT_PX`
  are then the context before and after each band. DV-2 judges it on real
  pages. Reported to the user at the end of RED; on 2026-11-17 the user chose to keep it ("Keep it").
