## Context

`architecture.md` D7 and §4. A 20-page run takes minutes and costs real money,
so it must be resumable; a crash mid-write must not cost the whole chapter. This
story creates the SQLite project file and the read/write path for it.

The schema in `architecture.md` §4 is written out in full there. This story
creates **all** of it — including the tables later stories fill — because a
migration on story three is cheap and a migration on story fifteen is not. What
it does not do is give any later stage a reason to exist.

**Which required gate would fail if this story's artifact broke:** `unit` and
`coverage` (the store is not in the 100% `coverage-core` set, but its logic is
pure enough that it should be close).

## Acceptance criteria

- **AC-1** — Given a chapter read by MT-004 and a target directory, when a
  project is created, then `<target>/project.db` exists, carries the current
  `schema_version`, and holds one `chapter` row and one `page` row per page with
  ordinal, filename, dimensions and sha256 preserved exactly.
- **AC-2** — Given an existing project file, when it is reopened, then the
  chapter and all pages come back byte-identical to what was written, including
  ordinals and hashes.
- **AC-3** — Given an existing project whose schema_version is *newer* than the
  code's, when it is opened, then a named error is raised rather than the file
  being read with the wrong schema.
- **AC-4** — Given a project where page 3's stored sha256 no longer matches the
  file on disk, when the project is opened against its source folder, then page
  3 is marked stale and every downstream artefact for page 3 only (regions,
  lines, cleaned image) is invalidated, and pages 1, 2 and 4 are untouched.
- **AC-5** — Given a write that fails partway (simulated by raising inside the
  transaction), when the project is reopened, then it is in its pre-write state
  — no partial page, no orphan region.
- **AC-6** — Given a project, when the same page's stage result is written
  twice, then the second write replaces the first and no duplicate row survives.
- **AC-7** — Given the project file, when it is created, then it is a sibling of
  the source folder (`<source>.mtproj/project.db`) and **no file inside the
  source folder has been created, modified or deleted**.

## Contract

```
src/mangatl/store/project.py
    SCHEMA_VERSION: int                      # starts at 1
    def create_project(chapter: Chapter, project_dir: Path) -> Project
    def open_project(project_dir: Path) -> Project
    class SchemaTooNew(Exception)
    class Project:                           # context manager; closes the conn
        chapter: Chapter
        def pages(self) -> tuple[Page, ...]
        def refresh_from_source(self) -> tuple[int, ...]   # stale ordinals
        def transaction(self) -> ContextManager[Cursor]

src/mangatl/store/schema.py
    DDL: str                                  # the full schema, one string
```

**Semantics behind each decision — one sentence each:**

- **`SCHEMA_VERSION` is an integer stored in the file, and `open_project` raises
  `SchemaTooNew` when the file's number exceeds the code's.** Reading a newer
  file with older code is the silent-corruption path; refusing is the cheap one.
  Reading an *older* file is a migration, and there are none yet — a v1 file
  opened by v1 code is the only case this story handles.
- **`refresh_from_source` returns the ordinals it invalidated**, so a caller can
  report "3 pages changed" without re-querying. An empty tuple means nothing
  changed.
- **Invalidation is per page and cascades down, never up.** Page 3's regions,
  lines and cleaned image go; page 3's *row* stays, with its hash updated. No
  other page is touched. This is the whole point of storing a per-page hash.
- **Every stage write is one transaction per page per stage** — that is the
  resume granularity (`architecture.md` §6), and it is why AC-5 is a criterion
  rather than an implementation detail.
- **`region.mask_blob` is a PNG-compressed 1-bit mask stored in the database**,
  not a loose file, because a loose file makes atomicity somebody else's problem.

**Create every table from `architecture.md` §4** — `chapter`, `page`, `region`,
`line`, `run`, `llm_call`, `glossary` — with their foreign keys and the
`ON DELETE CASCADE` that makes AC-4 a one-statement operation. Turn on
`PRAGMA foreign_keys = ON` on every connection; SQLite defaults it **off**, and
a cascade that silently does not cascade is exactly the bug AC-4 exists to catch.

**Oracle partition:**

| AC | Kind | Instruction to RED |
|---|---|---|
| AC-1, AC-2, AC-6, AC-7 | **Mechanical** | Round-trip and idempotence. Pin exactly. |
| AC-3, AC-5 | **Mechanical** | Named error type; failure injected, not simulated by mocking the whole store. |
| AC-4 | **Mechanical**, but see below | The cascade is specified; assert what survives *and* what does not. |

**AC-2 is a round trip, and `story-authoring` has a warning attached to exactly

satisfied by an implementation that never reads part of what it wrote, as long
as it can reconstruct that part by other means. So AC-2's test must assert
against a project opened from a **fresh connection in a fresh process-equivalent
state** (a new `open_project` on the path, not a cached object), and the
`## Deferred verifications` block below exists to prove the read path actually

### PO-2 - `page.status`: exactly two values, TEXT, no CHECK

AC-4 says page 3 is "marked stale", and the marker must survive a reopen or the
word means nothing. `architecture.md` §4 gives `page.status` and no vocabulary.

- `PAGE_PENDING = "pending"` - written by `create_project` for every page.
- `PAGE_STALE = "stale"` - written by `refresh_from_source` for each invalidated
  page.
- The column is `TEXT NOT NULL` with **no `CHECK` constraint**. MT-006 adds more
  values, and a CHECK here forces exactly the migration this story exists to
  avoid.
- `Page` (the `domain` dataclass) has no `status` field and does not gain one:
  `domain` describes a scan, not a run's progress through it. So the store
  exposes it separately:

```
    def page_status(self, ordinal: int) -> str
```

AC-4 therefore asserts, against a **reopened** project,
`page_status(2) == PAGE_STALE` and `page_status(n) == PAGE_PENDING` for n in
(0, 1, 3). Ordinals are 0-based from MT-004, so "page 3" in the AC prose is
ordinal 2.

### PO-3 - AC-6 is an upsert, NOT `INSERT OR REPLACE`. Measured.

`INSERT OR REPLACE` on a parent row **deletes that row's cascade children**:
the replace is a DELETE followed by an INSERT, and `ON DELETE CASCADE` fires on
it. Measured on sqlite 3.53.1 / CPython 3.12.14 with `foreign_keys = ON`,
against a `region` with one `line` attached:

```
OR REPLACE -> region rows: 1 line rows: 0
UPSERT     -> region rows: 1 line rows: 1
```

So AC-6's "the second write replaces the first and no duplicate row survives"
is only the half that is easy to satisfy. RED's AC-6 test must assert **both**:

1. one `region` row survives after two writes of the same
   `(page_id, reading_index)` - which requires the UNIQUE constraint to exist;
   and
2. the `line` attached to that region **is still there** - which fails against
   an `INSERT OR REPLACE` implementation and passes against
   `INSERT ... ON CONFLICT(page_id, reading_index) DO UPDATE SET ...`.

Without (2), a suite that destroys a page's translations every time detection
re-runs passes AC-6.

The UNIQUE keys the schema must carry, so RED can pin them:

| Table | UNIQUE | Why |
|---|---|---|
| `page` | `(chapter_id, ordinal)` and `(chapter_id, filename)` | ordinal is identity (MT-004); filename is how `refresh_from_source` matches |
| `region` | `(page_id, reading_index)` | one region per reading position per page |
| `line` | `(region_id)` | one line per region (§4 gives `line.region_id`) |
| `llm_call` | **none, deliberately** | §4: the ledger is append-only; a UNIQUE here would silently drop a real second call |
| `glossary` | `(chapter_id, term_ja)` | one English rendering per term per chapter |
| `run` | none | runs are events |

### PO-4 - `PRAGMA foreign_keys = ON` goes immediately after `connect()`

Measured: the pragma is a **silent no-op inside an explicit transaction** - set
inside `BEGIN`, it reads back `0`; set before `BEGIN`, it reads back `1`. And
SQLite's default really is off:

```
default foreign_keys pragma: 0
inside explicit txn, pragma reads: 0 (no-op if 0)
D pragma inside txn (set before BEGIN): 1
```

So it is set once per connection, before any transaction, in both
`create_project` and `open_project`. RED should pin this **directly** rather
than only through AC-4: on an open project, `PRAGMA foreign_keys` must read 1.
A cascade that does not cascade is the bug AC-4 exists to catch, and it is
invisible in every other assertion.

Also measured, for AC-4's one-statement invalidation: the two-level cascade
works - `DELETE FROM region WHERE page_id = ?` takes the region's `line` rows
with it.

### PO-5 - `transaction()` is non-reentrant and says so loudly

Measured, and this is the trap that would have made AC-5 vacuous. `with conn:`
is **not nestable** - the inner block's exit commits, so an outer raise does not
roll back:

```
E nested `with conn:` outer raises -> rows persisted: [4, 5]
```

and the obvious guard does not work either, because `Connection.in_transaction`
is `False` until the first DML statement inside the block:

```
after connect+executescript, in_transaction: False
inside `with conn:` BEFORE any DML, in_transaction: False
inside `with conn:` after a DML, in_transaction: True
```

So `Project.transaction()` keeps its **own instance flag**, not
`conn.in_transaction`, and raises `RuntimeError` when entered while already
inside one. One `if`, and it is the difference between AC-5 meaning "writes are
atomic" and AC-5 meaning "writes are atomic as long as nobody nests".

Confirmed working in the same probe: a raise inside a single `with conn:` rolls
back (`rows persisted: 0`), as does an explicit `BEGIN`/`ROLLBACK`. Also
confirmed: a DML statement with **no commit** followed by `close()` persists
nothing (`rows persisted: 0`) - a forgotten commit loses data silently, so
`transaction()` commits on clean exit.

### PO-6 - `refresh_from_source` matches by filename, and what it updates

- It re-reads the source folder through `store.intake.read_chapter(source_dir)`,
  reusing MT-004 rather than re-deriving hashing and decoding.
  `store.project` importing `store.intake` is an **intra-layer** import and is
  permitted - checked against `pyproject.toml`'s `layers` contract, which names
  `mangatl.store` as one layer with no container. So the `lint` floor stays at 5
  and **no import-linter contract changes in this story**.
- Stored pages are matched to freshly-read ones **by filename, not by ordinal**.
  Ordinal is identity (MT-004), and a file added or removed would shift every
  later ordinal.
- A stored page whose `sha256` differs from the fresh read is **stale**: its
  `sha256` **and** its `width`/`height` are updated (the file changed; leaving
  the old dimensions persisted would be storing a known-wrong value), its
  `status` becomes `PAGE_STALE`, and `DELETE FROM region WHERE page_id = ?`
  discards its regions, lines and masks by cascade.
- A stored page whose filename is **absent** from the fresh read is also stale;
  its stored hash and dimensions are left as they are, there being nothing to
  update them to.
- A file **present in the source folder but not in the project** is **ignored**.
  Adding pages to an existing project is out of scope, and renumbering ordinals
  to absorb it would break the identity MT-004 established.
- `NoPagesFound` and `FileNotFoundError` from `read_chapter` **propagate**.
  Repairing a source folder the user emptied is not this story.
- The return value is the stale ordinals, **ascending**.

### PO-7 - the version check reads `PRAGMA user_version`, not a column

`architecture.md` §4 lists `chapter.schema_version`, and `create_project` writes
it and keeps it for fidelity to §4. But it is **not** what AC-3 checks. Reading
a column out of a table whose shape you do not yet trust is self-defeating -
that is precisely the "read with the wrong schema" AC-3 forbids. SQLite's
`PRAGMA user_version` is schema-independent, so:

- `create_project` sets `PRAGMA user_version = SCHEMA_VERSION` **and** writes
  `chapter.schema_version`.
- `open_project` reads `PRAGMA user_version` **first**, before any SELECT, and
  raises `SchemaTooNew` when it exceeds `SCHEMA_VERSION`. The message carries
  both numbers, found and supported.
- The column is informational. An older version is a migration and there are
  none: a v1 file opened by v1 code is the only case this story handles.

This also makes AC-3's fixture constructible without RED knowing the table
layout at all: take a valid project and set
`PRAGMA user_version = SCHEMA_VERSION + 1`.

Two further pins in the same area, both about sqlite3 creating files behind you:

- `open_project` on a path with no `project.db` raises **`FileNotFoundError`**
  after an explicit existence check. `sqlite3.connect` *creates* the file, so
  without the check the failure surfaces later and as the wrong error.
- `create_project` where `project.db` already exists raises **`ProjectExists`**
  (a new exception in the module) rather than clobbering a project that may hold
  hours of edits.

### PO-8 - the `chapter` columns this story cannot fill

`architecture.md` §4 gives `chapter` eight columns. At create:
`source_dir = str(chapter.source_dir)`, `output_dir = str(<source>_en)` per §5,
`created_at` an ISO-8601 UTC string, `schema_version = SCHEMA_VERSION`; and
`budget_ceiling_usd`, `model_id` and `rate_table_version` are **NULL** - they
belong to MT-012 and MT-013, and this story has no reason to invent values for
them. The columns exist now so those stories need no migration, which is the
trade the story's `## Context` already states.

AC-2's "byte-identical" round trip is over `Chapter` and `Page` - `source_dir`
plus the five `Page` fields. `Path(str(p)) == p` holds, so `source_dir`
round-trips through TEXT.

`pages()` orders by `ordinal` **in SQL, explicitly**. A `SELECT` with no
`ORDER BY` is nondeterministic by contract even when it happens to look sorted,
and AC-2 is an ordering assertion.

`Project` is a context manager (`__enter__` / `__exit__`, where `__exit__`
closes the connection); `create_project` and `open_project` both return an
**open** `Project`; and `project.chapter.pages == project.pages()`.

### PO-9 - the ruff I001 flip: GREEN owns the fix, and it is a config line

...

- **GREEN** adds to `pyproject.toml` (a `config` path, which GREEN owns):
  `[tool.ruff.lint.isort]` with `known-first-party = ["mangatl"]`.
- **RED** writes its imports in the **post-fix, one-first-party-block** form,

- This changes the `lint` gate's behaviour, so GREEN records the control above

  block a name belongs in - and the probe is what makes that a fact rather than

**Three conventions that are load-bearing rather than stylistic**, all stated in
the module docstring so they survive into GREEN:

1. **AC-1's assertions are taken by a plain `sqlite3` connection** (`_raw`),
   never through `Project`. `tdd-cycle`: "a codec that is uniformly wrong

   depend on the read path at all.
2. **AC-2, AC-4, AC-5 and AC-6 assert against a project reopened from the
   path.** The object `create_project` returned is closed by its `with` block
   first and never consulted afterwards. `story-authoring`'s warning about round
   trips is that an implementation which never reads back part of what it wrote
   passes a same-object assertion.
3. **Every stage-shaped write is raw SQL through `project.transaction()`**, per
   PO-3. The `_INSERT_*` constants at the top of the file are consequently this
   suite's statement of the schema that §4 and PO-3 require, and GREEN should
   read them as the column lists to build against.

**The oracle partition, honoured.** Every AC here is mechanical, so no metric was
designed and no threshold calibrated - the risk this story actually carries is
the opposite one, a mechanical test that pins the wrong thing. Three places got
a deliberate discriminator rather than the obvious assertion:

| Place | The obvious test that would be vacuous | What is asserted instead |
|---|---|---|
| AC-2, ordering | `pages()` looks sorted because `create_project` inserts in ordinal order, so a `SELECT` with no `ORDER BY` passes | `_swap_ordinals` exchanges two rows' `ordinal` values *in place* after create, breaking the rowid/ordinal coincidence in a way no sort-on-insert can undo |

### 5. The export shape these tests already pin

```python
# src/mangatl/store/project.py
SCHEMA_VERSION: int          # == 1
PAGE_PENDING: str            # == "pending"
PAGE_STALE: str              # == "stale"

def project_dir_for(source_dir: Path) -> Path
def create_project(chapter: Chapter, project_dir: Path) -> Project   # returns it OPEN
def open_project(project_dir: Path) -> Project                       # returns it OPEN

class SchemaTooNew(Exception)    # message carries BOTH numbers, found and supported
class ProjectExists(Exception)   # message contains the substring "project.db"

class Project:
    chapter: Chapter                       # attribute, not a method
    def pages(self) -> tuple[Page, ...]    # a QUERY, ordered by ordinal in SQL
    def page_status(self, ordinal: int) -> str
    def refresh_from_source(self) -> tuple[int, ...]       # ascending
    def transaction(self) -> ContextManager[sqlite3.Cursor]
    def __enter__(self) -> Project                         # must return SELF
    def __exit__(self, *exc: object) -> bool | None        # closes the connection

# src/mangatl/store/schema.py

```

Pinned by an actual assertion, so do not vary it:

- **`Project.__enter__` returns `self`.** `test_a_project_is_a_context_manager...`
  asserts `entered is created`.
- **`Project.chapter` is an attribute**, read as `project.chapter`, with
  `project.chapter == the chapter passed to create_project` and
  `project.chapter.pages == project.pages()` (PO-8).
- **`pages()` queries the database.** After `__exit__`, `project.pages()` raises
  `sqlite3.ProgrammingError` ("Cannot operate on a closed database.", measured).
  A cached tuple would pass AC-2 vacuously and fail this.
- **`transaction()` yields something with `.execute(sql, params)`, `.fetchone()`,
  `.fetchall()`, `.lastrowid` and direct iteration** - i.e. a real
  `sqlite3.Cursor`. `cur.lastrowid` after an `INSERT` is how the tests get a
  region id.
- **`transaction()` is non-reentrant and raises `RuntimeError`**, and the guard
  **must not latch**: after a refused nesting, the next un-nested `transaction()`
  must work. `test_entering_a_transaction...` asserts both.
- **`transaction()` commits on clean exit and rolls back on any exception**, and
  the exception propagates - AC-5 catches a bespoke `_InjectedFailure`.
- **`transaction()` may be entered for a read.** `_pragma`, `_table_counts` and
  `_artefacts_by_ordinal` all run `SELECT`s and `PRAGMA`s through it with no DML
  at all. Measured: reading `PRAGMA foreign_keys` inside `with conn:` returns the
  true value both before and after a DML statement; only *setting* it inside a
  transaction is the silent no-op.
- **`pages()` and `page_status()` are only ever called from OUTSIDE a
  transaction.** RED restructured its own helpers so neither is ever called
  inside one - see section 12 item 5 for why that matters to you.
- **`SchemaTooNew` and `ProjectExists` derive from `Exception`**, not from
  `FileNotFoundError` or `sqlite3.Error`.
  `test_opening_a_directory_with_no_project_file...` expects a plain
  `FileNotFoundError`, which a subclass would also satisfy - so raise
  `FileNotFoundError` itself from the existence check.

### 12. What RED found that should change the implementation approach

1. **All ten PO decisions were re-measured before a test was written, and all
   ten hold** on this machine (CPython 3.12.14, sqlite 3.53.1). Reproduced
   verbatim: `default foreign_keys pragma: 0`; `set inside explicit BEGIN,
   reads: 0`; `set before any txn, reads: 1`; `OR REPLACE -> region rows: 1
   line rows: 0`; `UPSERT -> region rows: 1 line rows: 1`; `nested with conn:
   outer raises -> rows persisted: [4, 5]`; `in_transaction` `False` before the
   first DML; `DML with no commit then close -> rows persisted: 0`;
   `sqlite3.connect` creates a missing file. **Nothing to escalate.** The only
   correction is the PO-3 amendment above, which is about what a *test* can
   prove, not about the mechanism.
2. **Two facts PO-4 does not state that you need.** Reading `PRAGMA
   foreign_keys` *inside* `with conn:` returns the correct value both before and
   after a DML - only *setting* it inside a transaction is the no-op. And the
   one-statement two-level cascade works: `DELETE FROM region WHERE page_id = ?`
   takes the regions' `line` rows with it, so AC-4's invalidation really is one
   statement.
3. **`ON CONFLICT` is a schema dependency, not just a statement style.** The
   upsert form raises `OperationalError` unless a UNIQUE key covers exactly the
   conflict columns. When MT-007 writes regions for real it will need
   `UNIQUE (page_id, reading_index)` to still be there; a later story that
   "tidies" it into a plain index over different columns breaks the writer, not
   just a constraint.
4. **A non-obvious ordering hazard.** `create_project` inserts pages in ordinal
   order, so rowid order and ordinal order agree and a missing `ORDER BY` is
   invisible to 34 of the 35 items. Write the `ORDER BY ordinal` - PO-8 already
   says so - and note that the one test which catches it does so by swapping
   ordinals in place, not by expecting an unsorted insert.
5. **Do not implement `pages()` over `transaction()`.** It would work today, but
   PO-5 makes `transaction()` non-reentrant, so any future caller wanting the
   page list *inside* a write transaction would get a `RuntimeError`. RED
   restructured its own helpers to read `pages()` before opening a transaction
   precisely so that this stays your choice rather than a constraint the tests
   impose.
6. **pytest escapes non-ASCII safely, checked.** The suite uses real Japanese
   string literals for `line.source_ja` and `glossary.term_ja`. A failing
   assertion whose source line carries them prints as `最初` rather than
   raising `UnicodeEncodeError` on a cp1252 pipe - verified on this machine with
   a throwaway failing test, since a plain `print` of those bytes to a pipe
   *does* raise. So a red run in CI will be readable.
7. **`coverage-core` fails in RED purely as collateral.** `test_project.py` lives
   in `tests/core`, so its collection error interrupts the `coverage-core` gate
   too. That is not a `domain`/`typeset`/`bench` regression, and it clears the
   moment `store/project.py` exists.

- **`transaction()` is `contextlib.contextmanager` over `with self._connection:`**,
  with an instance flag set *after* the cursor is created and cleared in a
  `finally`. Creating the cursor first is what stops a closed connection
  latching the flag; clearing in `finally` is what makes the refused nesting
  recoverable (E11's second half).
- **`pages()` and `page_status()` go straight to the connection, not through
  `transaction()`** — handoff §12 item 5. `refresh_from_source` *does* use
  `transaction()`, deliberately: it is a project-level write, and a caller
  trying to nest it inside their own transaction is exactly the misuse PO-5
  wants to fail loudly.
- **`Project.chapter` is a read-only property**, and `refresh_from_source`
  re-derives it from the file before returning, so `chapter.pages == pages()`
  still holds after an invalidation instead of describing bytes that are gone.
  Untested either way; it keeps PO-8's invariant true rather than only
  usually-true.
- **Nullability of the columns no test constrains.** NOT NULL wherever the story
  that writes the row knows the value; nullable where a later stage supplies it.
  The one worth flagging: **`line.proposed_en` is nullable**, because OCR writes
  `source_ja` before translation exists to propose anything, and a NOT NULL here
  would force exactly the migration this story exists to prevent. Every column
  the handoff's table lists as nullable is nullable. The reasoning is in
  `schema.py`'s module docstring.
- **`llm_call.run_id` and `page_id` carry no `ON DELETE` action** while every
  other foreign key cascades. §4 calls the ledger append-only, and a bill that
  vanishes with its page row would make the money unauditable. No page row is
  ever deleted in this story, so nothing exercises the difference today.
- **`glossary.first_seen_page` has no foreign key**: it is a page *ordinal*
  (0-based, MT-004), and the suite writes `0` there — an FK to `page(id)` would
  have rejected it, since ids start at 1.
- **`DDL` does not contain `PRAGMA user_version`.** The version is a fact about
  one file, written by `create_project`; putting it in the schema would stamp it
  onto any connection that only wants the shape, including the in-memory one the
  DDL test uses.
