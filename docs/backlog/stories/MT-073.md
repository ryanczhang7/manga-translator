## Context

Split out of MT-028 on 2026-10-07 (its PO-1, user-approved): the third of the
High Contrast stories, and the one on the canvas. MT-026 decides what colour a
token is; MT-028 makes the chrome use it and exposes the mode as
`ThemeController.themeApplied(bool)`; this story makes the **canvas** react —
and, mostly, makes it *not* react.

**Two baselines this story has to build first, because MT-015 deferred them.**
`components.md` §3 says "a 1px `color.canvas.frame` line separates the viewport
from chrome", and A-13.2 wants a visible focus ring on every focusable control;
today `color.canvas.frame` is painted nowhere and `theme.qss.tmpl` has no
`#pageCanvas` rule, so the canvas has neither (MT-015 `## Test plan`: "the
`color.canvas.frame` line (no AC names it)"). A High Contrast delta on a line
that does not exist is not testable, so the dark-theme frame and ring are AC-1
here and the deltas sit on top.

Floor: `accessibility.md` **A-15.5, A-15.6, A-15.9**; reasoning in
`high-contrast.md` §6, §7, §7.1; deltas in `components.md` §10.3.

**The design point most likely to be "improved" by mistake:** the markers do
not change. Every `overlay.*` colour is `@static` because the markers are painted
on the user's scan, which a contrast theme cannot reach, and the two-stroke
halo-plus-core pair of A-06 already clears 3:1 against both extremes of the
artwork — which no single HC colour can (`tokens.md` §5). §7 argues it at
length; AC-2 and its mutation enforce it.

**Which required gate would fail if this story's artifact broke:** `unit` and
`coverage` (`tests/ui/`, offscreen). `required_gates` stays empty.

## Acceptance criteria

- **AC-1** — Given the default theme, when the canvas is shown, then a 1 px
  `color.canvas.frame` line separates the viewport from chrome, and when the
  canvas has keyboard focus a `focus.width` ring in `color.focus.ring` with its
  `focus.halo` is drawn around the viewport; neither moves the viewport's
  contents. *(`components.md` §3, A-13.2, `tokens.md` §7 — the baseline MT-015
  deferred.)*
- **AC-2** — Given High Contrast is active, when the canvas is painted, then
  every `overlay.*` colour and `color.canvas.surround` and
  `color.canvas.page-edge` are the **authored** values, unchanged — enumerated
  from `HC_PALETTE_ROLE`'s `@static` entries, not hand-picked. *(A-15.5, §6,
  §7.)*
- **AC-3** — Given High Contrast is active, when the canvas is painted, then
  **exactly three things differ** from the default theme and the markers are not
  among them: dimming stops (`overlay.dim.opacity` → `1.0`), the frame becomes
  `WindowText` at **2 px**, and the viewport focus ring becomes `WindowText`
  with a `Window` halo. *(`components.md` §10.3; A-15.5, A-15.6, §7.1.)*
- **AC-4** — Given High Contrast is active and a region is selected, when the
  canvas is painted, then **no marker is dimmed** (every marker's opacity is
  `1.0`) and the selected marker still differs from every other by core stroke
  width (3 px vs 2 px), selection fill, and a filled ordinal badge. *(§7.1.)*
- **AC-5** — Given High Contrast is active, when the frame colour or the focus
  ring colour is resolved, then each **falls back to its authored value if it
  fails 3:1 against the `#5F5F5F` mat**, checked at runtime through a pure
  function of two colours: the fallback triggers for a mid-grey `WindowText`
  such as `#808080` and does not for `#FFFFFF` (6.39:1) or `#000000` (3.29:1);
  nothing else on the canvas changes when it triggers. *(A-15.9. A fallback,
  not an exception.)*
- **AC-6** — Given the mode changes while a page is shown, when
  `themeApplied` fires, then the canvas repaints with the new frame, ring and
  dimming and keeps its zoom, pan and selection. *(A-15.10, canvas half.)*

## Contract

RED may amend any block in place with a reason; GREEN builds the amended block.

**Block 1 — `mat_safe` in `src/mangatl/ui/theme.py`.**

```
def contrast_ratio(a: str, b: str) -> float         # WCAG 2.x relative luminance, #RRGGBB in
def mat_safe(value: str, authored: str, *, mat: str = TOKENS["color.canvas.surround"]) -> str
    # value if contrast_ratio(value, mat) >= 3.0 else authored
```

Settled numbers to read out: `#FFFFFF` vs `#5F5F5F` = 6.39:1, `#000000` vs
`#5F5F5F` = 3.29:1 (`high-contrast.md` §6); the threshold is A-04's 3:1.

`mat_safe` is total: it never raises, and a value that fails is replaced, not
reported (A-15.9: "a fallback, not an exception"). `#808080` vs `#5F5F5F` is
**1.62:1**, computed for this contract — the one value AC-5 says must trigger.
No contrast arithmetic exists in `src/` today (`tests/ui/test_tokens.py` has
its own private copy); this block is the first production one, and the tests
for it compare against the documents' numbers, not against that copy.

**Block 2a — the boundary painter: `src/mangatl/ui/canvas.py`.**

```
def paint_boundary(
    painter: QPainter, rect: QRect, *,
    focused: bool,
    frame_width: int, frame_colour: str,
    ring_colour: str, halo_colour: str,
) -> None
```

A module-level function so the geometry is testable on a bare `QImage`
without a focused window. Geometry, in viewport pixels, `rect` being the
viewport's rect:

- **not focused:** the outermost `frame_width` px of `rect` are `frame_colour`
  on every side; nothing else is painted.
- **focused:** the outermost `focus.halo` (1) px are `halo_colour`, and the
  `focus.width` (2) px just inside them are `ring_colour`; the frame is covered
  while focus is shown, not drawn beside it (`components.md` §3 "a 2px
  `color.focus.ring` inset border on the viewport, with a 1px `color.focus.halo`
  outside it"; `tokens.md` §7, the ring is border-shaped, not outset).

Everything inside the painted band is untouched by this function — that is
what "neither moves the viewport's contents" means at the pixel level: the
page item and the markers are at the same scene-to-viewport mapping and the
same pixels with the band present as without it.

**Block 2b — the canvas: `src/mangatl/ui/canvas.py`.**

```
class PageCanvas(QGraphicsView):
    def set_high_contrast(self, enabled: bool, palette: Mapping[str, str]) -> None
    @property
    def high_contrast(self) -> bool
    @property
    def frame_width(self) -> int     # BORDER_WIDTH_HAIRLINE (1); BORDER_WIDTH_EMPHASIS (2) under HC
    @property
    def frame_colour(self) -> str    # TOKENS["color.canvas.frame"], or mat_safe(palette["WindowText"], that)
    @property
    def ring_colour(self) -> str     # TOKENS["color.focus.ring"],   or mat_safe(palette["WindowText"], that)
    @property
    def halo_colour(self) -> str     # TOKENS["color.focus.halo"],   or palette["Window"] (no mat check: §10.3)
```

The band is painted **in Python, last, over the viewport**: `PageCanvas`
overrides `QGraphicsView.paintEvent`, calls the base, then
`paint_boundary(QPainter(self.viewport()), self.viewport().rect(),
focused=self.hasFocus(), ...)`. Not `drawForeground`: that paints in scene
coordinates over the *exposed* scene rect, so a band fixed in viewport space
would be repainted only where the scene happened to be. The one consequence
GREEN owns and RED tests: **a pan must not leave a stale copy of the band
inside the viewport** (`QAbstractScrollArea` scrolls by shifting pixels). After
a pan the band pixels are at the edges and the pixel just inside the band is
not a band colour. How GREEN achieves it (`viewport().update()` in
`scrollContentsBy`, or `FullViewportUpdate`) is its choice; `#pageCanvas` gets
**no** new QSS rule, and `setFocusPolicy` is not changed.

`set_high_contrast(False, palette)` ignores `palette`; `set_high_contrast(True,
palette)` with `"WindowText"` or `"Window"` absent raises
`MissingPaletteRole` (theme.py's, re-used, not a new class) — consistent with
`resolve`, A-15.3. Either call ends with `self.viewport().update()` and a
`_restyle()`, and touches neither the transform nor the scroll bars nor
`_link_state`.

Dimming: `_restyle` passes `dimmed=False` for every marker when
`high_contrast` is true, and the existing `selected is not None and region_id
!= selected` otherwise. `BubbleMarker` and `markers.py` are **unchanged**;
`tokens_gen.HC_OVERRIDE["overlay.dim.opacity"]` is the documented value (1.0),
and `_restyle` may read it or may simply not dim — RED asserts
`marker.opacity() == 1.0`, not the mechanism.

**Block 2c — the wiring: `theme.py`, `workspace.py`, `app.py`.**

```
class ThemeController:
    @property
    def palette(self) -> Mapping[str, str]   # the palette read by the last apply(); {} while off

class Workspace(QMainWindow):
    def follow_theme(self, controller: ThemeController) -> None
        # applies controller.high_contrast / controller.palette to page_canvas NOW,
        # then connects controller.themeApplied so every later apply() does the same
```

`app.open_folder` calls `window.follow_theme(_theme)` when `_theme is not
None` — it is the only place a `Workspace` is constructed (`rg 'Workspace\('`
over `src/`: `app.py:137` alone). `Workspace.__init__` keeps its signature;
tests that build a bare `Workspace()` are unaffected. `themeApplied(bool)`
keeps its signature: the canvas reads the palette from the controller, so no
existing connection changes.

**Callers of changed signatures: none.** Every name above is new
(`contrast_ratio`, `mat_safe`, `paint_boundary`, `set_high_contrast`,
`high_contrast`, the four colour properties, `ThemeController.palette`,
`Workspace.follow_theme`). `_restyle` is private to `canvas.py` and its three
callers are in that file. RED's handoff states that this was checked against
the tree.

**Block 3 — the test surface:** `tests/ui/test_canvas_high_contrast.py`.

- AC-1 and the geometry: `paint_boundary` onto a `QImage` filled with a
  sentinel colour that is no token's value, focused and not, both modes'
  parameters; sample the band rows/columns and the first pixel inside them.
  Then the real canvas: a loaded page, `viewport().grab().toImage()`, band at
  the edges; and after `horizontalScrollBar().setValue(...)` the band is at
  the edges only.
- AC-2 and AC-3: render the canvas with a page and regions to a `QImage`
  under both modes with a synthetic palette (`test_theme_apply.PALETTE`'s
  convention — values that appear nowhere in `TOKENS`, re-asserted here, not
  imported from that file). **Marker pixels identical** across modes:
  compare the viewport image inside the band, with no selection so dimming
  is not in play. **Exactly three things differ:** `frame_width`,
  `frame_colour`, `ring_colour`/`halo_colour` (the pair is delta 3) and
  dimming; everything else `PageCanvas` exposes — `zoom()`, scroll values,
  `_link_state`, marker count, each marker's `state()`, the background brush
  — is equal before and after `set_high_contrast(True, ...)`. The `@static`
  set is **enumerated** from `HC_PALETTE_ROLE` and asserted to contain every
  `overlay.*` token plus `color.canvas.surround` and `color.canvas.page-edge`
  (A-15.5 "Testable as").
- AC-4: with a selection, every `marker.opacity()` is `1.0` under HC and the
  non-selected ones are `OVERLAY_DIM_OPACITY` with it off; the selected
  marker's `state()` is `SELECTED` and the others `IDLE`. The 3 px / 2 px /
  fill / filled badge differences are **MT-016's** and already pinned in
  `test_markers.py`; here it is enough that `MarkerState` still drives them.
- AC-5: a pure-function test of block 1 against the four settled numbers.
- AC-6: a real `Workspace` + `ThemeController` on a `FixedContrastSource`
  with a synthetic palette provider, `follow_theme`, a page and regions
  shown, zoom and pan set, a region selected; `set_value(True)` then
  `set_value(False)`: `canvas.high_contrast` follows, the four colour
  properties follow, and `zoom()`, both scroll values and
  `selected_region_id` are what they were. And the wiring itself:
  `open_folder` with `app_module._theme` set to such a controller returns a
  Workspace whose canvas already reflects the controller's mode.
