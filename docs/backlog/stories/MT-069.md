## Context

Filed by the MT-068 spike under its AC-4(a). Read
`docs/wiki/audits/MT-068-cv2-parallel-failure.md`, `## Decided` 1, 3 and 4 and
evidence E3-E6 and E9, before anything else.

**What breaks.** OpenCV 5.0.0 runs its parallel calls on the statically linked MSVC
Concurrency Runtime. The first parallel cv2 call on a thread attaches that thread
to ConcRT, and the attach calls `SetThreadpoolWait` on the calling thread. If the
process's default Windows thread pool has lost its I/O completion port handle,
`SetThreadpoolWait` raises `0xC000070A` (`STATUS_THREADPOOL_HANDLE_EXCEPTION`).
cv2 reports that as `cv2.error: Unknown C++ exception from OpenCV code`, and it
happens on **every** parallel cv2 call that thread makes, for the life of the
process.

**How this has failed.** It failed the `unit`, `coverage` and `coverage-core`
required gates four times between 2026-09-28 and 2026-10-05. Inducing the state
reproduces the 2026-10-05 logs exactly: 135 failed, 30 errors, the same ids
(audit E6).

**Exposure in the app [INFERRED].** The app runs each pipeline run and each bake
on a new thread, so the app is exposed too.

**What this story does.** It makes the production cv2 call sites survive that
state. It is defence in depth. The trigger, a stray `CloseHandle` from CPython
3.12's `_wmi` worker, is MT-070's.

The required gate that fails if this story's artifact breaks is `unit`, which
runs `tests/core`.

## Acceptance criteria

- **AC-1** - Given a fresh Python process whose default thread pool's I/O
  completion port has been closed before any cv2 call, when `erase_mask` and
  `letterbox` are called on the main thread with the fixture inputs, then both
  return the same arrays and values as the same calls in a fresh process where
  nothing was closed. Neither raises.
- **AC-2** - Given the same process state, when the same two calls run on a
  `threading.Thread` started after the port was closed, then they return the same
  results as in AC-1's clean process.

## Contract

- **Production entry points under test (unchanged signatures):**
  `mangatl.clean.mask.erase_mask(regions: Sequence[RawRegion], page_size: tuple[int, int]) -> NDArray[np.bool_]`
  and
  `mangatl.detect.postprocess.letterbox(page, side=MODEL_INPUT_SIDE, pad=PAD_VALUE) -> tuple[NDArray[np.float32], LetterboxTransform]`.
  Use a page that is **not** already `side` wide. A same-size resize copies, never
  reaches ConcRT, and so cannot fail (audit E9). A 48x64 erase mask does reach
  ConcRT (audit E3).
- **The inducing step**, re-derived from audit recipe A and not copied from
  `spikes/`:
  - in a fresh `sys.executable` subprocess, before any cv2 call, close the
    lowest-valued handle whose object type (`NtQueryObject`,
    `ObjectTypeInformation`) is `IoCompletion`;
  - then make the calls.

  The audit measured that closing that handle, and only that one of the 15
  thread-pool handles tried, breaks parallel cv2 (E5).
- **Oracle partition.** Both criteria are **mechanical**: equality with the clean
  process's output, and no exception.
  - *Negative control:* the clean process must produce the reference output.
  - *RED's expected failure:* in the induced process, both calls raise `cv2.error`
    whose message contains `Unknown C++ exception from OpenCV code`, in every
    attempt. The audit measured 30 of 30 for a bare `cv2.dilate` (E5).
  - A RED failure of any other kind is the wrong failure.
- **Baselines read out, not re-derived:** audit E5 (30/30 induced, 30/30
  control), E6 (exact suite match), E9 (`cv2.setNumThreads(0)` or `(1)` survives
  the closed port; a thread that attached *before* the loss survives, one
  attaching after it does not).
- **Platform.** The mechanism is Windows-only. A `skipif(sys.platform != "win32")`
  marker is a fact about the platform, not a weakening. CI's `gates.yml` runs on
  `windows-latest`.
- **Layer: production start-up.** That means any process that imports the modules
  calling cv2, not `mangatl.app` alone. The gates are where this failed, and the
  test harness must inherit the fix by importing production code, not from a
  conftest of its own. The implementation is not chosen here. Audit E9 states the
  constraint that makes one option known to work, and it is evidence, not a
  recommendation.

**C-1. The test.** Path `tests/core/test_cv2_lost_completion_port.py`, decorated
`pytest.mark.skipif(sys.platform != "win32", ...)`.
- Each case runs **fresh `sys.executable` subprocesses** with the test's own
  environment: one *clean* and one *induced* per criterion.
- Each child writes its results to an `.npz` under `tmp_path`, plus a one-line
  JSON report on stdout. The parent compares them.
- Names are RED's to choose.

**C-2. Inputs.**
- **Page:** a deterministic `uint8` page of `(1125, 1600, 3)`, PO-1's real page
  size. It is not square and not `side` wide, so `letterbox` really resizes and
  reaches ConcRT (audit E9).
- **Regions:** at least three `RawRegion`s with real 1-bit PNG masks over that
  page.
- Build every input **before** the induced close. Seeding an RNG after the port
  is gone kills the process with an uncaught `0xc000070a` (MT-068 PO-7).

**C-3. The inducing step,** in the induced child, before any cv2 call.
Re-derive it; do not copy it from `spikes/`.
- Enumerate the process's handles.
- Close the lowest-valued handle whose `NtQueryObject` type name is
  `IoCompletion`.
- Report the handle value, and that `CloseHandle` returned true.
- If no such handle is found, or the close fails, the child reports it and
  the test **fails**.

**C-4. Assertions.**
- **AC-1:** the induced child calls `erase_mask(regions, (1600, 1125))` and
  `letterbox(page)` on its main thread.
  - The mask must be `np.array_equal` to the clean child's.
  - The canvas must be `np.array_equal` to the clean child's.
  - The `LetterboxTransform` must be `==` to the clean child's.
  - No exception may be raised.
- **AC-2:** the same, with both calls made on a `threading.Thread` started
  **after** the close, and the results handed back to the main thread.
  Compare against the clean child's results.
- **Vacuity canary (binding).** After the production calls, the induced child
  calls `cv2.setNumThreads(4)` (an explicit thread count, so any start-up
  setting is overridden), then `cv2.GaussianBlur` on a `float32` 200x300
  array, on a thread that has not called cv2 yet.
  - That call **must raise** `cv2.error` containing
    `Unknown C++ exception from OpenCV code`.
  - If the canary succeeds, the state was never induced and a pass would mean
    nothing, so the test **fails**.
  - Measured on 3.13.15 on 2026-10-05 by the Lead PO: an induced
    `GaussianBlur` fails 5/5, the clean control succeeds 5/5, and serial
    `fillPoly` and a same-size `resize` survive.
  - **RED checks** that the canary's explicit `setNumThreads(4)` really does
    re-enable the failure in an induced process. If it does not, amend the
    block with a canary that does.
  - **AMENDED IN RED (test-developer, 2026-10-05): the cv2 canary above is
    replaced; it cannot fire.** RED checked, and `setNumThreads(4)` does **not**
    re-enable the failure. It *removes* it:
    - [MEASURED] In an induced process, `setNumThreads(4)` + `GaussianBlur`
      (float32 200x300, 5x5) on a fresh thread **succeeds**: alone, after a
      failed scaling `resize` on the main thread, and after two of them. The
      first test run's canary reported `VACUOUS` in both induced children while
      `erase_mask` and `letterbox` raised the signature in the same process.
    - [MEASURED] The same holds for **any** `cv2.setNumThreads` value tried:
      -1, 0, 4, 12. After any one call, a later `GaussianBlur`, `dilate` or
      scaling `resize` on a new thread succeeds on a closed port. Without one,
      `GaussianBlur` fails on the main thread and on a new thread, and so does
      `cv2.getNumThreads()`.
    - [INFERRED] OpenCV's ConcRT backend then runs on a scheduler it created
      and attaches to explicitly, not the default scheduler's implicit attach,
      which is what registers the thread-pool wait (audit E3). So **no cv2-level
      canary can fire in a process where anything called `setNumThreads`** -
      which every containment of the E9 kind does.
  - **The binding canary is now:** after the production calls, on a fresh
    `threading.Thread`, the child makes the call ConcRT's attach makes (audit
    E3) directly through `ctypes`: `CreateEventW` (manual, unsignalled),
    `CreateThreadpoolWait`, then `SetThreadpoolWait(wait, event, NULL)`.
    - In the **induced** child it must raise `OSError` with
      `winerror & 0xFFFFFFFF == 0xC000070A` (`STATUS_THREADPOOL_HANDLE_EXCEPTION`,
      audit E1; ctypes' SEH guard, audit E4). If it succeeds, or fails with any
      other code, the test **fails**.
    - In the **clean** child it must succeed, then is cancelled and closed.
    - It is independent of every cv2 setting. [MEASURED] It raises `0xC000070A`
      in an induced process with and without a prior `setNumThreads(4)` or `(0)`,
      on the main thread and on new threads. It succeeds in a clean process.
    - What it proves: the default pool's port is **still gone** when the test
      reads the results, so an equal result is a survival, not an absence of
      the state. It does not prove cv2 would fail without the containment. That
      is D-1's job, and in RED the production calls themselves show it.
  - **C-3, checked:** "the lowest-valued `IoCompletion` handle" holds on
    3.13.15. Its value is `0x20` in most children and `0x24` in some. Either
    one, closed, gives the signature.

These are the four modules that `import cv2` (C-7). The call runs at import,
under the `import cv2` line it protects, so any process that can reach a cv2
call has already made it. `bake` imports `clean.mask` anyway, but it gets its
own call so that no import order or future refactor leaves a caller
uncontained. A shared helper module was rejected for two reasons. The stage
packages cannot share one under the layers contract. And `mangatl/__init__.py`
would import cv2 into every process, `domain`-only and CLI `--help` included.

**Mechanism.** OpenCV's ConcRT backend attaches a thread through the *default*
scheduler on its first parallel call. That attach is what calls
`SetThreadpoolWait` (audit E3). With an explicit `setNumThreads`, OpenCV
creates a scheduler of its own and attaches to that instead, which never takes
that path (E9; C-4 amended; PO-3).

The call is process-wide and idempotent:
- A repeat with the same count does not recreate the scheduler.
- RED measured that it also rescues a process whose main thread had already
  failed a parallel call.

It does not repair the default pool. The canary still raises in induced
children (below).

**Chosen N = -1, and why it is robust.** `-1` is OpenCV's documented "reset
to the system default". It is not a number chosen here; it is whatever count
OpenCV would have used anyway, made explicit.

- [MEASURED] In a clean process here, `getNumThreads()` is 12 before and
  after the call, so nothing goes serial.
- [MEASURED] In an induced process (port `0x20` closed),
  `setNumThreads(-1)` followed by a scaling `resize` and a 15x15 `GaussianBlur`
  succeeds on the main thread and on a new thread, with `getNumThreads()` = 12
  and the same sums as clean. Without the call, both threads raise
  `Unknown C++ exception` (scratchpad probe).
- [INFERRED] On a machine of any core count, every value is contained:
  - default > 1: an explicit scheduler of that size, the path measured above;
  - default 1: OpenCV runs serial, which E9 measured as contained.

  CI's `windows-latest` (4 vCPU) therefore gets a 4-thread explicit scheduler,
  the same as PO-3's measured `setNumThreads(4)`.

  A hard-coded N would be wrong on some machine:
  - `os.cpu_count()` ignores `OPENCV_FOR_THREADS_NUM` and the process's
    affinity;
  - a constant 4 under-uses a 12-thread desktop.

  `getNumThreads()` cannot be queried first, because it is itself a failing
  call on a closed port (RED).
