## Context

EPIC-05 owns the review workspace and its theme. `components.md` §5's state
table (lines 883-888 at origin/main f1b2c15; 929-934 after the Lead
Designer's 2026-11-03 amendments) gives three statuses a border of their own:
`edited` a **2px `color.accent.base` leading bar even when unselected**
(deliberately `border-width.emphasis`, never `bar`), `failed` a **1px
`color.status.danger` frame** on all four sides, and `excluded` **no bar**
(an `edited` line's 2px bar is not shown while excluded; the selection's 3px
bar still is). None is a rule today: `theme.qss.in` 406-446 colours only the
gutter glyph and the excluded editor's text by `status`, and the status lives
on the gutter and the editor (`workspace.py` 754, 770), not on the row. Under
High Contrast, §10.4 (`components.md` 1312 at f1b2c15; 1448-1474 amended)
makes the `failed` frame **2px `WindowText`** and the `edited` bar
`WindowText` on `Window`, replaced by the selected bar on the selected row.

This story depends on **MT-135** - a true dependency, not a collision: its
three rules sit between MT-135's hover rule (slot 2) and selected rule
(slot 6) in the one-border-box precedence list (components.md 998-1016), and
every combination it tests (selected + edited = one 3px bar; selected +
failed = 3px accent left, 1px danger elsewhere) needs the selected bar MT-135
builds. It adds a row-level `status` property set in `_render` beside the
gutter's, re-polished the same way. Every line number above was re-read in
this worktree by the Lead PO at PLANNED.

The required gate that fails if the artifact breaks: `unit` (and `coverage`)
over `tests/ui`; `covers | unit | src/mangatl/**` reads `workspace.py`.

## Acceptance criteria

Sampling as MT-135: the packaged `theme.qss` as the application sheet, a shown
`Workspace` built with `_workspace_with_rows(qtbot, tmp_path, statuses)` so
each row has the status named, rows inside the viewport; "column *n*" and
"line *n* of an edge" are the lines *n* pixels in from the row's left edge or
from the named edge, over the row's extent less the item spacing band (RED
records the band and the corner inset, if the row has any radius - it has
none today). "Selected" is `translation_column.select(k)`.

- **AC-1** — *An unselected `edited` row carries the 2px bar.* Given an
  `edited` row that is not selected, when its columns are sampled, then
  columns 0 and 1 are every pixel `color.accent.base` and column 2 is every
  pixel `color.surface.raised` - two, not three: `border-width.emphasis`.
- **AC-2** — *A selected `edited` row carries one 3px bar.* Given the same row
  selected, then columns 0, 1 and 2 are every pixel `color.accent.base` and
  column 3 is every pixel `color.surface.selected` - the selection rule wins
  the left side; there is no 2px bar inside or beside it.
- **AC-3** — *A `failed` row carries the hairline frame.* Given an unselected
  `failed` row, when its four edges are sampled, then line 0 of each edge is
  every pixel `color.status.danger` and line 1 is every pixel
  `color.surface.raised`.
- **AC-4** — *A selected `failed` row: bar left, frame elsewhere.* Given the
  same row selected, then columns 0 to 2 are every pixel `color.accent.base`
  and column 3 `color.surface.selected`; and on the top, bottom and right
  edges line 0 is every pixel `color.status.danger` and line 1 every pixel
  `color.surface.selected`.
- **AC-5** — *`excluded` shows no bar, selected or not.* Given an `excluded`
  row, unselected: columns 0 to 3 are every pixel `color.surface.raised`;
  selected: columns 0 to 2 `color.accent.base`, column 3
  `color.surface.selected` (the selection bar still shows, components.md
  934). *Control:* the same row with status `edited` and unselected satisfies
  AC-1, so the test tells "excluded hides the 2px bar" from "nothing was ever
  drawn".
- **AC-6** — *Every other status carries nothing.* Given unselected rows of
  status `proposed`, `accepted` and `reverted`, then columns 0 to 3 and line 0
  of every edge are `color.surface.raised`.
- **AC-7** — *A status change repaints.* Given an unselected `proposed` row
  sampled as AC-6, when its editor's status becomes `edited` (the
  `test_app_theme_paint.py` "status changes" path, through the editor) and
  the row is re-sampled, then it satisfies AC-1; and back to `reverted`, AC-6.
  (Fails without the row-level re-polish.)
- **AC-8** — *Nothing moves.* Given the rows of AC-1 to AC-6, every row's
  `geometry()` and `sizeHint()` and its gutter, badge and editor
  `mapTo(viewport, (0, 0))` are the same for every status and across
  selection.
- **AC-9** — *Under High Contrast the `failed` frame is 2px `WindowText`.*
  Given the HC-composed sheet with the five-role palette, an unselected
  `failed` row: lines 0 and 1 of every edge are every pixel `WindowText` and
  line 2 `Window`; an unselected `edited` row: columns 0 and 1 `WindowText`,
  column 2 `Window`; a selected `edited` row: columns 0 to 2
  `HighlightedText`, column 3 `Highlight` (the selection override, authored
  after the `edited` one, wins the left side - C-3's ordering constraint); a
  selected `failed` row: columns 0 to 2 `HighlightedText`, and on the other
  three edges lines 0-1 `WindowText`, line 2 `Highlight`. *Negative control:*
  the base template alone against the
  same palette gives the `failed` frame as line 0 `WindowText`, line 1
  `Window` - the 1px frame the override widens.
- **AC-10** — *The override is a real override.* `test_theme_apply.py`'s
  `OVERRIDES` gains `#translationRow[status="failed"]` with the emphasis
  `WindowText` border (C-3), and both parametrised tests pass for it.

No AC names a threshold. The combinations are each one parametrised case over
the same sampler (components.md 1041-1043). The central claim's negative
control is the defect put back (`## Deferred verifications`).

### C-1 The base rules (`docs/wiki/design/theme.qss.in`, replacing MT-135's placeholder comment between its rules 2 and 6)

```
#translationRow[status="failed"] {
    border: @{border-width.hairline}px solid @{color.status.danger};
}

#translationRow[status="edited"] {
    border-left: @{border-width.emphasis}px solid @{color.accent.base};
}

#translationRow[status="excluded"] {
    border-left: none;
}
```

- **Order is the mechanism.** All five `#translationRow[...]` rules have
  specificity (1,1,0), so the later wins per property: `[selected]` (slot 6)
  restates `border-left` after all three and so wins the left side (AC-2,
  AC-4, AC-5); `[status="failed"]`'s shorthand sets all four sides and loses
  only the left to the selection (AC-4). `[status="excluded"]` after
  `[status="edited"]` is belt and braces - `excluded` replaces the stored
  status for display (`workspace.py` 740-750), so a row never matches both.
- **The semantics of 2 and 1.** `border-width.emphasis = 2` is the `edited`
  bar's width *by decision* (components.md 883 "deliberately 2px, never
  bar"): an edited line is marked, a selected one is marked more.
  `border-width.hairline = 1` is the danger frame (885). Neither is `bar` (3).
- `border: ... ` shorthand on `failed` comes **before** `[selected]`'s
  `border-left`, so the selected row keeps its frame on three sides.
- No `color` or ground declarations here: ground belongs to hover and
  selection (MT-135). Slot 7 (focus) stays unbuilt and commented.

The Lead Designer's amendments to `docs/wiki/design/components.md` (uncommitted
in this worktree on 2026-11-03; they land with MT-134's branch, in the
designer's own hunks - this story's agents do not edit that file):

- §5, **"How the row's ground and bars are rendered"**, lines 974-1044:
  **rules 3, 4 and 5** of the precedence list (`[status="failed"]` 1px danger
  all round; `[status="edited"]` `border-left` 2px = `emphasis`, deliberately
  never `bar`; `[status="excluded"]` `border-left: none`), the row-level
  `status` property set in `_render` beside the gutter's and editor's, and
  the combinations: selected + edited = one 3px bar; selected + excluded =
  the 3px bar, no 2px bar; unselected edited = the 2px bar alone; selected +

  still carried by the glyph and the caption, A-10).
- §10.4, lines 1448-1474: `edited` → the 2px bar becomes `WindowText` on
  `Window`, replaced by the selected bar on the selected row; `failed` → the
  1px danger border becomes **2px `WindowText`**, restated in the override as
  `RerunDialog[overBudget]` is (`theme_hc.qss.in` 51-54).

Designer's notes for this story, pasted from the 2026-11-03 brief: row-level
`status` property set in `_render` (beside `rowGutter` 754 and `rowEditor`
770), re-polished; rules between rest and `[selected]`: 3 `[status="failed"]`
border hairline solid `status.danger` (components.md 885), 4
`[status="edited"]` `border-left` emphasis solid `accent.base` (883, 2px never
bar), 5 `[status="excluded"]` `border-left: none` (888); combinations as above;

Tests: the combinations parametrised (designer's test 7). The PO added the
`edited` HC colour question in C-3 and resolved it from §10.4's own wording,
which the designer confirmed on 2026-11-03 (below), with the ordering constraint now in C-3.

**Designer's answer on C-3's `edited` colour (2026-11-03): the PO's reading
is correct — `WindowText` on `Window`, and the override rule is required.**
The base rule's `color.accent.base` maps to `Highlight` (`tokens.toml` 341),
and `Highlight` on a `Window` ground is not one of the two pairs Windows
guarantees (A-15.2: `WindowText`/`Window`, `HighlightedText`/`Highlight`), so
the mapped value is wrong under HC and components.md §10.4 (1449) says so
deliberately: the unselected `edited` row is `Window` ground, so its bar is
the ground's foreground, `WindowText`. Hence
`#translationRow[status="edited"] { border-left-color: @{hc.WindowText}; }`
in `theme_hc.qss.in`, and AC-9's unselected `edited` case reads `WindowText`
in columns 0-1 and `Window` in column 2. One ordering constraint, because the
two override selectors have equal specificity (one id and one attribute each):
this rule must be authored **before** MT-135's
`#translationRow[selected="true"]` override in the template, so that on a
selected `edited` row the later rule wins and the bar is 3px
`HighlightedText`, exactly as the base's rule 6 wins over rule 4. The
`failed` frame needs only its width restated (its colour already maps to
`WindowText`); on the selected row the frame's three sides are `WindowText`
on `Highlight` — not a guaranteed pair either, but a border is a boundary
against the row's edge rather than text on the ground, and the failure stays
carried by the glyph and caption (A-10); a reviewer who finds it illegible
on a real HC theme raises it as a follow-up, not here.
