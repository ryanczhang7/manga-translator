## Context

**Filed 2026-09-30 by the Lead PO**, on the user's decision, from a CI failure on
[[MT-056]]'s PR (ryanczhang7/manga-translator#50, run
https://github.com/ryanczhang7/manga-translator/actions/runs/36783767631).

MT-017's `test_an_edit_is_in_the_project_file_within_500_ms_of_enter`
(`tests/ui/test_line_review_workspace.py:656`) asserts in **wall-clock** time that
an edit is in the project file within `DESIGN_SAVE_BOUND_MS + SLACK_MS` = 500 +
250 = 750 ms of Enter. On the `windows-latest` runner, in the `unit` gate, it
measured **860 ms**:

```
>       assert elapsed_ms <= DESIGN_SAVE_BOUND_MS + SLACK_MS, f"on disk {elapsed_ms:.0f} ms after Enter"
E       AssertionError: on disk 860 ms after Enter
E       assert 859.9999999999 <= (500 + 250)
FAILED tests/ui/test_line_review_workspace.py::test_an_edit_is_in_the_project_file_within_500_ms_of_enter - AssertionError: on disk 860 ms after Enter
1 failed, 1667 passed in 244.72s (0:04:04)
```

The same test passed in the **same job's** `coverage` gate, which is
instrumented and so slower. It is not caused by MT-056: locally it takes 0.53 s
with MT-056's 87 drag tests run first (three runs) and 0.54 s alone (three
runs). MT-017's own GREEN notes record its figures as local only ("None is from
CI"): 500-516 ms against the 750 ms bound. It had passed on 8 CI runs since it
landed before this one.

CI runner time is noisy on identical code: across the last three runs,
`coverage-core` took 87 s, 428 s and 296 s, and `unit` 187 s, 238 s and 249 s.

## Acceptance criteria

- **AC-1** — Given the `unit` and `coverage` gates on the CI runner, when
  MT-017's AC-1 is checked, then the check fails when a commit is **not**
  saved within the design's 500 ms bound (a debounce raised well above it, as
  MT-017's own mutation table does with `SAVE_DEBOUNCE_MS = 60000`, still goes
  red), and does not fail on runner scheduling noise of the size measured
  above (860 ms). *How* - a different oracle, a measured slack, or moving the
  real-time half to an optional gate - is Q1, not decided here.

Constants: `DESIGN_SAVE_BOUND_MS = 500` kept (literal). `SLACK_MS = 250` kept -
it is still used, by the liveness waits and by
`test_a_save_that_fails_on_the_timer_also_keeps_the_text`'s `waitSignal`;
only its comment changed (it now sizes liveness waits, nothing else). New in
`test_line_editor.py`: `SECOND_COMMIT_AFTER_MS = 300` (C-1's gap, named) and
`TIMER_GRAIN_MS = 20`. `import time` removed from both files (unused).

**`TIMER_GRAIN_MS = 20`, measured and justified.** Outside pytest, 40 runs of
commit / `QTest.qWait(300)` / commit on this machine (Windows 11, offscreen):
`remainingTime()` after the second commit was 196-199 ms - never above
`500 - 300`, max excess -1 ms; wall-clock elapsed at the read 301.0-303.8 ms;
`remainingTime + elapsed - 500` in [-0.8, +0.7] ms, so the timer's clock and the
wall clock agree to under 1 ms. The grain covers integer-ms rounding (1 ms) and
one Windows default system tick (15.6 ms) in case a runner coarsens the timer;
it is not slack for scheduling, which only lowers `remainingTime`. A restart
reads ~500 (measured 499 under the restart mutation), 279 ms above the bound.

**Why scheduling noise cannot fail the new assertions.** The timer facts
(`isActive`, `isSingleShot`, `interval`) are read synchronously after
`QTest.keyClick` returns, before any event processing - they are configuration,
not time. "Nothing on disk yet" is read in the same synchronous stretch (a
delayed event loop can only delay the save further).

The no-restart test (C-1 amended): a `QTimer` fires only when the event loop
runs, so the 300 ms gap is a blocking `time.sleep`, and the second commit is
sent with `selectAll` / `QTest.keyClicks` / `QTest.keyClick` and *no*
`_settle` (the `_commit` helper is not used here: it calls `processEvents`).
Measured that `QTest` key clicks do not spin the loop: a `QTimer.singleShot(0)`
already due did not fire during `keyClicks` + `keyClick(Return)`, and fired at
the next `processEvents` (scratch script, outside pytest:
`zero-timer fired during key clicks: False` / `fired after processEvents:
True`). So the timer is still pending at the second commit however long the
runner stalls, and a stall only lowers both readings (to 0 when overdue).
Both bounds are one-sided and both are kept: `after <= before + 20` is the
restart check proper (a restart reads ~500 whatever `before` was);
`after <= 220` additionally pins that the timer running is the first commit's
(time.sleep guarantees at least 300 ms have passed), and an oversleep makes it
0, which passes.

Probe of robustness, against the real code (scratch copies of the test file in
the scratchpad with only the sleep changed, run with pytest):

```
1.51s call     test_oversleep_1500.py::test_a_second_commit_does_not_restart_the_save_timer
0.62s call     test_oversleep_600.py::test_a_second_commit_does_not_restart_the_save_timer
2 passed in 2.37s
```

and, outside pytest, the same logic at 300 / 600 / 1000 ms:
`before=199 after=199`, `before=0 after=0`, `before=0 after=0`, each saving
`('second', 'edited')`. Contrast: the same copy with the blocking sleep replaced
by the old non-blocking `qtbot.wait(600)` fails, because the first timer fires
in the gap:

```
E       AssertionError: the first commit did not leave the save timer running
1 failed in 1.08s
```

What remains exposed to the wall clock is only the liveness waits, 3000 ms
against ~500 ms needed - kept unchanged, not lengthened; the 860 ms CI
incident is 2140 ms inside them.
