## Context

**Filed 2026-09-29 by the Lead PO**, from
`docs/wiki/audits/opencv-unknown-exception-2026-09-28.md`, section "Addendum -
the WMI lead investigated (2026-09-29)", "Recommendations", first bullet
("Retention is the blocker"). It follows [[MT-046]] in the same lineage of
harness corrections ([[MT-031]]..[[MT-034]], [[MT-037]], [[MT-039]]..[[MT-043]]).

[[MT-046]] made `scripts/gates.sh` keep `.claude/state/gate-logs/<id>.failed.log`:
the **last** non-passing run of each gate, with a stamp, left alone by a pass.
That fixed the case it was filed for, where a passing re-run destroyed the only
copy of a failure. It does not fix the case that happened next.

Every story's RED run of `gates.sh --fast` fails `unit` **by design**. So a
`unit.failed.log` lasts only until the next story reaches RED. On 2026-09-29 the
MT-050 `unit.failed.log` was the one record of the recurring
`cv2.error: Unknown C++ exception from OpenCV code` intermittent. It held the
faulthandler `Windows fatal exception: code 0x8007000e` report and the 34 cv2
failures. About four hours later, MT-051's ordinary RED failure (a
`ZeroDivisionError` in `ui/badges.py`) replaced it (audit, **W0**). Two questions
the audit needs answered went with it:

- **W8.** Exactly one cv2-reaching test in `test_detect_postprocess.py` passed in
  the failing process. The lost log was the only record of which one.
- **W10.** Were there faulthandler reports *after* the first line? Dozens of
  `access violation` or `0xc000008f` reports would point at one mechanism, and
  none would point at another.

This is the second time the one log that mattered was lost. The first was on
2026-09-28, before MT-046.

This story keeps a failing log whose content matches an **unexplained
signature** in a place that later failing runs do not overwrite. It changes
what `gates.sh` **keeps**. It never changes what `gates.sh` **judges**: no gate
verdict, exit status, evidence line, floor, command or `## Gate results` record
changes (AC-9).

**Which required gate would fail if this story's artifact broke?** None, by
design (PO-3, as for MT-046). The judge is CI's `Harness self-test` step, which
runs `scripts/selftest.sh`, which runs `.claude/tests/gates.test.sh` and
`.claude/tests/settings.test.sh`.

## Acceptance criteria

These terms are used as [[MT-046]] defines them. **"Did not pass"** means any
outcome other than `pass` (`fail`, `noevidence`, `environment`, `blocked`), for a
required or an optional gate. **"A gate that ran"** means a gate whose command
was executed. **"Matches a signature"** means a line of the gate's log, cleaned
by `clean_log`, matches the extended regex of a `keep-when` line for that gate
in `.claude/harness/project.conf`.

- **AC-1** — Given a gate with a `keep-when` line, when that gate runs, does not
  pass, and its log matches the signature, then `scripts/gates.sh` writes a new
  file under `.claude/state/gate-logs/kept/`. After its header, the file holds
  that run's log byte-for-byte identical to `<id>.log`. Then, when the same gate
  later runs and does not pass again, with or without a signature, that file is
  byte-for-byte unchanged and still present. The only exception is eviction by
  the bound (AC-5).
- **AC-2** — The kept file's header carries the same stamp as MT-046's
  `<id>.failed.log`, computed the same way: the gate id, the outcome, the UTC
  time the gate started, the commit (with the uncommitted-changes note when it
  applies) and the gate tree hash. It also names the signature that matched: the
  `keep-when` regex, verbatim, and the first log line it matched. When more than
  one `keep-when` line for the gate matches, the header names the first one in
  manifest order, and the run still produces exactly one kept file.
- **AC-3** — Given a gate that ran and did not pass, and whose log matches no
  signature, when `scripts/gates.sh` finishes, then `<id>.failed.log` and the
  `failing log kept:` line are exactly what MT-046 specifies. `kept/` gains no
  file, every file already in it is byte-for-byte unchanged, and no
  `signature log kept:` line is printed. A run that *does* match a signature
  also writes `<id>.failed.log` and prints `failing log kept:` exactly as MT-046
  does. Every MT-046 assertion in `.claude/tests/gates.test.sh` and
  `.claude/tests/settings.test.sh` passes unmodified.
- **AC-4** — Given a gate that passes, including a pass whose log contains a
  line matching a signature, when `scripts/gates.sh` finishes, then no file under
  `kept/` is created, changed or removed, and no `signature log kept:` line is
  printed. The same holds for every gate a run does not execute: not selected by
  `--gate`, left out by `--fast` as `slow`, and every gate under `--list` and
  `--audit`.
- **AC-5** — `kept/` holds at most **5** files per gate id. Given 5 kept files
  for a gate, when a sixth run of that gate is kept, then the oldest of that
  gate's kept files is removed, and only that one. The other four and the new
  one remain byte-for-byte. Kept files of every other gate id are untouched,
  including an id that shares a prefix: evicting `coverage` never removes a
  `coverage-core` file.
  *Control:* 6 kept runs of `coverage` with distinct output, and 5 of
  `coverage-core`, must leave exactly 5 + 5 files. The first `coverage` run's
  output must be absent from every file, and all 5 `coverage-core` files must be
  unchanged.
- **AC-6** — The signatures come from `keep-when` lines in
  `.claude/harness/project.conf` and from nowhere else:
  - With no `keep-when` line, a failing log containing
    `Windows fatal exception` or `Unknown C++ exception` keeps nothing under
    `kept/`.
  - A `keep-when` line with an arbitrary regex, such as `ZEBRA-[0-9]+`, keeps a
    failing log that matches it.
  - `scripts/gates.sh` contains neither the string `Windows fatal exception` nor
    `Unknown C++ exception`.
- **AC-7** — The shipped `.claude/harness/project.conf` carries `keep-when` lines
  for `Windows fatal exception` and `Unknown C\+\+ exception`, one signature per

### The `keep-when` line

```
keep-when | <gate id> | <extended regex>
```

- It is parsed like `blocked-when`: `field 2` for the id, and `rest 3` for the
  regex, so a regex containing `|` survives. It is added to the `case "$kind"`
  allow-list at `gates.sh:155` and the per-kind `case` at `gates.sh:159-176`
  (`blocked-when` is at 174; line numbers re-measured 2026-10-14 against
  `e8d3e62`, the Contract's `~152` was the 2026-09-29 tree).
- Matching uses `grep -E` semantics over `clean_log "$log"`, case-sensitive.
  The `# line:` header field is the whole matched line (`grep -m1`, not `-o`).
  **Amended at RED (2026-10-14, Test Developer):** the block said "`clean_log
  "$log" | grep -Em1 -- "$regex"`, the idiom `blocked-when` already uses". It is
  not that idiom - `blocked-when` *detects* with awk, which reads all its input,
  and only *extracts* with `grep -Eom1 | head -1` inside `$(...)`, where no
  status is read - and as a status test it is the SIGPIPE defect
  `scripts/check-sigpipe.sh` exists to refuse: under `set -o pipefail`, once
  `grep -m1` leaves, `sed` dies writing the rest and the pipeline reports 141.
  Measured on this host, a signature on line 1 followed by 20,000 filler lines
  (348,917 B), `if sed … file | grep -Em1 …` matched **0 of 10** times; at
  6,000 lines (100,917 B) 5 of 5, at 10,000 (168,917 B) 0 of 5. Real failing
  logs are 23-29 KB today, so it would pass every test of ordinary size and
  then lose the one large log that mattered. So: **the decision must not rest
  on that pipeline's status.** Either capture the line and decide on its value
  (`kline="$(clean_log "$log" | grep -Em1 -- "$kre")"`, keep when non-empty),
  or drain after grep so its own status survives
  (`… | { grep -Em1 -- "$kre"; r=$?; cat >/dev/null; exit $r; }`, measured 10
  of 10 on the same log). Not awk: mawk has no interval expressions
  (HARNESS-025), and a `keep-when` regex is a user's ERE. A test pins it:
  "AC-1: a 348,917-byte log whose first line is the signature is kept". A
  regex that matches only an empty line is unconstrained by the tests.
- `scripts/gates.sh` must contain neither shipped signature in any spelling,
  the escaped `Unknown C\+\+ exception` included (*added at RED*: AC-6's two
  literal strings miss the form the manifest actually uses). So the header
  comment's example of the line kind uses some other regex.
- Lines for a gate are tried in manifest order, and the first match wins.
- A `keep-when` line never changes an outcome. It is read only after the
  `case "$outcome"` block has run.

### The kept file

Directory: `$LOGDIR/kept/`, created on first use (`mkdir -p`).

Name: `<id>.<seq>.<stamp>.log`.
- `<seq>` is a 6-digit zero-padded integer, one more than the highest `<seq>`
  among this gate's existing kept files, or `000001` if there are none. This
  makes "oldest" well defined when two runs start within the same second, which
  the test suite will do.
- `<stamp>` is `$started` with `-` and `:` removed (`YYYYMMDDTHHMMSSZ`), because
  Windows file names cannot hold `:`.
- "This gate's kept files" means names matching exactly
  `^<id>\.[0-9]{6}\.[0-9]{8}T[0-9]{6}Z\.log$`. A glob of `<id>*` would match
  `coverage-core` from `coverage`, and AC-5's control exists to catch that.

Content: an eight-line header, then the log exactly as `tee` wrote it to
`<id>.log`:

```
# gates.sh: failing run of gate '<id>' kept for a signature
# outcome: <fail|noevidence|environment|blocked>
# run:     <YYYY-MM-DDTHH:MM:SSZ>
# commit:  <commit_with_note output>
# tree:    <gate_tree_hash output>
# matched: <the keep-when regex, verbatim after trimming>
# line:    <the first cleaned log line it matched>
# ----
<the log, byte-identical to <id>.log from the same run>
```

- Lines 2 to 5 use the same values and helpers as MT-046's header
  (`$outcome`, `$started`, `commit_with_note`, `gate_tree_hash`). GREEN may
  compute each once and write it to both files.
- The file is testable as `tail -n +9 <kept file> | cmp - <id>.log`,
  immediately after the run that wrote both.
- It is written once and never rewritten. Only eviction removes it.

### When it is written, and eviction

After MT-046's `<id>.failed.log` step (`gates.sh:667-679` on 2026-10-14; the
`failing log kept:` print is line 679), inside the same
`if [ "$outcome" != pass ]` branch, and only when a `keep-when` line for `$id`
matches. After writing, if this gate has more than `KEEP_PER_GATE` kept files,
remove the lowest-`<seq>` ones until exactly `KEEP_PER_GATE` remain.

`KEEP_PER_GATE=5` is a named constant beside `LOGDIR` at the top of
`scripts/gates.sh`, with a comment that points here. It is not a `project.conf`
line: it bounds disk use, and it is not a property of the project.

Why 5 (PO-2 has the full reasoning):
- The intermittent recurred twice in about 24 hours (2026-09-28 in
  `coverage-core`, 2026-09-29 in `unit`).
- The audit learned most by comparing two incidents side by side. W8's `25 + 9`
  against the first report's "34, every one at line 340" was one such
  comparison.
- 5 keeps the next several recurrences of one gate side by side.
- If a signature ever starts to fire on every failing run, the directory stays
  bounded at 5 x the gate count. That is 45 files for the 9 gates today.
- Measured failing-log sizes in the main checkout on 2026-09-29:
  `unit.failed.log` 22,897 B and `coverage.failed.log` 28,931 B. Even at 1 MB a
  log, the worst case is under 50 MB.

## Out of scope

- **Any change to what a gate is judged to be.** No gate's verdict, command,
  evidence line, floor, waiver, `slow`, `covers`, `blocked-when` or
  `skipped-when` changes. Nothing changes the `## Gate results` record, the
  `last-gate-run` stamp, the summary lines or `record_in_story`'s output. A
  `keep-when` line never alters an outcome (AC-9). The one new `FAIL` path is
  `--audit`'s check of the new line kind (AC-7).
- **Any change to MT-046's `<id>.failed.log`**: its name, header, replacement
  rule or output line (AC-3).
- **An automatic re-run, retry or suppression** of the flaky tests or of any
  gate. Nothing marks a test flaky, skips it or reruns it. Keeping a log is the
  whole behaviour.
- **A fix for the cv2/onnxruntime intermittent itself.** The audit found none
  and filed none ("Decided" 4 of the addendum). That includes the gate-side
  mitigations it rejected, such as caching `platform.uname()` or moving
  `onnxruntime` out of `postprocess.py`'s imports.
- **Any change under `src/` or `tests/`.**
- **Upload or reporting anywhere outside `.claude/state/`.** No new CI artifact,
  no issue, no notification. CI already uploads `gate-logs/` as a directory, and
  on CI each run is fresh, so this story's value is local.
- **Keeping a passing log that contains a signature.** A pass carrying
  faulthandler's WMI line would be diagnostic too. The request fixes "a pass
  leaves everything alone" (AC-4), so this is left as an open question (PO-7).
- **Keeping the last N failing logs regardless of signature.** This was
  considered and declined (PO-2).
- **Showing `keep-when` lines in `--list`** as `blocked-when` and
  `skipped-when` are shown. That is useful, but it would change the
  `list.golden` fixture and is not needed to keep the log.
- **A wildcard gate id** (`keep-when | * | ...`). One line per gate, as with
  every other per-gate line kind.
- **Atomic writes, and locking between concurrent `gates.sh` runs.** Two
  concurrent runs could pick the same `<seq>`. `gates.sh` detects rather than
  locks (`.claude/state/README.md`), and the window is one `ls` long. File
  separately if it ever causes a problem.
- **A gate id containing `.`**, which would make the name pattern ambiguous.
  None exists.
- **Moving `mutate.sh --check` before the gate loop.** This is the follow-up
  MT-046 found. It is a separate story.
- **Python, or any dependency beyond bash, awk and coreutils**
  (`.claude/harness/rules.md`, "Portability").

### The shape the tests pin (fact, not suggestion)

- **Line kind:** `keep-when | <id> | <ERE>`; id by `field 2`, regex by
  `rest 3` (a `|` inside the regex survives: `(QUAGGA|OKAPI) [0-9]+`).
  Several lines per gate; tried in manifest order; first match wins.
- **Match:** `grep -E` semantics, case-sensitive (`windows fatal exception`
  must NOT match), over `clean_log`. A signature on line 1 of a 348,917-byte log
  must be found - see the amended Contract bullet: do not decide on the status
  of `clean_log | grep -m1`.
- **When:** only for a gate that ran and whose outcome is not `pass`
  (`fail` covers an optional gate printed `WARN`); after MT-046's
  `<id>.failed.log` is written. Never on a pass, never for a gate not executed
  (`--gate other`, `--fast` + `slow`, `--list`, `--audit`).
- **Directory/name:** `.claude/state/gate-logs/kept/<id>.<seq>.<stamp>.log`;
  `<seq>` = 6 digits, max existing for that id + 1, first is `000001`;
  `<stamp>` = that run's `# run:` value from `<id>.failed.log` with `-` and `:`
  deleted (the test derives it from `failed.log` line 3, so the two must come
  from the same `$started`). The tests list a gate's files with
  `^<id>\.[0-9]{6}\.[0-9]{8}T[0-9]{6}Z\.log$` and count *any* name by prefix
  (`nokw` must have none of any name).
- **Header (exactly 8 lines), then `<id>.log` byte for byte** (`tail -n +9 |
  cmp`):
  ```
  # gates.sh: failing run of gate '<id>' kept for a signature
  # outcome: <outcome>
  # run:     <same as <id>.failed.log line 3>
  # commit:  <same as <id>.failed.log line 4>
  # tree:    <same as <id>.failed.log line 5>
  # matched: <regex, verbatim after trim>
  # line:    <whole first cleaned line THAT regex matched>
  # ----
  ```
  Note the column alignment: `# run:     `, `# commit:  `, `# tree:    `,
  `# matched: `, `# line:    `.
- **Bound:** 5 per id; after writing, remove lowest-`<seq>` files of that id
  only until 5 remain. The 6th of `coverage` -> seqs `000002..000006`;
  `coverage-core`'s five untouched.
- **Stdout:** exactly one line per kept file,
  `signature log kept: .claude/state/gate-logs/kept/<file> (matched: <regex>)`,
  after the same gate's `failing log kept: …` line and before the next
  `=== gate: ` header. Eviction prints nothing on stdout that contains `kept/`.
  Not in `$results`.
- **`--audit`:** `printf 'FAIL %-12s a `keep-when` line names no configured gate\n'`

- **README row:** `| \`gate-logs/kept/*.log\` | \`scripts/gates.sh\` | … | yes |`

**PO-2: the retention decision is signature-triggered, not "the last N failing
logs regardless".** The request asked which is better. Signature-triggered is
better, for this repository, for these reasons:

- **Last-N measures a log's lifetime in ordinary failures. Signature retention
  measures it in recurrences of the thing worth keeping.** In this harness,
  ordinary failures are produced on a schedule: every story's RED fails `unit`
  by design, and GREEN's iterations add more. Several arrive per story, and two
  or three stories close in a day (MT-050 and MT-051 both closed on 2026-09-29).
  So with any N small enough to bound the directory, an intermittent's log still
  expires after a day or two of normal work. The audit's second investigation
  started about five hours after the incident and still found the log gone. To
  survive a week, last-N would need N of about 20-30 per gate. That keeps 20-30
  copies of known, explained RED failures in order to hold one unexplained one.
- **Signature retention keeps exactly what the audit asked for.** The audit's
  next steps (W8, W10) require the failing log of the next recurrence, and that
  log will contain one of the two named signatures.
- **Its weakness is the unknown next failure**, one whose signature nobody has
  written down yet. Two things mitigate it. MT-046's `<id>.failed.log` still
  catches that failure until the next non-pass. And adding a signature is one
  `project.conf` line (AC-6, AC-7), which is the right moment to decide the
  failure is worth keeping.
- **Doing both was declined** to keep this story to one cycle. If an unknown
  signature is ever lost the way W0 was, that is the evidence for a last-N
  story, and it should be filed then.
