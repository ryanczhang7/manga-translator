## Context

**Filed 2026-09-28 by the Lead PO**, from the investigation in
`docs/wiki/audits/opencv-unknown-exception-2026-09-28.md` ("Recommendations",
first bullet). Same lineage of harness corrections as [[MT-031]]..[[MT-034]],
[[MT-037]] and [[MT-039]]..[[MT-043]].

On 2026-09-28 the `coverage-core` gate failed once with 34 x
`cv2.error: Unknown C++ exception from OpenCV code`. The immediate re-run
passed, and in passing it overwrote `.claude/state/gate-logs/coverage-core.log`
- the only copy of the failure. The investigation could not pin the root cause
for that reason alone; the audit says so.

The overwrite is at `scripts/gates.sh:513-515`:

```bash
log="$LOGDIR/$id.log"
start=$(date +%s)
( cd "$ROOT/$cwd" && eval "$cmd" ) 2>&1 | tee "$log"
```

Every run of a gate truncates its log. That is right for `<id>.log` - it is
"what the last run said", and `-> .claude/state/gate-logs/<id>.log` in the
summary points at it - but it means an intermittent failure's evidence lives
exactly until the next run, which is usually the one somebody starts
immediately to see whether it was a flake.

This story keeps **one** extra file per gate, `<id>.failed.log`: the last run
of that gate that did not pass, stamped with when it ran and the code it ran
against. Nothing else about the run changes.

**Which required gate would fail if this story's artifact broke?** None, by
design - see PO-3. The judge is CI's `Harness self-test` step, which runs
`scripts/selftest.sh`, which runs `.claude/tests/gates.test.sh` and
`.claude/tests/settings.test.sh`.

## Acceptance criteria

"Did not pass" below means any gate outcome other than `pass` in
`scripts/gates.sh`'s outcome classification - `fail`, `noevidence`,
`environment` or `blocked` - for a required or an optional gate alike. A gate
that is never executed (unconfigured, no command, cwd missing, not selected by
`--gate` or left out by `--fast`) has no outcome and is not "a gate that ran".

- **AC-1** — Given a gate whose command runs and does not pass, when
  `scripts/gates.sh` finishes, then `.claude/state/gate-logs/<id>.failed.log`
  exists, begins with a header naming the gate, the outcome, the UTC time the
  gate started and the commit it ran against (with a note if the working tree
  had uncommitted changes) and the gate tree hash, and after the header holds
  that run's log byte-for-byte identical to `.claude/state/gate-logs/<id>.log`.
- **AC-2** — Given `<id>.failed.log` preserved from an earlier failing run,
  when the same gate later runs and passes, then `<id>.failed.log` is
  byte-for-byte unchanged (not removed, not rewritten), while `<id>.log` holds
  the passing run.
- **AC-3** — Given `<id>.failed.log` preserved from an earlier failing run,
  when the same gate fails again with different output, then `<id>.failed.log`
  holds only the newer run (its header and log), none of the older run's output
  remains in it, and no other preserved copy of that gate exists in
  `gate-logs/` (one file per gate, the last failure only).
- **AC-4** — Given no `<id>.failed.log`, when a gate runs and passes (including
  a PASS annotated for a missing evidence line or a no-longer-needed waiver),
  then no `<id>.failed.log` is created.
- **AC-5** — AC-1 to AC-4 hold identically under `--fast` and under
  `--gate <id>`; and a gate that a run does not execute - not selected by
  `--gate`, left out by `--fast` as `slow`, or any gate under `--list` or
  `--audit` - leaves its existing `<id>.failed.log` byte-for-byte unchanged.
- **AC-6** — Given a gate that does not pass, when `scripts/gates.sh` runs,
  then its stdout contains the line
  `failing log kept: .claude/state/gate-logs/<id>.failed.log`; given a gate
  that passes, no such line is printed for it.
- **AC-7** — `.claude/state/README.md`'s state-file table has a row for
  `gate-logs/*.failed.log` (written by `scripts/gates.sh`, hand-editable `yes`),
  and `.claude/tests/settings.test.sh`'s check of the shipped pair still reports
  no disagreements.

### The preserved file

Path: `$LOGDIR/<id>.failed.log`, i.e. `.claude/state/gate-logs/<id>.failed.log`
relative to the repository root. Exactly one per gate id.

Content: a six-line header, then the gate's log exactly as `tee` wrote it to
`<id>.log` for that run:

```
# gates.sh: last failing run of gate '<id>'
# outcome: <fail|noevidence|environment|blocked>
# run:     <YYYY-MM-DDTHH:MM:SSZ>
# commit:  <short sha>[ (working tree had uncommitted changes)]
# tree:    <gate_tree_hash output>
# ----
<the log, byte-identical to <id>.log from the same run>
```

- `outcome` is the internal outcome name the `case "$outcome"` block at
  `gates.sh:~568` switches on, not the display word (FAIL/WARN/KNOWN/BLOCKED),
  because the display word depends on required/optional/waiver and the outcome
  does not.
- `run` is the UTC time **captured just before the gate command starts**, in
  the same `date -u +%Y-%m-%dT%H:%M:%SZ` format `record_in_story` uses. Not the
  end time.
- `commit` and its dirty note are computed **exactly as `record_in_story`
  (`gates.sh:276-280`) computes them** - `git rev-parse --short HEAD`, falling
  back to `no commit`; the note when `git status --porcelain -- . ':!docs'` is
  non-empty. GREEN may factor that computation into a helper both call, but
  `record_in_story`'s output must stay byte-identical (Out of scope).
- `tree` is `gate_tree_hash` (`.claude/hooks/lib.sh:963`), the same hash the
  `## Gate results` block records. It is computed only when a gate did not
  pass, so a green run pays nothing.
- "Byte-identical" is testable as: `tail -n +7 <id>.failed.log | cmp - <id>.log`
  immediately after the run that wrote both.

Replacement is a whole-file overwrite (`>` / `cp`), never an append.

### When it is written

After the outcome of a gate that **ran** has been classified, and only when
`outcome != pass`. Never on `pass`. Never for a gate that did not run. Never
removed by `gates.sh` under any mode. `--list` and `--audit` do not reach the
run path and must not touch it.

### The output line (AC-6)

Exactly, on its own line, on stdout:

```
failing log kept: .claude/state/gate-logs/<id>.failed.log
```

printed once per non-passing gate, after that gate's `=== gate: <id> ...`
header and before the next gate's header. It is **not** added to `$results`:
`$results` is what `record_in_story` writes into a story's `## Gate results`
(`gates.sh:922`), and that record's content is out of scope. The existing
`-> .claude/state/gate-logs/<id>.log` pointers in the summary stay as they are
(`gates.test.sh:719` pins one).

### Oracle partition

All seven criteria are **mechanical**: a file exists or does not, bytes match
or do not, a line is printed or is not. *Precision beats invention; pin it
exactly, leave nothing open-ended.* There is no metric and no threshold, so no
negative control on a number is owed; the mutations under `## Deferred
verifications` play that role for the suite as a whole.

### How the tests run

Fixture only, like every other block in `gates.test.sh`:
`make_project_fixture` + `write_conf` from `.claude/tests/_lib.sh`, gate
commands that are `printf`s (a failing one: `printf 'boom A\n'; exit 1`). The
fixture is a git repository with one commit, so `commit:` can be asserted
against `git -C "$FIX" rev-parse --short HEAD` exactly. No test runs a real
gate or the real manifest.

```bash

bash scripts/selftest.sh settings   # AC-7's standing check
bash scripts/selftest.sh            # everything, before GREEN hands off
```

### Existing exports whose signature changes

None. `record_in_story` keeps its signature and output; if GREEN extracts a
commit/dirty helper, its only callers are inside `scripts/gates.sh`
(`record_in_story` and the new preservation code) - checked with

## Out of scope

- **Rotation or history.** One preserved copy per gate, the last non-pass.
  No `<id>.failed.1.log`, no timestamps in file names, no retention policy.
- **Any change to the gate record** - `## Gate results`, `last-gate-run`, the
  `-> <id>.log` summary pointers, `record_in_story`'s output. `check-boundaries.sh`
  reads the record; this story does not touch what it reads.
- **CI artifact upload.** Already done, for free: `.github/workflows/gates.yml`
  uploads `.claude/state/gate-logs/` on failure, so `<id>.failed.log` rides
  along. On CI each run is fresh, so it will equal `<id>.log` there; the value
  of this story is local re-runs. No workflow change.
- **Atomic replacement** (write-to-temp-then-rename). A kill mid-copy could
  leave a truncated preserved log; the window is one `cp` long, and a temp file
  would be another state file for the README table. File separately if it ever
  bites.
- **Preserving logs for gates that never ran** (unconfigured, no command,
  missing cwd). There is no log to keep.
- **A gate id that ends in `.failed`.** `foo.failed.log` would collide with
  gate `foo`'s preserved copy. No such id exists and none is plausible.
- **Adding a `selftest` gate.** PO-3; [[MT-039]] declined it with arithmetic.

**PO-1 - The phase lock enforces nothing in this story. The discipline is the
agents'.** Every path it touches classifies `harness`, which every phase
permits:

```

    .claude/tests/settings.test.sh .claude/state/README.md .claude/state/gate-logs/unit.failed.log; do

.claude/tests/gates.test.sh                  harness
.claude/tests/settings.test.sh               harness

```

So the story runs the ordinary **PLANNED -> RED -> GREEN -> GATES -> REVIEW ->
DONE** path, **not SCAFFOLD**: the behaviour can be written test-first, and
SCAFFOLD exists for work that cannot. RED writes only `.claude/tests/**` (and
`floors.conf`); GREEN writes only `scripts/gates.sh` and
`.claude/state/README.md`. Nothing will stop either from crossing; the handoff
and the diff are how the orchestrator checks they did not. No
`## Scaffold inventory` is needed: none of these paths classify `source`, so
`check-boundaries.sh`'s source-without-tests rule has nothing to judge.

Because there is no lock to make RED's failure real, `## Handoff` must carry
the failure output of `bash scripts/selftest.sh gates` verbatim. All of AC-1,
AC-3, AC-6 fail naturally in RED (no preserved file, no line). **AC-2, AC-4 and
AC-5's "untouched" halves pass on arrival** - today no `<id>.failed.log` is ever
created or removed, so "unchanged" and "not created" are trivially true. They
must be earned: for AC-4 and AC-5-untouched, the DV-1 mutation 2 in GATES is
the earning experiment; RED says so in the handoff rather than claiming a
failure it did not see. For AC-2, RED can make it fail honestly by seeding a
`<id>.failed.log` fixture and asserting it survives a pass *and* that a prior
failing run in the same test created it - the creation half fails in RED.

**PO-2 - `gate-logs/*.failed.log` is hand-editable `yes`, not denied.** Asked
explicitly by the orchestrator, so answered explicitly. The two `no` rows
(`current-story.env`, `last-gate-run`) are denied because a script **believes
their contents as a verdict** - the phase, and whether a gate obligation was
met. Nothing reads `<id>.failed.log` at all; it is diagnostic exhaust for a
human, same as the `gate-logs/*.log` row beside it. Forging it forges nothing
anyone acts on. And denial has a real cost: the README records, by probe, that
a file-specific deny also blocks a Bash `rm` of that path - so an agent could
not clear a stale failure after the cause is fixed, which is the one thing a
person will reasonably want to do to it. The row therefore carries no
settings.json rules, and `settings.test.sh`'s both-directions check stays green
with no rule change. Note the existing `gate-logs/*.log` glob already matches
`*.failed.log`; the separate row is there so the README says what the file is
and who reads it, not because the check needs it.

**PO-3 - `required_gates: []` is a decision.** No gate in `project.conf` reads
`scripts/**` or `.claude/tests/**`; the eight gates judge the product. The judge
is CI's `Harness self-test` step. Same answer as [[MT-043]] PO-4, for the same
reason.

**PO-4 - One cycle, not split.** One behaviour (keep the last non-pass log),
one file of production change, one test suite, plus a README row. AC-5 and
AC-6 are properties of the same code path under different flags, not separate
features; splitting them would produce stories that cannot be demonstrated
alone.
