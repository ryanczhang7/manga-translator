## Context

`integration` reports `PASS` on a machine where it ran one of its twenty-six
tests. Reproduced by the orchestrator at PLANNED, in this very worktree, against
the manifest as it stands (PO-1 below, pasted in full):

```
=== gate: integration (optional) ===
uv run pytest -q tests/integration -m "gpu or network"
sssssssssssssssss.ssssssss                                               [100%]
1 passed, 25 skipped in 2.71s

--- gate summary ---
PASS         integration (9s, observed 1)
```

The page scans and model weights the integration suite needs live under
`spikes/**`, which `.gitignore` covers, so every one of those tests calls
`pytest.skip` when they are absent. The gate's evidence line is
`evidence | integration | [1-9][0-9]* passed`, and **`1 passed` satisfies it**.
There is no `floor` line. So the gate reports `PASS` and is, on that machine,
precisely the vacuous gate the `evidence` mechanism was added to catch — see the
`project.conf` header ("exit 0 is not proof of work — it is the absence of a
complaint, and a tool with nothing to do does not complain") and the
`quality-gates` skill's "The vacuous pass".

**This is a defect in the gate, not a gap in a feature — hence `type: fix`.** A
mechanism whose stated job is distinguishing a gate that worked from one that
only exited 0 currently cannot distinguish them for this gate. AC-1 reproduces
it and its test becomes the permanent regression test.

### Why it is consequential now, and where the harm actually is

`integration` has had this property since MT-001. **MT-036 is the first story to
put it in `required_gates`**, making it binding — the first story, therefore,
whose *binding* gate could report PASS without exercising the artifact it was
made binding for. MT-011 already carries `required_gates: [integration]` and is
next.

The orchestrator's probes (PO-2, PO-3) moved where the harm is:

- **It is not principally a CI problem.** On CI there is no active story at all:
  `gates.sh` reads the story from `.claude/state/current-story.env`, which
  `.gitignore` excludes from every commit, so `required_gates` never escalates
  anything on a runner. CI's `integration` line has never been evidence for any
  story, and never could be.
- **It is a problem on the machine that records the evidence.** A git worktree
  does not carry gitignored files. This harness dispatches its work into
  `.claude/worktrees/**`. So an agent running `bash scripts/gates.sh` for a story
  that escalates `integration` — from a worktree, which is the normal case —
  gets `1 passed, 25 skipped`, records `PASS integration (observed 1)` into
  `## Gate results`, and `check-boundaries.sh` then reads that line and agrees
  that *"story-required gate 'integration' passed in the recorded run"*. Every
  mechanism in the chain behaves exactly as designed and the chain certifies
  nothing.

### What is already fine, and is not re-litigated here

**MT-036's own evidence stands.** Its `## Gate results` records
`PASS integration (7s, observed 26)` from a full local run in a checkout that
carried `spikes/`, stamped against tree `e777c915…`, and `check-boundaries.sh`
verified that stamp against the merged tree. This story does not re-verify
MT-036, re-measure anything MT-036 measured, or touch MT-036's file.

### The required gate that would fail if this story's artifact broke

**None of the eight.** Everything this story writes classifies as `harness`
(verified: `scripts/gates.sh`, `.claude/harness/project.conf` and
`.claude/tests/gates.test.sh` all classify `harness`), so no `covers` line
governs it and the `changes:` check never sees it. Its criteria are checked by
`bash scripts/selftest.sh`, which is a **CI step and not a gate** — it runs in
`.github/workflows/gates.yml` ("Harness self-test") and in `scripts/ci-local.sh`,
and it must stay green. `required_gates` cannot fix that, because no gate runs
the harness self-test; making one is named in `## Out of scope` as a follow-up.

## Acceptance criteria

<!-- AC-1 is the bug reproduction and is FALSE against the manifest as this

- **AC-1** — Given `integration`'s configuration in
  `.claude/harness/project.conf`, when its command exits 0 having run 1 of its 26
  collected tests (log: `1 passed, 25 skipped in 0.46s`), then `gates.sh` reports
  **something other than `PASS`** for it. *Against the manifest at the start of
  this story this is false: it reports `PASS integration (9s, observed 1)`, pasted
  in `## Context`. That output is the defect; the test that pins this criterion is
  the permanent regression test.*
- **AC-2** — *(negative control for AC-1)* Given the same configuration, when the
  command exits 0 on a machine that has the spike data (log: `26 passed in 7.1s`),
  then `gates.sh` reports **`PASS`**, and the summary names both the observed
  count and the floor (`observed 26, floor 26`). *A fix that satisfies AC-1 by
  making `integration` never pass fails here.*
- **AC-3** — Given a story whose frontmatter escalates a gate
  (`required_gates: [<id>]`) and a run of that gate that exits 0, falls below its
  floor, and whose log matches the gate's declared skip pattern, then the gate is
  reported **`BLOCKED`**, the run **exits 3**, and the stamped
  `## Gate results` records `result: blocked` — so there is **no `PASS <id>` line**
  for `check-boundaries.sh`'s *"story-required gate passed in the recorded run"*
  check to read.
- **AC-4** — Given **no** active story, so the gate is optional (the condition on
  CI and on any checkout between stories), and the same short, skip-matching run,
  then the gate is reported **`KNOWN`** with its reason inline, the run **exits
  0**, and the recorded result is still `pass`. *It is specifically not `WARN`: a
  WARN on every PR for the life of the project is the outcome MT-007 and MT-008
  declined a floor to avoid, and `quality-gates` reserves WARN for something that
  changed.*
- **AC-5** — *(negative control for AC-3 and AC-4)* Given the same gate and floor,
  when the command exits 0 with a count below the floor whose log does **not**
  match the skip pattern (log: `3 passed in 0.4s` — a suite that genuinely
  shrank), then the gate is reported exactly as a floor shortfall is today:
  **`FAIL`** when required, **`WARN`** when optional. *The pattern classifies a
  shortfall; it must never excuse one.*
- **AC-6** — Given a `skipped-when` line that (a) names no configured gate, or
  (b) carries no pattern, or (c) names a gate that has no `floor`, when
  `bash scripts/gates.sh --audit` runs, then the audit **fails** and says which of
  the three it is. *Negative control: a well-formed `skipped-when` on a floored
  gate passes the audit and is printed with it.* Each of the three can never
  protect anything: (a) fires on nothing, (b) would match every log and turn every
  shortfall into a block, (c) has no measurement to classify.
- **AC-7** — Given a gate carrying a `skipped-when` line, when
  `bash scripts/gates.sh --list` runs, then the pattern is printed under that
  gate, beside its `evidence`, `floor` and `blocked-when` lines.

### C-1 — The new `project.conf` table kind

Exact format line, to be documented in the `project.conf` header in the style of
the existing kinds:

```
skipped-when | <gate id> | <extended regex>
```

Parsed exactly as `evidence` and `blocked-when` are — `cut -d'|' -f3-`, so a
regex containing `|` (alternation) survives the split — and stored in a table
alongside `EVIDENCE`, `FLOORS`, `BLOCKEDWHEN`.

**Semantics, in one sentence:** *when a gate exits 0, matches its evidence
regex, and comes in below its floor, this pattern says whether the shortfall is
the environment declining to supply the work (report it as a block) or the suite
having lost work (report it as a floor shortfall, unchanged).*

It is consulted **only** in that one place:

- never when `rc != 0` — that path is the existing fail/`blocked-when` logic and
  is untouched;
- never when `observed >= floor` — a passing gate stays a pass even if some of
  its tests skipped;
- never when there is no floor — see the audit rule below.

Two live lines:

  reasoning.
- **Adding a `selftest` gate to `project.conf`.** This story's criteria are
  checked by `bash scripts/selftest.sh`, which is a CI step rather than a gate
  (`## Context`). Making it a gate is a real and possibly correct idea, and it is
  a change to what every story's gate run costs and means — its own story, with
  its own probe. Noted, not done.
- **Changing the `BLOCKED` advisory text `gates.sh` prints at the end of a run.**
  That block describes the pending-CI playbook, which is the wrong path for a
  `skipped-when` block (C-3 item 2). Correcting the prose belongs with the
  playbook; here it is documented in the `project.conf` header instead.
- **Unifying the existing launch-failure `BLOCKED` path's optional branch with
  the new one.** Today an optional gate the environment refused to launch reports
  `WARN`; the new path reports `KNOWN`. That inconsistency is visible and
  arguable, and changing the `rc != 0` path is a behaviour change to a mechanism
  with its own eight-run field report behind it. Not here.
- **A `discovery` line for `spikes/**`.** Tempting, and wrong: `discovery` asks a
  *runner* what it can see, and collection of the integration suite succeeds at
  26 whether or not the data is present — the skip happens at call time. A
  `test -d spikes` line would be reading the filesystem while wearing the
  runner's name, which is the exact anti-pattern the `discovery` header warns
  about. The gate's own `KNOWN` line is the diagnosis.
- **Any change to `src/mangatl/**` or `tests/**`.** This story does not touch the
  product.

### PO-1 — orchestrator probe, PLANNED, 2026-09-17: the vacuous PASS, on the real repo

orchestrator in this worktree
(`.claude/worktrees/quizzical-sanderson-f9d214`) against the manifest exactly as

PASS         integration (1s, observed 1)

### PO-4 — the decision: what won, and what each loser loses

The user asked for a probe rather than taste. All four options were run or read
against `gates.sh` before this was written.

**What wins: a narrow form of option 2, measured by option 1 and reported in
option 3's vocabulary.** A new `project.conf` kind, `skipped-when`, that
classifies a below-floor shortfall as environmental, plus the `floor | integration
| 26` that makes the shortfall measurable at all. One-line reason: *"N passed" is
not evidence of work when M were skipped* — option 2's sentence — and the only
way to say it without weakening anything is to measure the shortfall (option 1)
and then report an environmental one as a declared non-result (option 3's
`BLOCKED`/`KNOWN`) instead of noise.

- **Option 1, a bare `floor | integration | 26`. Rejected on its own; adopted as
  the measurement.** Probe D shows it closes the real hole: with a story
  escalating the gate, the short run FAILs instead of passing. Probe E and B show
  what it costs: CI never escalates, so on CI the shortfall is a `WARN` on every
  PR forever — exactly the outcome MT-007 and MT-008 wrote into `project.conf` as
  the reason `integration` has no floor, and exactly what `quality-gates` forbids
  ("WARN must mean something changed"). Their reasoning was right and is not
  overruled; it is *discharged*, because `skipped-when` turns that WARN into a
  `KNOWN`.
- **Option 2 as a regex change. Rejected as stated; adopted as the idea.**
  Evidence lines are matched with `grep -Eq`. "N passed **and** no skips" needs a
  negative lookahead POSIX ERE does not have, and the alternative — pushing the
  assertion into the gate command as `&& test $(…)` — moves the liveness check out
  of the mechanism built and audited for it into a shell one-liner nothing
  inspects. The `evidence` header's own rule ("assert volume of work observed")
  points at a *count*, which is a floor.
- **Option 3, extending `blocked-when`. Rejected as a reuse; adopted as the
  verdict vocabulary.** Probe F is decisive and is not a matter of taste:
  `blocked-when` is consulted **only** inside `if [ "$rc" -ne 0 ]`, and
  `1 passed, 25 skipped` exits **0**. The line never fires; the gate still reports
  `PASS … observed 1`. Making it fire on a zero exit would also contradict its own
  documented meaning — *"These patterns describe a process that never STARTED"* —
  and a pytest run that started, collected 26 tests and skipped 25 of them plainly
  started. What option 3 is right about is the *verdict*: `BLOCKED` when a story
  is leaning on the gate, and a declared non-result when it is not.
- **Option 4, leave it. Rejected — but half of it is true, and it is the half
  nobody was worried about.** Probe E confirms CI never escalates, so "the local
  stamped run is the evidence and CI was never meant to be" is correct about CI.
  The hole is *inside that local stamped run*: PO-1 shows a worktree — the normal
  place agents work — producing `PASS integration (observed 1)`, which
  `check-boundaries.sh` then reads as *"story-required gate 'integration' passed in
  the recorded run"*. Option 4 nominates as the backstop the exact mechanism that
  is fooled.

### PO-5 — two frontmatter decisions, and their reasons

**`depends_on: []`, and no edge to or from MT-011.** A `depends_on` edge is a hard
block: `phase.sh set` refuses to move a story past PLANNED while a dependency is
not DONE. MT-011 is fully buildable without this story — nothing in it needs
`skipped-when` to exist — so the relationship is *landing order*, not dependency,
and encoding an ordering preference as a hard block is how a backlog acquires
edges nobody can later justify. **Recommendation, recorded here and not written
into MT-011 (which is out of scope): land MT-037 before MT-011 starts.** It is
small, and MT-011's AC-8 is the next binding `integration` claim in the backlog.
If MT-011 starts first it is not harmed — it simply inherits the old behaviour and
must be gated from a checkout carrying `spikes/`.

**`required_gates: []`, deliberately.** Escalating `integration` here would be
self-defeating rather than rigorous: this story is developed in a worktree, PO-1
shows a worktree has no `spikes/`, so an escalated `integration` would report
`BLOCKED` and exit 3 at every GATES run — and the BLOCKED playbook's remedy
(quote the PR's CI log) cannot apply, because CI has no `spikes/` either. Nothing
would be learned. The better outcome is the one that arrives for free: with
`required_gates` empty, the full run at GATES will exercise the new rule against
the real gate and record **`KNOWN integration`** in this story's own
`## Gate results` — the fix demonstrating itself on the real manifest, which is
better evidence than a self-referential `PASS`. The real-suite `PASS … observed
26, floor 26` case is covered by probe P-2 (C-8), run from a checkout that has
the data.
