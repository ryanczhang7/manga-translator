## Context

EPIC-09 PO-7: corrections land on lines the user has **not** touched, as a
new `proposed_en`, with the previous text and the reason kept in a
`correction` row (MT-103); accepted, edited and reverted lines are left
alone. This story runs the pass (MT-114's request) from the pipeline after a
batch is collected (MT-112) - and after a synchronous run finishes - guards
each chunk before its call (D6, `call_estimate` from MT-105), ledgers each
chunk as a chapter-level row, and applies the parsed corrections.

**Open question Q-2** (EPIC-09): apply, as here, or show as suggestions. This
story is cut on "apply to untouched lines"; if the user chooses suggestions,
the application step becomes a `correction` row **without** the
`write_proposed`, and MT-116 builds the surface. The AC that would change is
AC-3; the rest holds either way.

The pass runs on `proposed_en` where the line is `proposed`, and on the
**user's `final_en`** as the current English where the line is `accepted` or
`edited` - the pass should see what the volume will actually read - but may
change only the `proposed` ones.

Required gates: `unit`, `coverage`.

## Acceptance criteria

- **AC-1** - Given a collected volume of three pages with a glossary, a fake
  pass returning two corrections for `proposed` lines, when
  `run_consistency_pass` runs, then each corrected line's `proposed_en` is the
  `corrected_en`, its status is still `proposed`, a `correction` row holds the
  previous text, the new text and the reason, `corrections_for(page)` returns
  it, and `CorrectionsApplied(applied=2, skipped_user_lines=0,
  unchanged_returned=0)` is emitted after a chapter-level `CallPriced`.
- **AC-2** - With one of the two corrections aimed at an `accepted` line and
  one at an `edited` line, neither line changes, no `correction` row is
  written for them, and the event reads `applied=0, skipped_user_lines=2`.
- **AC-3** - The pass's text for a page carries `final_en` for accepted and
  edited lines and `proposed_en` for proposed ones (the fake pass records
  the text it received).
- **AC-4** - Given a stored ceiling that the first chunk's `call_estimate`
  would exceed, the pass is **not** called, `RunAborted(BUDGET,
  ordinal=None)` is emitted, nothing is written; given a ceiling that admits
  the first chunk but not the second of two, the first chunk's corrections are
  applied and ledgered, the second is refused by name, and the event says how
  many chunks ran.
- **AC-5** - Each chunk that ran has one ledger row with `page_id NULL`,
  `pricing "standard"`, its usage priced at the interactive row, and
  `request_id` the call's; `chapter_total` grows by their sum and
  `chapter_call_costs` does not change.
- **AC-6** - In the batch flow the pass runs once, after the
  `BatchCollected` of the volume's **last** pending job (a volume split into
  several jobs, MT-137, runs it when none is still `submitted`); in the
  synchronous flow it runs once, after the last page and before the run
  ends, so that a refused pass ends the run as `RunAborted(BUDGET,
  ordinal=None)` exactly as a refused glossary pre-pass does, and
  `RunFinished` means the pages **and** the pass are done. A chapter whose
  pass already ran (`chapter.consistency_run_id` set) does not run it again
  when collected or run again. *Refined at PLANNED, 2026-11-05 (PO-2): the
  first wording said "after `RunFinished`", which would put a second
  terminal event after the first.*

    applied: int
    skipped_user_lines: int
    unchanged_returned: int

    chunks_refused: int

# pipeline/consistency.py  (pipeline may not import translate: text building, chunking, parsing come in as callables)
ConsistencyPass = Callable[[str], ConsistencyResult]
@dataclass(frozen=True)
class ConsistencyTools:          # bound by compose from translate.consistency
    text: Callable[[Sequence[PageLines], str], str]
    chunk: Callable[[Sequence[PageLines], str], Sequence[Sequence[PageLines]]]
    parse: Callable[[str, Mapping[tuple[int, int], str]], ParsedCorrections]
    max_output_tokens: int
def run_consistency_pass(project: Project, run_id: int, pass_: ConsistencyPass, tools: ConsistencyTools, model_id: str, emit) -> CorrectionsApplied
    """Per chunk: estimate = call_estimate(model_id, TokenUsage(estimate_tokens(text), max_output_tokens, 0, 0));
    Budget.check(chapter_total, Projection(estimate, ...)); refused -> stop, count; else call, record_call(None,...),
    emit CallPriced(None), parse, apply: for each correction, line status == "proposed" -> record_correction + write_proposed;
    else skipped_user_lines += 1. One transaction per chunk for the writes."""

# store: a marker that the pass ran - `chapter.consistency_run_id INTEGER NULL` (schema v9, one column) or

# compose.py: binds pass_ = partial(gemini.run_consistency, client) and the tools; None for anthropic.

**Semantics.**

- *What the pass sees (AC-3).* Pages in ordinal order, each page's lines from
  `store.lines.read_review_lines` (so `status` is the derived one), a `None`
  entry skipped. The English of a line is: `final_en` when its status is
  `accepted` or `edited` and `final_en` is not `None`; `proposed_en` when the
  status is `proposed`, `reverted`, or `accepted` with `final_en None` (an
  accepted line keeps the proposal's text, `domain.line.Line`); `None` for
  `failed` and `excluded` lines, and for any line whose chosen text is
  `None` - such a line is absent from the text and from `current`. A page
  with no line that has English is dropped before chunking (MT-114 drops its
  block anyway; dropping it here keeps `chunk` from sending a glossary-only
  request). The glossary block is `render_block(read_entries(project),
  MAX_GLOSSARY_TOKENS)` - the per-page prompt's block, `pipeline.continuity`'s
  rule.
- *Already ran.* `project.consistency_run_id() is not None` -> return
  `None`: no call, no event, no write, no marker change. *Nothing to send*
  (no page kept) -> no call, `mark_consistency_run(run_id)`, emit and return
  `CorrectionsApplied(0, 0, 0, 0, 0)`.
- *Per chunk* `i` of `K = tools.chunk(pages, glossary_block)` (a
  `PageTooLarge` propagates): `text = tools.text(chunk, glossary_block)`;
  `estimate_i = call_estimate(model_id, TokenUsage(estimate_tokens(text),
  tools.max_output_tokens, 0, 0))` (`domain.glossary.estimate_tokens`);
  `budget = budget_for(project, page_estimate(model_id))`;
  `decision = budget.check(chapter_total(project), Projection(next_call=estimate_i,
  remaining_chapter=sum(estimate_i..estimate_K-1), basis="estimate",
  sample_count=len(chapter_call_costs(project))))` - the remaining chunks
  are the rest of the chapter. **Refused with `i == 0`**: raise
  `BudgetRefused(decision)` - the caller turns it into `RunAborted(BUDGET,
  ordinal=None)`; nothing written, no event from the pass, marker unset.
  **Refused with `i > 0`**: stop; emit and return `CorrectionsApplied(...,
  chunks_run=i, chunks_refused=K - i)`; the marker stays **unset**, so a
  later run under a higher ceiling runs the whole pass again (the chunks
  already applied then come back as `unchanged_returned`, which is the
  cheap side of the two errors). **Permitted**: `result = pass_(text)`;
  `record_call(project, run_id, None, result.call.request_id,
  price(result.call.model_id, result.usage))` (`pricing` left at its
  `"standard"` default: the pass is interactive, Q-4); emit
  `CallPriced(ordinal=None, spent=chapter_total(project), ceiling=budget.ceiling,
  projection=budget.project(chapter_call_costs(project), 0))` - every page is
  behind the pass, so `pages_remaining` is 0; then
  `parsed = tools.parse(result.text, current)` with `current` the chunk's
  `(ordinal, reading_index) -> english` for every line in the text (an
  `UnknownLine` or `ValueError` propagates: the step fails, the caller
  reports it as it reports a failed prelude, earlier chunks' writes stand,
  the marker stays unset).
- *Apply.* For each `ProposedCorrection` in `parsed.corrections`, in order:
  the line's derived status is `proposed` -> `record_correction(project,
  run_id, page_ordinal, reading_index, before_en=current[(p, i)],
  after_en=corrected_en, reason)` **then** `project.write_proposed(page_ordinal,
  {reading_index: corrected_en})` - two store transactions, the row first,
  so a crash between them leaves a recorded change that was not applied
  rather than an applied change nobody recorded (replaces the sketch's "one
  transaction per chunk": both store calls open their own and refuse a
  caller holding one); `applied += 1`. Any other status (`accepted`,
  `edited`, `reverted`) -> nothing written, `skipped_user_lines += 1`.
  `unchanged_returned += parsed.unchanged_returned`. The line's `status`
  column is untouched by the write, so a corrected line is still `proposed`
  (AC-1).
- *End.* After the last chunk: `mark_consistency_run(run_id)`, then emit
  and return `CorrectionsApplied(applied, skipped_user_lines,
  unchanged_returned, chunks_run=K, chunks_refused=0)` - after the last
  `CallPriced` (AC-1).
- *Batch hook (AC-6).* `collect_volume`, after `emit(BatchCollected(...))`:
  when `postlude is not None` and `pending_jobs(project) == ()` (no job of
  the volume still `submitted`), run `postlude(project, job.run_id, emit)`;
  `BudgetRefused` -> `emit(RunAborted(BUDGET, None))`; any other exception
  -> `emit(RunAborted(f"{type(e).__name__}: {e}", None))` (`submit_chapter`'s
  spelling); the answer is returned either way, and the job stays
  `collected`. A job that is not the last runs nothing.
- *Synchronous hook (AC-6).* `run_chapter`: after the page loop, when
  `progress.reason is None` and `postlude is not None`, run it through the
  same helper the prelude uses (`_run_prelude`'s failure mapping, `ordinal
  None`); a failure sets `progress.reason`, so the outcome is `RUN_ABORTED`
  with `pages_done` the full count and no `RunFinished`.
- *Events.* `CorrectionsApplied` is a `RunEvent`. The UI's `progress` and
  the CLI tolerate an unknown event? They do not: `ui/progress.py` and
  `cli.py` match on event types - RED checks each consumer of `RunEvent`
  and lists what the new event does there (expected: nothing, through each
  consumer's fall-through; if a consumer raises on an unknown event, that
  consumer is in RED's handoff as a GREEN change and its file is added to
  `touches:`).
