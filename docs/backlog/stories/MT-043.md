## Context

**Filed 2026-09-21 by the Lead PO**, out of a defect the orchestrator found and
reproduced while closing [[MT-039]]. Same lineage of corrections to the
machinery [[MT-001]] built as [[MT-031]]..[[MT-034]], [[MT-037]] and
[[MT-039]]..[[MT-042]].

`bash scripts/gates.sh --audit` ends every run in this repository with:

```
WARN mutation     no evidence line; a vacuous pass would go unnoticed
...
1 required gate(s) have no evidence line. Add one per gate:
  evidence | <id> | <regex proving the tool did work>
Use `evidence | <id> | -` only where no such output exists, and say why in the story.

Manifest audit passed.
```
`[MEASURED — 2026-09-21, orchestrator, full --audit run captured to a file, 210 s]`

**`mutation` is `optional`, and it is the only gate in the manifest with no
evidence line.** All six required gates have one:

| gate | required? | has `evidence`? |
|---|---|---|
| `format` | optional | yes |
| `lint` | **required** | yes |
| `typecheck` | **required** | yes |
| `unit` | **required** | yes |
| `coverage` | **required** | yes |
| `coverage-core` | **required** | yes |
| `integration` | optional | yes |
| `build` | **required** | yes |
| `mutation` | optional | **no** |

`[project.conf:284-325 and 599; read 2026-09-21]`

So the sentence is false on its face: zero required gates have no evidence
line, and the audit says one does.

### The cause: two paths through one counter, guarded differently

`noevidence` is one variable (`scripts/gates.sh:277`), incremented from two
places and printed by two summaries. The normal run path guards the increment
by `req`; the `--audit` path does not.

**Normal run — `scripts/gates.sh:525-527`:**

```bash
elif [ "$exp" = "<none>" ] && [ "$BOOTSTRAPPED" = "yes" ] && [ "$req" = "required" ]; then
  results="$results\nPASS         $id (${dur}s) -- no evidence line: a vacuous pass would go unnoticed"
  noevidence=$((noevidence+1))
```

**`--audit` — `scripts/gates.sh:436-439`:**

```bash
if [ "$exp" = "<none>" ]; then
  printf 'WARN %-12s no evidence line; a vacuous pass would go unnoticed\n' "$id"
  noevidence=$((noevidence+1)); continue
fi
```

— **no `req` test at all.** Then `scripts/gates.sh:640-644`:

```bash
if [ "$noevidence" -gt 0 ]; then
  printf '\n%d required gate(s) have no evidence line. Add one per gate:\n' "$noevidence"
```

over the unguarded count. The run path's own summary
(`scripts/gates.sh:758-759`) uses the same words — *"%d required gate(s) ran
without an evidence line"* — and there they are true, because there the counter
was guarded. One variable, one wording, two population rules. That asymmetry is
the defect.

**The per-gate `WARN` line is accurate and useful and is not the problem.** It
names the gate, so a reader can see for themselves that it is optional. It is
also the *only* place an optional gate's missing evidence line is surfaced at
all: on a normal run, `gates.sh:525`'s `req` guard means an optional gate with
no evidence line prints a bare `PASS` with no annotation. The `WARN` stays.

### Why this is worth a story rather than a comment

**1. It cries wolf.** An audit whose *standing* output claims a required gate is
unguarded, when none is, is an audit people learn to skim. This lineage exists
because vacuous passes hide in output nobody reads — `project.conf`'s header
(*"exit 0 is not proof of work — it is the absence of a complaint, and a tool
with nothing to do does not complain"*) and [[MT-037]], which removed the last
way a gate here could report PASS having done nothing.

**2. It masks the exact thing `--audit` exists to catch — and this is the
load-bearing reason.** `.github/workflows/gates.yml:58-62` states the step's
job:

> ```
> # Catches a gate whose command was emptied, whose cwd was moved away, or
> # whose evidence line was dropped - none of which the gate run itself can
> # report, because a gate that no longer does anything still exits 0.
> - name: Audit the gate manifest
>   run: bash scripts/gates.sh --audit
> ```

*"whose evidence line was dropped"* is signalled by **this sentence and nothing
else**: the count is the signal. And the count is already non-zero for a benign
reason. Reproduced — same fixture, `evidence | unit | ...` deleted so that a
**required** gate has genuinely lost its line:

```
2 required gate(s) have no evidence line. Add one per gate:
  evidence | <id> | <regex proving the tool did work>
Use `evidence | <id> | -` only where no such output exists, and say why in the story.

Manifest audit passed.
```
`[MEASURED — 2026-09-21, Lead PO, fixture run]`

1 → 2, and **the sentence reads identically**. Note also `Manifest audit
passed.` and exit 0: this summary never fails the run, so the number is the
entire signal, and it is a number a reader has been trained to expect to be 1.

## Acceptance criteria

*Oracle partition: all four are **mechanical**. Every one is an exact string in
`gates.sh`'s output against a fixture manifest whose contents the test writes.
Pin them exactly; invent nothing. There is no metric here and therefore no
negative-control-on-a-statistic — but AC-3 and AC-4 are negative controls on the
change itself, and they are the two that stop this fix from silencing a real
signal.*

- **AC-1** — Given a manifest in which every **required** gate has an `evidence`
  line and at least one **optional** gate has a command but none, when
  `bash scripts/gates.sh --audit` runs, then the output does **not** contain the
  string `required gate(s) have no evidence line`, and the audit still exits 0.

- **AC-2** — Given that same manifest, when `--audit` runs, then the per-gate
  line for the optional gate is still printed, unchanged. The authoritative form
  is the existing `printf` at `gates.sh:437` —
  `printf 'WARN %-12s no evidence line; a vacuous pass would go unnoticed\n' "$id"`
  — which for a gate named `mutation` renders as
  `WARN mutation     no evidence line; a vacuous pass would go unnoticed`
  (`%-12s`, so `mutation` is followed by five spaces; do not hand-count padding,
  assert the substring `WARN mutation` and the substring
  `no evidence line; a vacuous pass would go unnoticed` on one line, as the
  existing assertions in `gates.test.sh` do).
  *This AC is why the fix is not "delete the WARN": the one place the condition
  is reported must survive.*

- **AC-3** — Given a manifest in which a **required** gate has a command and no
  `evidence` line, when `--audit` runs, then the output contains
  `1 required gate(s) have no evidence line.` — and given a manifest in which
  **one required and one optional** gate both lack one, it contains
  `1 required gate(s) have no evidence line.`, not `2`.
  *This is the masking defect stated as a test: the count must move only for
  required gates. It is the negative control on AC-1 — a fix that simply removed
  the summary block would pass AC-1 and fail this.*

- **AC-4** — Given a manifest with `BOOTSTRAPPED=no` and a **required** gate
  that has a command and no `evidence` line, when `--audit` runs, then the
  output still contains `1 required gate(s) have no evidence line.`
  *Unchanged behaviour, pinned so the fix cannot drift into it. The run path's
  guard is `BOOTSTRAPPED=yes && req=required`; only the `req` half is being
  copied. Measured 2026-09-21: today this case counts. See `## Contract`,
  "Why `req` and not `BOOTSTRAPPED`".*

## Contract

### The change

**File:** `scripts/gates.sh`. **Lines:** the `if [ "$exp" = "<none>" ]` block at
`436-439` in the `--audit` branch.

**Direction chosen: guard the `--audit` counter by `req`, matching the run
path.** The increment becomes conditional on `[ "$req" = "required" ]`; the
`printf` of the per-gate `WARN` and the `continue` do not move. In shape:

```bash
if [ "$exp" = "<none>" ]; then
  printf 'WARN %-12s no evidence line; a vacuous pass would go unnoticed\n' "$id"
  [ "$req" = "required" ] && noevidence=$((noevidence+1))
  continue
fi
```

GREEN owns the exact form (a `&&` one-liner under `set -uo pipefail` where the
last command's status can leak is a real hazard here — `gates.sh` does not use
`set -e`, but the block ends in `continue`, so the status is discarded; an
`if`/`fi` is equally acceptable and may read better).

**The summary text at `scripts/gates.sh:640-644` does not change.** Under this
direction the existing wording becomes *true*, so there is no new string to pin
and nothing downstream has to learn a new sentence:

```
%d required gate(s) have no evidence line. Add one per gate:
  evidence | <id> | <regex proving the tool did work>
Use `evidence | <id> | -` only where no such output exists, and say why in the story.
```

### Why this direction and not the other

The dispatch named two defensible fixes. They are not equivalent.

**Rejected: keep counting every gate and reword the summary to stop claiming
"required".** It fixes the sentence and leaves the defect, which is that
`noevidence` means *"required gates missing evidence"* in one path of this
script and *"any gate missing evidence"* in the other. Rewording commits to that
divergence permanently: the two summary blocks (`:640` and `:758`) would then
have to say different things about the same variable, and the next reader
comparing the paths finds the asymmetry still there with a comment over it.
It also does not fix the masking in AC-3 — a reworded sentence still reads
identically at 1 and at 2. To fix the masking under this direction you would
have to print **two** counts, which is more output on every audit for a benign
condition: the cry-wolf failure mode one notch quieter.

**Chosen: guard by `req`.** One decision, taken once, in the path that did not
take it; the two paths then agree; the existing wording becomes true; the
masking goes away because the count moves only for the thing the count claims to
be about. Diff is one line of `gates.sh`.

**What is lost, named honestly.** An optional gate with no evidence line stops
being *aggregated*. It is not silenced — AC-2 keeps the per-gate `WARN`, which
is one line among roughly ten in `--audit`'s output and names the gate. The
summary's job is to make a count actionable, and a count that mixes two
severities is less actionable than either.

### Why `req` and not `BOOTSTRAPPED`

The run path guards by both. Only `req` is copied, deliberately.

`req` is a property of the **manifest** — this gate is or is not binding — and
the audit's job is to judge the manifest. `BOOTSTRAPPED` is a property of the
project's **stage**, and `--audit` is precisely the tool a bootstrap story uses
to check a manifest it is still filling in; telling it nothing about missing
evidence lines would be a regression. The run path's `BOOTSTRAPPED` guard exists
because a non-bootstrapped run's summary is already full of `UNCONFIGURED`
noise; the audit has no such problem, and the `-z "$cmd"` branch above
(`gates.sh:425-432`) already handles the unconfigured case with its own
`BOOTSTRAPPED` test before this block is reached. AC-4 pins the behaviour so the
fix cannot drift into it.
