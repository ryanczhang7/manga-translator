tax on every command any agent in this repository runs, all day.

records the same lesson from the other direction:

> One awk process for any number of paths, because spawning one per rule cost

### The hook fails OPEN, which sets the risk of this story

### C-2 The substitutions, and which one is a trap

Sixteen of the 21 `tr` spawns have an exact parameter-expansion equivalent that
works on **bash 3.2**:

| today | replacement | n | bash 3.2? |
|---|---|---:|---|
| `tr -d '[:space:]'` | `${s//[[:space:]]/}` | 7 | yes (pattern substitution, bash 2+) |
| `tr '\134' '/'` | `${s//\\//}` | 5 | yes |
| `tr -d '"'"'"` — **both** quote characters, see below | ~~`${s//\"/}`~~ → `${s//[\"\']/}`, or fold into the adjacent `sed`/`awk` | 4 | yes |
| `tr 'A-Z' 'a-z'` (`lower()`) | ~~`${s,,}`~~ | 3 | **NO — bash 4. See AC-3.** |
| 2 others | to be identified from the trace | 2 | RED to determine |

Call sites for the first three, from `grep -n "tr " .claude/hooks/lib.sh`:
`1050, 1053, 1077` (`tr -d '[:space:]'`); `549, 550, 616, 627, 668, 679`
(`tr '\134' '/'`); `234, 267, 691` (`tr -d '"'`). Line `205` is a `tr` with a
**two-argument character map** used for placeholder restoration and line `1097`
is `tr -d '\r'` piped into `awk` — neither is one of the four forms above;
judge each on its own and say so in the handoff.

**Amended by the orchestrator at PLANNED→RED, 2026-09-24 — the quote row was
wrong.** The three sites (`234`, `267`, `691`) are spelled `tr -d '"'"'"` in
source: shell concatenation of `'"'` and `"'"`, so the delete set is `"'` —
**double AND single quote**. Measured:
`printf 'a"b'"'"'c\n' | tr -d '"'"'"` prints `abc`. The replacement this row
originally carried, `${s//\"/}`, deletes only `"` and would leave every `'` in
`shell_assignments`, `mutate_targets` and `command_cwd` output — a verdict
change on `A='src/x'`-style assignments and `cd 'dir'`. The correct in-process
form is `${s//[\"\']/}` (measured: `a"b'c` → `abc`, bash 5.3). **AC-1's words
"`tr -d '"'`" name this form** — the AC text is not edited (that would need an
`## Amendments` entry and nothing about the criterion changes); this block is
the reading of it. RED's adversarial input set for this equivalence must
therefore carry a **single** quote, not only a double one.
Also note all three are **mid-pipeline on multi-line streams**, not scalar
values: the natural rewrite is to fold the deletion into the neighbouring
`sed -E` / `awk` stage (one process fewer, no new stage), or to capture and
expand. Either is GREEN's choice; the adversarial inputs are RED's.

**`${s//\\//}` needs care and a test.** Backslash is both the thing being
matched and bash's escape character inside a substitution pattern, and getting
it wrong silently produces the input unchanged — which on Windows means
`to_rel` stops normalising `C:\Users\…` and every absolute-path verdict moves.
AC-4's and AC-5's inputs must include a backslash-spelled absolute path.

**A measurement trap the orchestrator hit at PLANNED→RED, 2026-09-24.**
`"${s//\\//}"` on `C:\Users\x` **is correct** — it prints `C:/Users/x` when run
from a file written with the `Write` tool (bash 5.3.15, cygwin). Typed into the
agent `Bash` tool as a one-liner *or even inside a quoted heredoc*, the same
text printed the input **unchanged**, and `od -c` of the heredoc-written file
showed a single `\` where two were typed: the tool channel collapses `\\` before
bash sees it. So a probe of this substitution typed at the Bash tool reports a
false "broken", and — worse — a fix "confirmed" there may be a different
expression from the one in the file. **Probe backslash expressions from files
written with `Write`/`Edit`, and check the bytes with `od -c`.** The same caution
applies to any `mutate.sh` `sed` expression containing `\\`.

### C-3 `is_ignored`, batched — and the two spellings are not optional

Today:

```bash
is_ignored() {
  [ -n "${1:-}" ] || return 1
  git -C "$HARNESS_ROOT" check-ignore -q -- "$1"  2>/dev/null && return 0
  git -C "$HARNESS_ROOT" check-ignore -q -- "$1/" 2>/dev/null && return 0
  return 1
}
```

Two git processes per classified path. The batched idiom already in this file
at `lib.sh:880` is `git check-ignore --stdin --verbose --non-matching`, which
takes one path per line and reports a verdict per line, so **both spellings of
every candidate go through one process**.

Constraints:

- **`--non-matching` is what makes the output line up with the input.** Without
  it, non-ignored paths produce no line and the caller cannot tell which answer
  belongs to which path. This is the standard way to get this wrong.
- **A path containing a newline** cannot go through `--stdin` safely. Today's
  per-path form has no such limit. Decide explicitly: either use `-z`
  (NUL-delimited, which `check-ignore` supports) or state in the handoff that
  newline-bearing paths fall back to the per-path call, and add a case for it.
  Do not leave it undecided — a guard that mis-answers on a crafted path is a
  lock bypass.
- **`classify` calls `is_ignored` for ONE path.** The batching win is therefore
  not automatic: it is one process instead of two for a single path (AC-4's
  "at most one"), and one instead of 2N wherever a caller has many. Say in the
  handoff which callers have many, so the claim matches the code.
- **Ordering is frozen** ([[MT-034]] C-3): rules on the bare form → rules on the
  slashed form → `git check-ignore` → `source`. Batching invites hoisting the
  git call to the front. Do not.

**Amended by the Test Developer in RED, 2026-09-24 — the newline decision is
made, and `--stdin` is not the only single-process form.** Measured against
git 2.55.0.windows.5 on the adversarial fixture in `lib.test.sh` (`MT-041 AC-4`
block):

- **Decision: a newline-bearing path goes through the same single process as
  any other path. There is no fallback to two calls.** `lib.test.sh` enforces
  it: the "at most one `git check-ignore`" loop includes `x<LF>.vitest`, so a
  two-call fallback fails there even though its verdicts are right.
- **Preferred mechanism: both spellings as argv, `git -C "$HARNESS_ROOT"
  check-ignore -- "$1" "$1/" >/dev/null 2>&1`, decided by exit status** (0 if
  either spelling is ignored, 1 if neither). One process, no stdin, nothing to
  align, and non-verbose mode never reports a negated match. Measured: identical
  answers to today's two-call form on `keep.tmp` (1), `slashonly` (0),
  `bareonly` (0), `x.tmp` (0), `spikes` (1), `x<LF>.vitest` (1), `a.tmp<LF>b`
  (1), `a<LF>b.tmp` (0), and a tracked `t.tmp` (0 — see Handoff finding F-3).
- **`--stdin -z --verbose --non-matching` is acceptable** and also measured
  working: per path, four NUL-terminated fields (source, line, pattern, path),
  the first three empty for a non-match. **If `--stdin` is used, two traps are
  real, both measured:** (1) `--verbose` prints a line for a path that matches a
  **negated** pattern (`.gitignore:9:!keep.tmp<TAB>keep.tmp`), and that path is
  *not* ignored — a pattern beginning with `!` must be read as "not ignored",
  not merely "not `::`"; (2) without `-z`, a non-ASCII path is C-quoted in the
  output (`"caf\303\251/"`), so output lines can only be matched to input by
  position, never by path text. The `--non-matching` requirement above applies
  only to a `--stdin` implementation; the argv form parses no output.

### C-4 If `lower()` is eliminated — the optional stretch, with its caveat

`to_rel` lowercases both the path and the root only to do a case-insensitive
prefix comparison. `shopt -s nocasematch` (bash 3.0) makes `[[ "$p" ==
"$root"/* ]]` case-insensitive directly, removing both `lower()` calls and both
`tr` spawns without any bash 4 feature.

**The caveat, and it is why this is optional rather than pinned:**
`nocasematch` is **global shell state** and it also affects `case` statements.
`lib.sh` is *sourced* by twelve files, several of which use `case` for path and
command matching where case-sensitivity is load-bearing. So it must be saved and
restored around the one comparison (`shopt -p nocasematch` captures the restore
command), and `set -e`/early returns must not skip the restore.

If that looks fragile, **leave `lower()` alone.** AC-1's budget of 27 does not
assume this, and three `tr` spawns are not worth a global-state bug in the lock.

#### G-1 — why the 27th spawn is `phase_message`'s `sed`, not line 140 (read this)

D-2 opened line 140 and suggested folding the quote deletion into the adjacent
stage. The adjacent stages are `grep -vE` and `sort -u`, and neither can delete
characters, so a fold means **replacing `grep -vE` with `awk` or `sed`**. I
measured that, and it is **not verdict-identical**. Under a UTF-8 locale
(`LC_ALL=C.UTF-8`, the usual Linux CI setting), GNU grep turns a candidate
containing an invalid UTF-8 byte into the literal line `Binary file (standard
input) matches`. Today's guard classifies *that string*, not the path. An
`awk`/`sed` filter passes the real path through, so a path like
`docs/caf<0xE9>.md` in RED would go from denied (on a bogus `source` path) to
allowed. The difference cannot be seen with this machine's default locale:
all three forms printed byte-identical output there. So I left `grep` alone,
swapped `tr` for a `sed` of equal cost (`tr:quotes` = 0, no count change), and
took the one extra spawn from `phase_message`. That function formats denial
text and decides no verdict, and the C-2 TAB-padded `phase_message` assertion
pins it. **Finding for its own story:** the grep "binary file" substitution
is a pre-existing defect in the lock. The hook's JSON input is very unlikely to
deliver raw invalid UTF-8, but nobody has shown that it cannot. Also, the
comment at `phase-guard.sh:136` still says "`tr -d` and `sort -u` see them as
inert". It is now `sed`, and D-2 does not open line 136 to fix it.

### R-1 — the spawn instrument mis-parses xtrace's `'\''` escape (REVIEW → RED, 2026-09-24)

**What is wrong.** `.claude/tests/_spawns.sh`'s `_spawn_commands` consumes a
shell word with `value()`, which understands `'…'` and `$'…'` but not a
backslash escape **outside** quotes. xtrace prints an embedded single quote as

```

```

(from the `read` loop over a harness config comment) is split after `…project'\''s`

then counts it whenever `type -P .gitignore` resolves.

**How it was found.** PR #34, run `36068740516`, `Harness self-test`:
`FAIL AC-1: at most 27 external processes … spawned 29`, with the tally printing
