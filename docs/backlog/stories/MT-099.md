## Context

Filed 2026-10-27 at the user's request, from the feature-developer's GREEN
finding on MT-097 (`docs/backlog/stories/MT-097.md`, `## Notes`, "Caveat: the
save-*failed* path is not fully covered"). **LOW priority.** It needs a save
that fails, which in practice means a full disk or a locked project file.

**What MT-097 fixed.** `show_page` now flushes the translation column
**before** `_page_ordinal` changes (`src/mangatl/ui/workspace.py`, the
`self.translation_column.flush()` added in `show_page`). So a save that
**succeeds** on leaving page A updates page A's strip row, not page B's.

**What it leaves open, by reading the code (not yet measured).**

1. When a row's save raises, `LineEditor.flush()` (`src/mangatl/ui/line_editor.py:127-141`)
   emits `saveFailed` and returns **without** clearing `_pending`.
2. MT-097's new flush therefore leaves the save pending. `show_page` then
   sets `_page_ordinal = B`, and the second flush, in `_load_regions` or
   `TranslationColumn.set_rows`, retries the same save.
3. If that retry also fails, `saveFailed` -> `TranslationRow._on_save_failed`
   -> `_render` (`workspace.py:692-694`) -> `linesChanged` ->
   `_refresh_page_progress` runs with `_page_ordinal` already B, while the
   column still holds page A's rows. Page A's statuses are written onto page
   B's strip row, which is MT-097's defect again, for a save that keeps
   failing.

The row's save is `_saver(project, page_ordinal, reading_index)`
(`workspace.py:851-858`), which calls the module-level
`mangatl.store.lines.commit_line` imported into `workspace.py` (`:113`). A test
can make every save fail by replacing `mangatl.ui.workspace.commit_line` with
one that raises.

**Evidence to verify, not assume:** the whole mechanism above. RED reproduces
it with its own test on this story's fixture before relying on it, and if the
shipped code does **not** fail, RED stops and reports rather than writing a
passing test.

Required gate that fails if this breaks: `unit` and `coverage`, which collect
`tests/ui/test_page_strip_status.py`.

## Acceptance criteria

- **AC-1** - Given the `reviewing` project with page 1 shown, and every line
  save failing, when the user accepts one of page 1's lines and selects page 2
  before that line's save timer fires, then page 2's strip row still reads
  exactly what it read before (`progress(1) == before[1]`), and rows 3 and 4
  are unchanged.
  - In the strip, `progress(0)` is page 1 and `progress(1)` is page 2.
  - Expected to fail on the shipped code; RED confirms that.
- **AC-2** - In the same sequence, page 1's strip row reads the same value it
  reads when only the **first** flush fails, i.e. the second, retried failure
  changes no row but its own page's. RED reads that value out of the shipped
  code's first-flush behaviour and pins it exactly; GREEN must not change it.
