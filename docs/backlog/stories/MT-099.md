## Context

Filed 2026-10-27 at the user's request, from the feature-developer's GREEN
finding on MT-097 (`docs/backlog/stories/MT-097.md`, `## Notes`, "Caveat: the
save-*failed* path is not fully covered"). **LOW priority.** It needs a save
that fails, which in practice means a full disk or a locked project file.

**What MT-097 fixed.** `show_page` now flushes the translation column
**before** `_page_ordinal` changes (`src/mangatl/ui/workspace.py`, the
`self.translation_column.flush()` added in `show_page`). So a save that
**succeeds** on leaving page A updates page A's strip row, not page B's.

**What it leaves open, by reading the code (not yet measured).**

1. When a row's save raises, `LineEditor.flush()` (`src/mangatl/ui/line_editor.py:127-141`)
   emits `saveFailed` and returns **without** clearing `_pending`.
2. MT-097's new flush therefore leaves the save pending. `show_page` then
   sets `_page_ordinal = B`, and the second flush, in `_load_regions` or
   `TranslationColumn.set_rows`, retries the same save.
3. If that retry also fails, `saveFailed` -> `TranslationRow._on_save_failed`
   -> `_render` (`workspace.py:692-694`) -> `linesChanged` ->
   `_refresh_page_progress` runs with `_page_ordinal` already B, while the
   column still holds page A's rows. Page A's statuses are written onto page
   B's strip row, which is MT-097's defect again, for a save that keeps
   failing.

The row's save is `_saver(project, page_ordinal, reading_index)`
(`workspace.py:851-858`), which calls the module-level
`mangatl.store.lines.commit_line` imported into `workspace.py` (`:113`). A test
can make every save fail by replacing `mangatl.ui.workspace.commit_line` with
one that raises.

**Evidence to verify, not assume:** the whole mechanism above. RED reproduces
it with its own test on this story's fixture before relying on it, and if the
shipped code does **not** fail, RED stops and reports rather than writing a
passing test.

Required gate that fails if this breaks: `unit` and `coverage`, which collect
`tests/ui/test_page_strip_status.py`.

## Acceptance criteria

- **AC-1** - Given the `reviewing` project with page 1 shown, and every line
  save failing, when the user accepts one of page 1's lines and selects page 2
  before that line's save timer fires, then page 2's strip row still reads
  exactly what it read before (`progress(1) == before[1]`), and rows 3 and 4
  are unchanged.
  - In the strip, `progress(0)` is page 1 and `progress(1)` is page 2.
  - Expected to fail on the shipped code; RED confirms that.
- **AC-2** - In the same sequence, page 1's strip row reads the same value it
  reads when only the **first** flush fails, i.e. the second, retried failure
  changes no row but its own page's. RED reads that value out of the shipped
  code's first-flush behaviour and pins it exactly; GREEN must not change it.
- **AC-3** - Given the `reviewing` project with page 1 shown, where the
  accept's **first** save attempt fails and every later attempt succeeds, when
  the user accepts one of page 1's lines and selects page 2 before that line's
  save timer fires, then page 2's strip row still reads exactly what it read
  before (`progress(1) == before[1]`), rows 3 and 4 are unchanged, and the
  project file holds the accept for page 1's line. Expected to fail on the
  shipped code; RED confirms that.

## Test plan

All three criteria are **mechanical** (Contract, oracle partition). Every
value is pinned exactly as a whole `PageProgress` tuple or a whole stored-line
tuple, with no tolerance. All three tests are integration-level in `tests/ui/test_page_strip_status.py`, directly after
MT-097's two tests. They use the `reviewing` fixture, `_reviewing(qtbot,
project, 0)`, `_click(window, 0, "accept_button")` and `_settle()`. The defect
lives in the `Workspace` wiring: `show_page` flush, then `_load_regions` /
`set_rows` flush, then `saveFailed` (AC-1, AC-2) or `saveSucceeded` (AC-3),
then `_render`, then `linesChanged`, then `_refresh_page_progress`. A unit test
of any one of those pieces cannot falsify it.

Two helpers carry the sequence:

- `_saves_fail(monkeypatch, *, first_only=False)` patches
  `mangatl.ui.workspace.commit_line` with `monkeypatch.setattr`. The
  replacement records `(page_ordinal, reading_index, text, status)` and raises
  `OSError("disk is full")`. With `first_only=True` it raises on the first
  call only, and every later call delegates to the real
  `mangatl.store.lines.commit_line`, so the store receives the accept.
- `_accept_then_change_page(qtbot, project, calls)` records
  `before = [strip.progress(i) for i in range(4)]`, clicks Accept on row 0,
  calls `strip.setCurrentRow(1)` and `_settle()`.
  `_accept_then_change_page_with_every_save_failing` is the AC-1 / AC-2 form,
  with every save failing.

The helper asserts three preconditions so no scenario can pass vacuously:

- the save was attempted at least twice, which means it was retried after the
  page change;
- every attempt was `(0, 0, None, "accepted")`, which is page 1's line;
- `currentRow() == 1`.

| Test | AC | What it asserts |
|---|---|---|
| `test_a_save_failing_again_after_the_page_change_leaves_the_new_pages_row_its_own` | AC-1 | `before[1] == PageProgress("translated", 0, 1, 0)`, the fixture read out. `progress(1) == before[1]`. `[progress(2), progress(3)] == before[2:]`. **Fails on the shipped code at `progress(1)`, which reads page 1's `PageProgress("partly_reviewed", 1, 3, 0)`.** |
| `test_a_save_failing_again_after_the_page_change_leaves_the_left_pages_row_as_one_failure_did` | AC-2 | `before[0] == PageProgress("translated", 0, 3, 0)`. `progress(0) == PAGE_1_AFTER_A_FAILED_SAVE == PageProgress("partly_reviewed", 1, 3, 0)`. **Passes on arrival.** It is earned by the mutation in the handoff, which makes AC-1 pass and this test fail. |
| `test_a_save_that_succeeds_on_retry_after_the_page_change_leaves_the_new_pages_row_its_own` | AC-3 | The first save attempt fails and every later one succeeds through the real store. `before[1] == PageProgress("translated", 0, 1, 0)`. Then the stored row: `_stored_row(reviewing, 0, 0) == ("accepted", None, "en 0", "ja 0", True)`, read with `read_review_lines` as MT-097's AC-2 test does (status, final_en, proposed_en, source_ja, edited_at set). Then `progress(1) == before[1]` and `[progress(2), progress(3)] == before[2:]`. **Fails on the shipped code at `progress(1)`, which reads page 1's `PageProgress("partly_reviewed", 1, 3, 0)`.** The store assertion comes **before** `progress(1)`, so it runs while the strip assertion fails. It **holds** on the shipped code, and is earned by a mutation in the handoff. |

**How AC-2's value was obtained.** It was measured on the shipped code
(`adc1ebe`), not derived. Two throwaway probe tests were appended to the file,
run with `-s`, and then removed. The file was restored from a copy, and
`git diff` showed only the AC-1 and AC-2 tests. AC-3's test was added later,
under Amendment A-1.

- **Probe B: only the first flush fails, with no page change.** Every save
  raises. After Accept, `translation_column.flush()` is called once on page 1.
  The save is attempted once, as `(0, 0, None, 'accepted')`. Row 0's caption
  reads `Not saved: disk is full`. The strip reads
  `[partly_reviewed 1/3, translated 0/1, skipped 0/2, pending 0/2]`.
- **Probe A: the page change happens and only its first flush fails.** The
  save raises on its first call and succeeds after that. `progress(0)` right
  after the click is `partly_reviewed 1/3`. After the page change,
  `progress(0)` is `partly_reviewed 1/3`.
- **Probe C: AC-1's sequence, with every save failing.** The save is attempted
  3 times, all `(0, 0, None, 'accepted')`: in `show_page`, in `_load_regions`
  and in `set_rows`. The strip after is
  `[partly_reviewed 1/3, partly_reviewed 1/3, skipped 0/2, pending 0/2]`.

Probes A and B agree, so page 1's row after one failure is
`PageProgress("partly_reviewed", 1, 3, 0)`. It is the in-memory statuses
`(accepted, proposed, proposed)` on a `PAGE_DONE` page. It is also the value
the click itself writes, so a failed save leaves the row where the commit put
it. GREEN must not change it.

Mechanisms the brief named, checked rather than assumed:

- **The patch on `mangatl.ui.workspace.commit_line` reaches `_saver`: holds.**
  Every call is recorded, and row 0's caption shows `Not saved: disk is full`.
  No `OSError` escapes into the test, because `LineEditor.flush` catches it and
  emits `saveFailed`.
- **The save is retried after `_page_ordinal` changes: holds.** There are 3
  attempts, as above.
- **The retried failure writes page 1's statuses onto page 2's row: holds.**
  That is the AC-1 failure.
- **The patch does not leak: holds.** `monkeypatch` is function-scoped. The
  check ran the AC-2 test and then MT-097's
  `test_a_save_pending_when_the_page_changes_still_reaches_the_project_file`
  in that order, in one session. MT-097's test asserts that the real store row
  becomes `accepted`, and it passed (`2 passed in 1.02s`).

**Found while probing, now AC-3 (Amendment A-1).** Probe A shows the same
corruption when the first flush fails and the retry **succeeds**. Page 2's
row read `partly_reviewed 1/3` there too, because `saveSucceeded` also goes
through `_render`, then `linesChanged`, then `_refresh_page_progress` with
`_page_ordinal` already 1. AC-3's test is probe A written as a real test. It
reproduces the probe's value, with 2 attempts made (the first fails in
`show_page`; the retry in `_load_regions` succeeds, which clears `_pending`, so
`set_rows` has nothing left to flush).

Out of scope, not pinned: telling the user that the failed line was not saved
after they leave its page; automatic retry.
