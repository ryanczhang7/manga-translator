## The five symptoms, and how much is actually known about each

### Symptom A — prose that *mentions* the in-place editor flag is scanned for paths. Reproducible on demand, and it **hard-blocks**.

**This was characterised by a single-variable A/B while filing this story, after
the guard blocked the commit that files it — twice.** The two commands below are
byte-identical apart from one phrase in the message body, and **both are
`--dry-run`, so neither writes anything at all**:

```
$ git commit --dry-run --allow-empty -F - <<'EOF'
a real in-place edit hard-BLOCKED with its own expression reported as the
EOF
On branch backlog/mt-031-phase-guard-path-resolution      <- ALLOWED

$ git commit --dry-run --allow-empty -F - <<'EOF'
a real sed -i hard-BLOCKED with its own expression reported as the
EOF
BLOCKED by the harness phase lock.
  story:    MT-003
  phase:    RED
  path:     sed -i hard-BLOCKED with its own expression reported as the
  category: source
```
`[MEASURED — 2026-09-13, MT-003 in RED]`

That is the whole bug in six lines, and it is a **ready-made case for
`.claude/tests/phase-guard.test.sh`**: same command, one phrase, opposite
verdicts, nothing written either way. It is also precisely the situation
`CLAUDE.md` names — *"if it still blocks a command that writes nothing, that is
a bug in the guard"*.

**Note the reported `path:`.** It is an English clause, spaces and all,
classified `source`. Whatever the extractor is handing the classifier, it is not
a filename, and the classifier's default for an unrecognised string is the most
restrictive category — which is a sensible default meeting a bad input.

The guard's own decline log carries the same defect firing through the softer
path, from the day before, while MT-030's PO-6 was being written:

```
$ tail -3 .claude/state/phase-guard-declined.log

declined MT-030 in REVIEW: implausible target sed-i`expressionasthepathargument.Falsepositive,so
declined MT-003 in RED: implausible target /c/.../scratchpad/sib-$
```

The middle line is the guard reading the sentence *"the guard took the `sed -i`
expression as the path argument. False positive, so…"* — a sentence **about**
this bug — and trying to resolve it as a filename. `[MEASURED]`

**So the same defect has two exits**, and a fix must close both: `decline` when
the garbage candidate looks unresolvable, `BLOCK` when it happens to classify.
Only the second stops work.

While writing MT-030's `## Notes` — a **documentation write**, in `docs/`, in a
phase where `docs` is permitted — the guard extracted a candidate path out of the
English sentence being written and declined it:

```
$ tail -3 .claude/state/phase-guard-declined.log
declined MT-001 in SCAFFOLD: implausible target src/mangatl/$p/__init__.py
declined MT-030 in REVIEW: implausible target sed-i`expressionasthepathargument.Falsepositive,so
declined MT-003 in RED: implausible target /c/.../scratchpad/sib-$
```

The middle line is the guard reading the prose *"the guard took the `sed -i`
expression as the path argument. False positive, so…"* — a sentence **about** the
bug — and trying to resolve it as a filename. `[MEASURED]`

The mechanism is `.claude/hooks/phase-guard.sh` line 92:

```bash
printf '%s\n' "$MASKED" | grep -oE '\bsed\b[^|&;()]*-i[^|&;()]*' | awk '{print $NF}'
```

`\bsed\b … -i …` matches inside ordinary text, and `$NF` then takes whatever
word happens to end the run. Nothing distinguishes *a command invoking sed* from
*a sentence containing the word sed*.

Note that the guard **declined rather than blocked** here, which is the designed
behaviour for an unresolvable candidate and is correct. The defect is that the
candidate existed at all.

### Symptom C — a trailing redirect hides the real operand, and the write is permitted. **This is a bypass of the phase lock.**

**Single-variable A/B, in `RED`, where `source` is frozen. The two commands
differ by one space.**

```
$ sed -i 's/x/y/' src/mangatl/nonexistent_probe_mt031.py
BLOCKED by the harness phase lock.
  path:     src/mangatl/nonexistent_probe_mt031.py      <- correct: the real operand
  category: source

$ sed -i 's/x/y/' src/mangatl/nonexistent_probe_mt031.py > /dev/null
sed: can't read src/mangatl/nonexistent_probe_mt031.py: No such file or directory
  exit=2                                                <- ALLOWED. The guard saw nothing.
```
`[MEASURED — 2026-09-13, MT-003 in RED]`

**The only reason nothing was written is that the probe deliberately named a
file that does not exist.** The guard's decision does not depend on existence —
the control blocked the very same nonexistent path — so a real source file in
its place would have been edited during `RED`.

**Mechanism**, and it is the same line 92 as Symptom A:

1. `grep -oE '\bsed\b[^|&;()]*-i[^|&;()]*'` matches the whole command tail,
   redirect included, because `>` is not in its terminating character class.
2. `awk '{print $NF}'` then returns **`/dev/null`** — the last field — instead of
   the file operand.
3. The candidate filter drops it: `grep -vE '…|^/dev/'`.
4. The redirect extractor independently produces `/dev/null` too. Also dropped.
5. **Zero candidates survive. Nothing is checked. The command runs.**

The unspaced form `>/dev/null` blocks — but *by accident*: `$NF` is then the
single token `>/dev/null`, whose leading `>` defeats the `^/dev/` filter, so it
survives as a candidate, classifies `source`, and denies. **A guard that is
correct only when the author omits a space is not correct.** That near-miss is
itself worth a test case, because a fix could easily preserve the accident while
missing the hole.

**This generalises past `/dev/null`.** Any trailing redirect makes `$NF` the
redirect target rather than the operand. Whether the result denies, declines or
allows then depends on what the *redirect target* classifies as — which has
nothing to do with the file being written. The fix must parse the operand, not
take the last word.

**Scope note for whoever picks this up:** check `cp`, `mv`, `rm`, `touch` and
`tee` on line 93–95 for the same shape. Three of those also use
`awk '{print $NF}'` or an equivalent, and the reasoning above is not specific to
`sed`. **Do not assume they are fine because only `sed` was observed** — only
`sed` was *tried*.
### Symptom D — a capture group in the expression bypasses the guard with no redirect anywhere in the command. **Found in PLANNED, 2026-09-13, by the orchestrator. Not in the story as filed.**

Symptom C needs a trailing redirect. This one needs nothing but a `\(` — the
single most ordinary thing a `sed` expression contains. Three commands, in `RED`,
against the fixture suite's tracked `src/main.ts`:

```
sed -i 's/a/b/'          src/main.ts   -> BLOCKED  path: src/main.ts     (correct)
sed -i 's/\(a\)/b/'      src/main.ts   -> BLOCKED  path: s               (right by accident)
sed -i '/x/!s/\(a\)/b/'  src/main.ts   -> ALLOWED                        (bypass)
```
`[MEASURED — 2026-09-13, fixture in RED]`

Isolating one metacharacter at a time, all against `src/main.ts` in `RED`:

| expression contains | verdict | reported path |
|---|---|---|
| `\|` | BLOCKED | `src/main.ts` |
| `;` | BLOCKED | `src/main.ts` |
| `&` | BLOCKED | `src/main.ts` |
| `<` and `>` | BLOCKED | `src/main.ts` |
| `!` | BLOCKED | `src/main.ts` |
| `(` `)` | BLOCKED | **`s`** |
| `!` **and** `(` `)` | **ALLOWED** | — |

`[MEASURED — all seven, 2026-09-13]`

`(` and `)` are in the extractor's terminating class (`[^|&;()]*`), added when a
subshell's closing paren was being glued onto a target. They are also what a
`sed` capture group is spelled with, so the class truncates the match *inside the
expression*, and `$NF` becomes a fragment of the script. **This is the plainest
bypass of the three and the one most likely to be hit by accident**, because
nothing unusual is being done — no redirect, no variable, just a capture group.

### Symptom E — the masker is not the defect. **The story as filed says it is.**

The story's `## Contract` stated, from a prediction checked against a `cat`
heredoc, that *"heredoc bodies are not masked at all"* and that *"the masking
simply is not reaching here"*. **Independently reproduced and contradicted.**
`mask_shell_quotes` called directly, output through `cat -v`:

```
$ printf '%s' 'cat <<"EOF"
sed -i is a real way to write a frozen file.
EOF' | mask_shell_quotes | cat -v
cat <<"EOF"
sed^F-i^Fis^Fa^Freal^Fway^Fto^Fwrite^Fa^Ffrozen^Ffile.
EOF

$ printf '%s' 'git commit -m "do not reach for sed -i here"' | mask_shell_quotes | cat -v
git commit -m "do^Fnot^Freach^Ffor^Fsed^F-i^Fhere"
```
`[MEASURED — 2026-09-13]`

Every space inside the heredoc body and inside the quoted argument **is** masked,
to `\006` (`^F`). The masker is doing exactly what `lib.sh` documents. What fails
is the next step:

```
$ M="$(printf '%s' 'git commit -m "do not reach for sed -i here"' | mask_shell_quotes)"
$ printf '%s\n' "$M" | grep -oE '\bsed\b[^|&;()]*-i[^|&;()]*' | awk '{print $NF}' | cat -v
sed^F-i^Fhere"
```
`[MEASURED]`

**So the bug is in the extractors, not in the masker, and the one-sentence
statement of it is:** `\bsed\b` matches *inside* a masked span, and the
terminating classes `[^|&;()]` and `[^|&;><()]` do not exclude the mask
characters `\001`–`\010`, so `awk '{print $NF}'` — which splits on real
whitespace — returns the whole masked run as one field. Unmasking it afterwards
is what turns a sentence into a reported `path:` with spaces in it.

**This correction matters because the filed framing points at the wrong file.** A
fix that goes looking for a hole in `lib.sh`'s masker will find none, and the
obvious "make masking reach the heredoc" change is a no-op. The extractors in
`.claude/hooks/phase-guard.sh` lines 91–95 are the whole of it.

## Acceptance criteria

Nine criteria. **Four of them describe behaviour the guard already has** — they
are regression guards against the fix, and they are marked as such, because a test
written against working code passes on its first run and forever and has to be
earned some other way (see `## Deferred verifications`). Every verdict below was
measured on 2026-09-13 against the `_lib.sh` fixture in `RED`.

- **AC-1 — prose that mentions the in-place flag is not a path.** *(FAILS today.)*
  Given the A/B pair in Symptom A — two `git commit --dry-run --allow-empty -F -`
  invocations differing only in whether the heredoc message body contains the
  phrase `sed -i` — when the guard runs in `RED`, then **both are permitted**,
  because neither writes anything. Reproduced independently: variant A allowed,
  variant B blocked on
  `path: sed -i hard-BLOCKED with its own expression reported as the`.
  The test must use **arbitrary prose in a quoted argument**, not this one
  sentence: the contract being restored is `CLAUDE.md`'s *"quoted arguments and
  heredoc bodies are data, not syntax"*, and a fix that special-cases an observed
  phrase satisfies the letter of this while leaving the contract false.

- **AC-1b — the same defect through a write the phase permits.** *(FAILS today.
  Reworded in PLANNED — see PO-1; the criterion as filed was unreachable.)*
  Given a `Bash` command that writes a path the current phase **permits** and
  whose quoted data — a heredoc body or a quoted argument — contains the phrase
  `sed -i` in ordinary prose, when the guard runs, then the write is
  **permitted**, **and no line is appended** to
  `.claude/state/phase-guard-declined.log`. Fixture: appending MT-030's PO-6
  sentence to `docs/notes.md` in `RED`, which today is **hard-BLOCKED** on
  `path: sed -i expression as the path argument. False positive, so` with
  `category: source`, and logs nothing. *Both halves are required: the softer exit
  of this defect is a decline, and a fix that converts the block into a decline
  has moved the noise rather than removed it.*

- **AC-2 — a real in-place edit of a frozen path is still blocked, on the
  operand.** *(PASSES today — regression guard, DV-1.)* Given a `Bash` command
  that genuinely invokes `sed -i FILE` on a path the current phase forbids, when
  the guard runs, then it is **still blocked**, and the reported `path:` is the
  **file operand**, not any part of the `sed` expression. *This is the criterion
  that stops AC-1 being satisfied by deleting the `sed -i` heuristic.*

- **AC-3 — a metacharacter in the expression changes nothing.** *(FAILS today for
  `(` `)`.)* Given a `sed -i` on a path the current phase forbids whose expression
  contains any of `|`, `&`, `;`, `<`, `>`, `!`, `(` or `)`, when the guard runs,
  then it is **blocked** and the reported `path:` is **exactly the file operand** —
  for every one of those characters and for them in combination. Today `(` `)`
  reports `s`, and `!` together with `(` `)` is **allowed outright** (Symptom D).
  *Strengthened in PLANNED from "the reported candidate set contains exactly the
  file operand" to "is blocked, naming the operand" — see PO-2. The filed wording
  was satisfied by a guard that blocks on `s`.*

- **AC-4 — a target outside the repository root is nobody's business.** *(PASSES
  today — regression guard, DV-2.)* Given a write whose target lies outside the
  repository root, when the guard runs in any phase, then the write is permitted.
  Four spellings measured allowed: an MSYS absolute path
  (`/tmp/claude/scratch/sib.py`), a quoted `C:/` path, a double-quoted `C:\` path,
  and a relative `../` climb out of the tree.

- **AC-5 — Symptom B is reproduced or recorded as not reproduced.** Either
  reproduced, with the trigger named and covered by a case in
  `.claude/tests/phase-guard.test.sh`, or the story records in `## Notes` that it
  could not be, listing the variants tried. Seven were tried when the story was
  filed; three more in PLANNED (PO-8), all allowed. **An unreproducible bug closed
  as "fixed" is worse than one closed as "not reproduced".**

- **AC-6 — the redirect bypass is closed.** *(FAILS today.)* Given a write command
  against a path the phase forbids **with a trailing redirect**, when the guard
  runs, then it is **blocked** and the reported `path:` is the **real operand**.
  All six forms below, measured today:

  | command | today | reported path |
  |---|---|---|
  | `sed -i 's/a/b/' src/main.ts` | BLOCKED | `src/main.ts` (control) |
  | `… src/main.ts > /dev/null` | **ALLOWED** | — |
  | `… src/main.ts >/dev/null` | BLOCKED | **`>/dev/null`** (accident) |
  | `… src/main.ts 2>/dev/null` | BLOCKED | **`2>/dev/null`** (accident) |
  | `… src/main.ts > docs/log.txt` | **ALLOWED** | — |
  | `… src/main.ts >> docs/log.txt` | **ALLOWED** | — |

  The unspaced and `2>` forms must block **for the right reason** — naming
  `src/main.ts`, not the redirect. *`> docs/log.txt` and `>> docs/log.txt` were
  added in PLANNED (PO-4): a redirect to a path the phase actually permits is a
  more ordinary thing to write than `/dev/null` and bypasses the guard the same
  way, so a fix that special-cases `/dev/null` fixes nothing.*

- **AC-7 — every write-capable extractor, not only `sed`.** *(FAILS today for
  three of six; PASSES for three — mixed, DV-3.)* Given `sed`, `cp`, `mv`, `rm`,
  `touch` and `tee` each invoked against a forbidden path with a trailing
  redirect, when the guard runs, then each is **blocked naming the real operand**.
  Measured:

  | command, with `> /dev/null` appended | today |
  |---|---|
  | `sed -i 's/a/b/' src/main.ts` | **ALLOWED** |
  | `cp docs/notes.md src/main.ts` | **ALLOWED** |
  | `mv docs/notes.md src/main.ts` | **ALLOWED** |
  | `rm src/main.ts` | blocked, `src/main.ts` |
  | `touch src/new.ts` | blocked, `src/new.ts` |
  | `echo x \| tee src/main.ts` | blocked, `src/main.ts` |

  *The story as filed asserted the shape generalises to all five others and that
  "three of those also use `awk '{print $NF}'` or an equivalent". Measured, it
  does not: `rm`/`touch` split on whitespace and drop `/dev/null` by filter, and
  `tee`'s class already excludes `>`. Corrected in PLANNED, PO-3. All six stay in
  scope — three as fixes, three as regression guards — because a rewrite of the
  extractor block is exactly what breaks the three that work.*

- **AC-8 — a zero-candidate command leaves a trace.** *(FAILS today.)* Given a
  `Bash` command in a restrictive phase that the extractors reduce to **no
  candidates at all**, when the guard runs, then that outcome is **logged** to
  `.claude/state/phase-guard-declined.log`, distinguishably from a command whose
  candidates were all permitted. Measured today: after the AC-6 bypass the log is
  empty, and after a permitted `echo x > docs/notes.md` the log is also empty —
  the two are indistinguishable from outside, and that is what made Symptom C
  invisible. *A command with no write construct in it at all must **not** log; see
  C-4 for where the line is drawn and why.*

Approved by: **the Lead PO (orchestrator), 2026-09-13, in PLANNED.** Each entry

**A-1 — AC-1b, rewritten.** *(PO-1)*

- **Was:** *"Given a `Write` or `Edit` whose **content** contains `sed -i` in
  ordinary prose … then the write is permitted and no line is appended to the
  decline log."*
- **Now:** the same requirement over a **`Bash`** command that writes a
  phase-permitted path and carries the phrase in its quoted data.
- **Why:** the criterion as written was unreachable, so no test could have been
  watched to fail against it. The guard's `Write|Edit|MultiEdit|NotebookEdit`
  branch calls `check_path` on `file_path` and `notebook_path` and **never reads
  `content`**. Measured: a `Write` of `docs/notes.md` with content
  `"Never reach for sed -i here."` is allowed and silent, as is a payload carrying
  only a `content` key. The exit that *does* fire is a Bash heredoc, which blocks
  on `path: sed -i expression as the path argument. False positive, so`.
  Both halves of the criterion survive; only the tool changed.

**A-2 — AC-3, strengthened.** *(PO-2)*

- **Was:** *"the reported candidate set contains **exactly** the file operand."*
- **Now:** *"it is **blocked** and the reported `path:` is **exactly the file
  operand**"*, over `|`, `&`, `;`, `<`, `>`, `!`, `(`, `)` and combinations.
- **Why:** the old wording is satisfied by a guard that blocks on `s`, which is
  what `sed -i 's/\(a\)/b/' src/main.ts` does today. Probing the characters one at
  a time uncovered Symptom D — `sed -i '/x/!s/\(a\)/b/' src/main.ts` is **allowed
  outright** in RED, a bypass needing no redirect at all. A criterion that does
  not require blocking cannot catch it.

**A-3 — AC-7, premise corrected, scope unchanged.** *(PO-3)*

- **Was:** the trailing-redirect shape generalises to `cp`, `mv`, `rm`, `touch`
  and `tee`, *"three of those also use `awk '{print $NF}'` or an equivalent"*.
- **Now:** per-command measured verdicts. Bypassed: `sed`, `cp`, `mv`. Holding:
  `rm`, `touch`, `tee`.
- **Why:** measured. `rm`/`touch` split their operand list with `tr ' ' '\n'` and
  drop `/dev/null` by filter; `tee`'s class already excludes `>`. All six commands
  stay in the criterion — three as fixes, three as regression guards, because a
  rewrite of the extractor block is exactly what breaks the three that work. This
  narrows no requirement; it corrects a stated fact and adds the three regression
  guards that fact had hidden.
- **RED refined this further, and it stands as a correction to A-3 rather than a
  new amendment**, because it changes no criterion: `tee`'s immunity comes from
  `[[:space:]]` in its terminating class, not from the `>` the class also excludes.
  The `>` earns its place only against the *unspaced* `tee src/main.ts>/dev/null`,
  so RED added two unspaced cases to give it something to own.

**A-4 — AC-6, three fixtures added.** *(PO-4)*

- **Was:** the spaced and unspaced `> /dev/null` forms.
- **Now:** additionally `2>/dev/null`, `> docs/log.txt` and `>> docs/log.txt`.
- **Why:** a redirect to a path the phase **permits** is a more ordinary thing to
  write than `/dev/null` and bypasses the guard identically — measured ALLOWED for
  both `>` and `>>`. Without these, a fix that special-cases `/dev/null` passes
  AC-6 and closes nothing. `2>/dev/null` blocks today on the nonsense path
  `2>/dev/null`, so it needs the "for the right reason" clause the other accident
  already had. This **widens** the criterion; nothing was removed.

**A-5 — AC-8, `WRITE` scope clarified in C-4 rather than in the criterion.**

No criterion text changed. Recorded here because the *fixture* the dispatch brief
suggested for AC-8 was unsatisfiable and RED said so: the Symptom C command cannot
be both zero-candidate **and** blocked naming `src/main.ts` (AC-6), because once
the fix lands it yields a candidate. AC-8's own text names no fixture — *"given any
command the extractors reduce to no candidates at all"* — so RED substituted two
that stay zero-candidate after the fix (`find src -name '*.ts' | xargs rm` and
`xargs touch < list`). **The orchestrator's brief was wrong, not the criterion.**
The escalation was correct and is accepted.

**Nothing here weakens a criterion.** A-1 moves one to a reachable tool; A-2 and
A-4 tighten; A-3 corrects a factual premise and adds coverage; A-5 changes no text.
No assertion was loosened, no tolerance widened, no case deleted, and no input
domain narrowed.

`mask_shell_quotes` is correct. The extractors are not, in two independent ways.

**(a) They match inside a masked span.** `\bsed\b`, `\btee\b`, `\b(cp|mv)\b` and
`\b(rm|touch)\b` all match a word sitting in prose inside a quoted argument or a
heredoc body, because masking replaces *operators and whitespace*, not letters. A
command name is only a command name at a **real** token boundary: start of string,
or after an unmasked space, tab, newline, `;`, `&`, `|`, `(` or `)`.

> **AMENDED IN RED, 2026-09-13 — (a) is true of `sed` only, and the reason
> matters.** Probed by piping each extractor's own `grep` over
> `mask_shell_quotes` output. Of the four command-name extractors, **only the

> require real whitespace after the name. `\btee\b([[:space:]]+-a)?[[:space:]]+`,
> `\b(cp|mv)\b[[:space:]]+` and `\b(rm|touch)\b[[:space:]]+` all demand
> `[[:space:]]+`, and a masked space is `\006`, which is **not** `[[:space:]]`:
>
> ```
> $ printf 'a\006b\n' | grep -cE 'a[[:space:]]b'   -> 0
> $ printf 'a\006b\n' | grep -cE 'a[^|&;()]b'      -> 1
> ```
> `[MEASURED — 2026-09-13]`
>
> Measured end to end against the `_lib.sh` fixture in `RED`: a `--dry-run`
> commit whose heredoc body mentions `cp`, `mv`, `rm`, `touch` or `tee` in
> ordinary prose is **allowed**; the same shape mentioning `sed -i` is
> **blocked**. So (a) and (b) are not independent for `sed` either — the prose
> match only *reaches* `-i` by crossing masked spaces, which is (b). Excluding
> `\001`–`\010` from the classes would therefore fix AC-1 on its own.
>
> **Two things follow, and neither weakens the prescription.** First, the five
> prose cases in AC-1 that name the other commands **pass today**; they are
> regression guards on the rewrite and are earned by DV-5 below. Second, (a) is
> still independently real, and a wider character class does **not** cover it:
> `\bsed\b` matches the `sed` in the *unmasked* token `sed-i`, so
> `git commit -m "sed-i"` is blocked today on `path: sed-i` with no mask

**(b) Their terminating classes omit the mask characters.** `[^|&;()]` and

masked span and `awk '{print $NF}'` returns the entire run as one field. The
mapping, from `lib.sh`: `\001` = `|`, `\002` = `&`, `\003` = `;`, `\004` = `>`,

**The fix is an operand parse, not a wider character class.** For each
write-capable command: find it at a real token boundary, split its arguments on
real whitespace, drop options and any redirect (`>`, `>>`, `>|`, `2>`, `<` and
their operands), and judge the remaining operand(s). "The last word" produced every
one of Symptoms A, C and D; a class that merely adds `>` to `[^|&;()]` fixes AC-6
and leaves AC-1 and AC-3 broken.

### The fix, and the one thing in it that was not in C-2

`write_candidates <masked-command>` is a single `awk` pass that scans the masked
command character by character and emits one write target per line, preceded by a
verdict line (`W`/`-`) saying whether a write-capable command name appeared at a
real token boundary. It is exactly C-2's prescription — anchor at a real token
boundary, split on real whitespace, drop redirects and their operands, judge the
rest per C-3's per-command table — and **C-2 needed no amendment**: it was built
as written and all 179 assertions pass.

The boundary rule falls out of the scan rather than being bolted on: a quoted
span is one token because the masker leaves the *quote characters* in place while
masking everything inside them, so `sed` inside prose is never a word. That is
why `git commit -m "sed-i"` stops blocking too — a widened character class could
not have fixed that case, because its match contains no mask character (C-2's
amendment says so, and it is the reason the rule is a scan and not a class).

**The one rule that is not in C-2, found by measurement:** *a literal newline
closes a quoted span.* `mask_shell_quotes` does **not** mask `'` or `"`, and it
does not mask them inside a comment or a heredoc body either. So the apostrophe
in the pre-existing case

```
echo hi # it's fine
echo x > src/main.ts
```

opens a span the scanner then never closes, and the real redirect on the next
line is swallowed as quoted data — **a source write in RED, allowed.** Measured
during GREEN, before the suite ran:

```
$ ... | write_candidates          # first cut, no newline rule
-                                 <- no candidate at all
$ ... | write_candidates          # with it
-
src/main.ts
```

The rule is sound rather than a patch: the masker emits `\010` for a newline a
quote spans and a literal `\n` only where it was *not* inside one, so a literal
newline is a guaranteed "outside a quote" point. The pre-existing assertion `a
redirect after a commented apostrophe` is what caught it, which is the second
time that case has earned its place.

Everything else in the parser is C-3 as amended, with two extensions to the
`sed` option grammar that RED's table did not cover. Both were **measured against
real sed rather than assumed**, because the brief says to check a named mechanism
rather than trust it:

```
$ sed --version | head -1
sed (GNU sed) 4.9
$ sed -ni 's/a/b/p' f1        -> f1=b            # -i inside a short cluster is in-place
$ sed -ie 's/a/b/' f1         -> f1=b, f1e       # the `e` after -i is the BACKUP SUFFIX,
                                                 # not -e: the script is still positional
$ sed -i -n -e 's/a/b/p' f1   -> f1=b            # -e: the first positional is a FILE
$ sed --in-place=.bk 's/a/b/' f1 -> f1=b, f1.bk
$ sed -i --file=sc.sed f1     -> rc=4            # --file= takes the script, f1 is the file
$ sed -i 's/a/b/' f1 f2       -> f1=b f2=b       # C-3's fourth bypass, re-confirmed
```

So: in a short cluster, scanning stops at `i` (everything after it is the backup
suffix), and only a trailing `e`/`f` consumes the next argument. `-ie` would have
been parsed as "expression follows" by a naive reading and the file operand would
have been mistaken for a script.

### Things a reviewer should look at sceptically

1. **The parser recognises a command name in any word position**, not only at
   the head of a simple command — `xargs rm`, `echo x | tee f`, and the
   `mutate.sh … -- cp a b` payload all depend on that, and so does the old
   behaviour it replaces. The cost is that `foo(rm)` in a heredoc body would be
   read as a command, since `(` is a real token boundary by C-2's own list. No
   case covers it; it is a false positive of the same family this story exists
   to remove, and it is narrower than what shipped before.
2. **Quote parity.** The masker leaves quote characters in place, so a span whose
   quotes do not balance (a `$( … )` with nested double quotes, say) merges
   tokens. Merging fails **open**, never closed: a merged token cannot equal a
   command name. The newline rule above bounds the damage to one line.
3. **`cp docs/notes.md src/main.ts docs/other.md` is still allowed**, and that is
   PO-11's correction, not an oversight: `cp` writes only its last operand, so
   `src/main.ts` there is a read.

extraction at all*, and the "one environmental difference" was a red herring.
`[MEASURED — 10 invocations, 2026-09-13]`

**The trigger, named.** It is Symptom D's mechanism, not a fourth bug:

1. `sed -i ` sits *outside* the quotes, so its spaces are real and `awk` sees
   three fields; the third is the whole quoted script, because every space
   inside it is masked to `\006`.
2. `[^|&;()]*` truncates that third field at the `(` of `min(` — inside the
   script.
3. `$NF` returns the truncated fragment. `tr -d` strips the opening quote,
   leaving `s\001\006\006…min`.
4. `path_is_implausible` **believes it**: the fragment carries alphanumerics and
   no paren (the paren is what truncated it), so it is not declined.
5. It unmasks to `s|        if a.ndim == 4 and min`, falls through `paths.conf`
   to the `source` fallback, and denies.

So B *is* A and D firing on a real command whose expression was scanned instead
of its operand, and the operand parse closes all three together. Covered by two
cases under `describe "MT-031 AC-5"`.

**Why the ten replays missed it, honestly: not known.** The difference is not
the phase (tested both) and not the variable, the delimiter, the parens or the
target (tested all four). The replays were run as live session commands while
this reproduction drives the hook directly with a fixture, which is the only
uncontrolled variable left — possibly the live command string differed from the
recorded one in some way nobody wrote down. Recorded as an open loose end rather
than resolved; it does not change the fix, and the case is in the suite now.
