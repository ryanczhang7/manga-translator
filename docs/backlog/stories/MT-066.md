## Context

Split out of MT-021 by the user on 2026-10-03 (MT-021 PO-2). MT-021 builds
`bake_chapter` and its `BakeReport`, and wires the command line to it; the
window has no way to bake at all. This story adds the Render command and
`BakeConfirmDialog` (`docs/wiki/design/components.md` §7 and §9).

The contract was pinned at PLANNED -> RED on 2026-10-03; see `## Contract`.

**Gate.** If this story's artifact broke, `unit` and `coverage` would fail. Both
are `required`, and both `covers src/mangatl/**`, which includes the new
`ui/bake.py`, `ui/bake_dialog.py` and `pipeline/bake.py`. No optional gate is the
only one reading this code, so `required_gates` stays empty.

## Acceptance criteria

- **AC-1** — Given a chapter open in the workspace, when Render is invoked, then
  `BakeConfirmDialog` opens stating the output folder path, the page count, the
  number of unreviewed lines with the pages containing them, and any `failed`
  or overflowing lines.
- **AC-2** — Given unreviewed lines, when the dialog is shown, then its primary
  action still renders — review does not gate the bake (§7).
- **AC-3** — Given the dialog is open, then focus is trapped inside it, and on
  close focus returns to the invoking control.
- **AC-4** — Given the user confirms, when the bake runs, then it runs off the UI
  thread and the window stays responsive.

**Baseline measured for this contract** (Lead PO, 2026-10-03, this machine):
`typeset` costs **~18 ms per line** (18 lines of 5-75 characters, one 200x160
polygon), and `load_faces` ~9 ms. So a 340-line chapter's overflow count costs
~6 s. **That is why the dialog's counts are computed on the worker too (C-3)**,
not on the GUI thread before the dialog opens. Read this number out; do not
re-derive it.

### C-1 — `mangatl.pipeline.bake`: the counts the dialog reads, before the bake

New exports, added to `__all__`. `bake_chapter` and `BakeReport` are unchanged.

```python
def output_dir_for(source_dir: Path) -> Path      # source_dir.with_name(source_dir.name + "_en")

@dataclass(frozen=True)
class LineRef:
    page_ordinal: int     # 0-based, the page's ordinal
    reading_index: int    # 0-based, the region's place in reading order

@dataclass(frozen=True)
class BakePreview:
    output_dir: Path
    page_count: int                      # len(project.pages()); == BakeReport.pages_written
    total_lines: int                     # entries of read_review_lines that are not None, whole chapter
    unreviewed: tuple[LineRef, ...]      # status == "proposed"
    failed: tuple[LineRef, ...]          # status == "failed"
    overflowing: tuple[LineRef, ...]     # see below

def preview_bake(project: Project) -> BakePreview
```

- Every tuple is ordered by `(page_ordinal, reading_index)`, ascending.
- `output_dir` is `output_dir_for(project.chapter.source_dir)`.
- **`len(unreviewed)` equals `bake_chapter(...).unreviewed_lines`** on the same
  project, by the same definition: `status == "proposed"`, read through
  `read_review_lines`, so `derive_status` applies. This cross-check needs no
  oracle. Assert that the two agree on a seeded chapter.
- `overflowing` holds exactly the lines whose block `bake_chapter` **would set**
  and that do not fit. A line `bake_chapter` would set is on a page with regions
  *and* a cleaned image, is not `None`, is not `failed`, and has an
  `effective_text` that is not blank. It overflows when
  `typeset(effective_text(line), region.polygon, faces).overflowed` is `True`.
  A line on an uncleaned page is never baked, so it never overflows. GREEN
  should share the rule for which lines get set with `bake_chapter` (today the
  private `_blocks`) rather than write it a second time. Two copies of that rule
  are how the dialog and the output come to disagree.
- It only reads. It writes nothing and creates no output folder: assert that the
  output folder does not exist after `preview_bake` on a chapter never baked.

### C-2 — `mangatl.ui.bake_dialog.BakeConfirmDialog`

```python
class BakeConfirmDialog(QDialog):
    def __init__(self, preview: BakePreview, parent: QWidget | None = None) -> None
    confirm_button: QPushButton   # objectName "bakeConfirm", property variant="primary", default button
    cancel_button: QPushButton    # objectName "bakeCancel"
```

The dialog only presents. It is built from a `BakePreview`, it reads no project
and it starts nothing. Confirm calls `accept()`. Cancel and `Esc` call
`reject()`.

**Exact copy.** voice.md says the interface uses *render*, never *bake*. In the
table, `n` = `page_count`, `t` = `total_lines` and `u/f/o` = the lengths of the
three tuples. `{pages}` is the distinct 1-based page numbers
(`page_ordinal + 1`) in that tuple, ascending and joined by `", "`, with the
prefix `page ` when there is one page and `pages ` when there are more. Every
label is `Qt.TextFormat.PlainText`, because a folder name holding `<` is not
markup, and every label word-wraps.

| objectName | When | Text |
|---|---|---|
| (window title) | always | `Render pages` |
| `bakeOutputFolder` | always | `str(output_dir)`, selectable by mouse and keyboard |
| `bakeUnreviewed` | `t == 0` | `No lines were found on any page.` |
| `bakeUnreviewed` | `u == 0 < t` | `All {t} lines were reviewed.` |
| `bakeUnreviewed` | `u == 1` | `1 of {t} lines was never reviewed ({pages}). Render anyway?` |
| `bakeUnreviewed` | `u > 1` | `{u} of {t} lines were never reviewed ({pages}). Render anyway?` |
| `bakeFailed` | `f == 1` | `1 line could not be translated and will be left empty ({pages}).` |
| `bakeFailed` | `f > 1` | `{f} lines could not be translated and will be left empty ({pages}).` |
| `bakeOverflow` | `o == 1` | `1 line does not fit its bubble and will be cut off ({pages}).` |
| `bakeOverflow` | `o > 1` | `{o} lines do not fit their bubble and will be cut off ({pages}).` |
| `bakeConfirm` | `n == 1` / `n > 1` | `Render 1 page` / `Render {n} pages` |
| `bakeCancel` | always | `Cancel` |

`bakeFailed` and `bakeOverflow` always exist. Each is **hidden**
(`isVisibleTo(dialog)` is `False`) when its count is 0.

**Accessible markup.** `accessibleName()` is `Render pages`.
`accessibleDescription()` is the visible label texts in the table's order
(folder, unreviewed, failed if shown, overflow if shown), joined by `"\n"`, so
that a screen reader reads the whole statement when the dialog opens.

**AC-2: review does not gate the bake.** With `u > 0`, the confirm button is
visible, enabled and the default button, and clicking it accepts the dialog.

**AC-3: focus.** The dialog is modal (`isModal()`) and is opened with `open()`.
Never use `exec()`, which would block the test. Initial focus is on
`confirm_button`. Pressing `Tab` (and `Shift+Tab`) more times than the dialog
has focusable children never puts `QApplication.focusWidget()` outside the
dialog. However the dialog closes (confirm, Cancel or `Esc`), focus ends on the
workspace's `render_button` (C-4). That focus is set **explicitly** on the
dialog's `finished` signal rather than left to window reactivation, because the
offscreen platform does not reactivate windows reliably: the workspace calls
`self.activateWindow()` and then `render_button.setFocus()`, in that order.

### C-3 — `mangatl.ui.bake.BakeController`: both steps off the GUI thread

```python
class BakeController(QObject):
    previewed = Signal(object)   # a BakePreview
    baked = Signal(object)       # a BakeReport
    failed = Signal(str)         # str(exception), from either step
    def __init__(self, project_dir: Path, parent: QObject | None = None) -> None
    def preview(self) -> None    # starts a worker, returns at once
    def bake(self) -> None       # starts a worker, returns at once
    def wait(self) -> None       # joins the current worker; no-op if none
    def is_running(self) -> bool
```

It follows the `RunController` pattern (`mangatl/ui/run.py`), for the same
reasons:

- Each step runs on a `threading.Thread` and opens its **own** `Project`
  through `open_project`, closing it before the thread ends. Under
  `check_same_thread`, a `Project` never crosses threads.
- `open_project`, `preview_bake`, `bake_chapter` and `output_dir_for` are
  imported by name into `mangatl.ui.bake` and called **as attributes of that
  module**. That is the seam the tests patch. The bake writes to
  `output_dir_for(chapter.source_dir)`.
- Signals are emitted from the worker, and receivers on the GUI thread get them
  through a queued connection.
- The worker catches any exception from either step and emits it as
  `failed(str(error))`. Nothing propagates out of the thread.

### C-4 — `Workspace`: the Render command

- `Workspace.render_button` is an `ActivatedByEnter` with objectName
  `renderButton`, property `variant="primary"` and text `Render pages`, at the
  **right end of the footer**. That is components.md §3's primary "Render
  pages" in the footer. `Workspace.render_status` is a `QLabel` in the footer,
  plain text and selectable, and empty at rest.
- `Workspace.render()` is also the button's `clicked` handler. Before
  `load_chapter` it does nothing. Otherwise it runs these steps in order:
  1. `translation_column.flush()`, so that a pending edit is counted and baked.
     An edit that was typed and not yet debounced must show as *reviewed* in
     the dialog.
  2. Create a `BakeController` for `project_dir_for(chapter.source_dir)`.
  3. Call `preview()`.
- **Loading** (components.md §1). This state lasts from `render()` until the
  dialog opens, and again from confirm until `baked` or `failed` arrives. In it:
  - `render_button.property("loading")` is `True`;
  - its `accessibleName()` is `Render pages, working`;
  - its text is `···` (three U+00B7), at an unchanged width, because the
    minimum width is fixed to the rest width;
  - it keeps focus;
  - a click does nothing: no second controller, no second dialog.

  At rest, `loading` is `False` and the accessible name is `Render pages`.
- On `previewed`, `Workspace.bake_dialog` becomes a
  `BakeConfirmDialog(preview, self)`, opened with `open()`. If it is rejected,
  nothing is written and the button returns to rest. If it is accepted, the
  workspace calls `flush()` again and then `bake()`.
- On `baked(report)`, `render_status` shows `Rendered {n} pages to
  {output_dir}.` and `live_region.announce` says the same, with `n` =
  `report.pages_written` (`Rendered 1 page to …` for one page). That sentence is
  voice.md's whole completion message and accessibility.md A-12's "bake
  complete, with the output folder". The button returns to rest.
- On `failed(reason)`, the same two show `Render failed: {reason}`. The button
  returns to rest and Render can be used again.
- `closeEvent` waits for an in-flight controller (`wait()`) **before** it
  flushes and emits `closed`, because `mangatl.app` closes the GUI thread's
  project on `closed`. A bake cannot be cancelled (`bake_chapter` takes no
  cancel), so the close waits for it to finish.

| Criterion | Kind | Oracle |

| AC-3 | mechanical | C-2's focus rules, read through `QApplication.focusWidget()` |
| AC-4 | oracle-free: invented metric + negative control | below |

**AC-4's metric.** Patch `mangatl.ui.bake.bake_chapter` (and, separately,
`preview_bake`) with a fake. The fake records `threading.current_thread()`,
then blocks on a `threading.Event` **with a timeout** of at most 5 s, then
returns a report. While the fake is blocked:

- (a) the recorded thread is not `threading.main_thread()`;
- (b) a `QTimer.singleShot(0, …)` that the test posts fires within 1000 ms
  (`qtbot.waitUntil`);
- (c) the button is `loading`.

Then the test sets the event and waits for `baked`.

**Negative control.** A worker that runs the step synchronously on the GUI
thread must fail (a) and (b). It must *fail* rather than hang, and that is what
the fake's timeout is for. RED cannot run this control because nothing is built
yet, so it is DV-2.

### PO-6 — `Workspace.render()` shadows `QWidget.render` (Lead PO, 2026-10-03)

C-4 named the command `render()`, which collides with Qt's
`QWidget.render(target, ...)`, the call that paints a widget into an image.
`tests/ui/test_app_theme_paint.py` makes that call on a `Workspace`. GREEN
found the collision: with a plain `render()`, that test failed with `TypeError:
Workspace.render() takes 1 positional argument but 5 were given`. GREEN resolved
it in source only. A bare `render()` runs the Render command, any call with
arguments goes to `QWidget.render`, and the button connects to the private
`_render_pages`. `QWidget.render` is not virtual, so Qt's C++ never dispatches to
this override. Only Python callers reach it, and the full suite passes.

**Decision:** keep it for this story. Renaming the command (for example to
`render_pages()`) would mean amending C-4 and returning to RED to change frozen
tests, all to remove a design smell rather than a defect. The contract's naming
was my error. I am reporting it to the user, who may prefer the rename.
