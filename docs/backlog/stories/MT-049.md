## Context

This is a defect in MT-016, recorded by MT-016's own GREEN phase (MT-016 `## Notes`,
"GREEN notes for review"). GREEN removed a viewport `Leave` handler because no test
required it (law 1). As a result, **hover persists when the pointer leaves the canvas
while it is over a region at the viewport edge.** The canvas reports hover only from
`mouseMoveEvent`. The last move inside the viewport reported that region, and no later
event reports "nothing". So the marker stays in `hover`, and the row keeps its hover
ground, after the pointer has moved to the page strip, the header or outside the window.

This breaks `docs/wiki/design/components.md` §4.4, which is normative: hover "never
persists after the pointer leaves". MT-016 AC-5's test covers leaving a region *inside*
the canvas only, where the next move reports `None`. That is why the gap shipped green.

This is a `fix`. AC-1 and AC-2 reproduce the defect against the shipped code, and the
tests that capture it become the permanent regression tests.

**Which required gate would fail if this story's artifact broke:** `unit`
(`uv run pytest -q tests/core tests/ui`; `tests/ui/` runs offscreen). No optional gate
is involved.

## Acceptance criteria

- **AC-1** — Given the pointer is over a region on the canvas and that region is
  hovered (its marker is in HOVER and its row's `hovered` property is truthy), when the
  pointer leaves the canvas viewport onto another widget of the window (the page strip),
  then `link.state.hovered_region_id` is `None`, no marker is in HOVER, and no row's
  `hovered` property is truthy.
- **AC-2** — Given the same hovered region, when the pointer leaves the canvas
  viewport without entering any other widget of the window (the viewport receives a
  `Leave` and nothing receives an `Enter`), then the three conditions of AC-1 hold.
- **AC-3** — Given a hovered region and a different, selected region, when the
  pointer leaves the canvas viewport, then `link.state.selected_region_id` is
  unchanged, the selected marker is still SELECTED, and every other marker is still
  dimmed. Neither the canvas viewport (both scroll values and the whole `transform()`)
  nor the translation list's vertical scroll value changes. (§4.4 says hover is purely
  visual, and §4.1 says selection is never lost by moving the mouse.)
- **AC-4** — Given a region hovered on the canvas, when the pointer moves from it
  directly onto the translation row of a different region, then that row's region is
  the hovered one: `hovered_region_id` is its id, its marker is in HOVER, and its row's
  `hovered` property is truthy. When the canvas clears its hover on the way out, it never
  wipes the hover that the row set on the way in.

## Out of scope

- Any other hover behaviour. §4.4 stays as MT-016 built it: no dimming on hover, no
  change to the selected marker's appearance, no pan and no list scroll.
- Hover during a drag. Also hover during a pan by keyboard or scroll wheel while the
  pointer is still: the art moves under the pointer, so the region under it changes
  without a mouse move. That is a real defect, but a different one with a different fix,
  and this story does not claim it.
- Row-side hover. `TranslationRow.leaveEvent` already clears it (MT-016).
- The `OffscreenIndicator` (MT-052). It will be a child widget of the viewport, and
  entering a child widget sends `Leave` to the viewport, so this fix will clear hover when
  the pointer moves onto the indicator. That is correct, because the indicator is not a
  region. MT-052 owns asserting it.
- Refactoring the hover wiring. The fix is one handler and one emit.
