## Context

Filed 2026-10-06 by the Lead PO from a user report. EPIC-01 (foundations: real gates).

Since the interpreter pin moved to CPython 3.13.15 (MT-070, merged 2026-10-05), the
required `coverage` gate (`project.conf`: `uv run pytest -q tests/core tests/ui
--cov=src/mangatl --cov-report=term-missing --cov-fail-under=90`) prints 20 warnings,
every one of them:

    .venv\Lib\site-packages\coverage\collector.py:236: ResourceWarning: unclosed database in <sqlite3.Connection object ...>

Python 3.13 warns when a `sqlite3.Connection` is garbage-collected without `close()`.
The gate passes - a warning is not a failure - which is exactly why it must be fixed at
the source rather than tolerated. **The user ruled out a `filterwarnings` entry**: that
silences the check instead of meeting it.

### Evidence (gathered before planning; the PO reproduced item 5 independently)

1. **Only under coverage's GC timing.** `unit` gate (plain `uv run pytest -q tests/core
   tests/ui`): 2574 passed, **0** unclosed-database warnings. `coverage` run: 20. The
   warnings are attributed to whichever test GC happened to run in
   (`test_the_project_stays_open_while_the_window_is_open` x4,
   `test_app_theme_startup.py::test_each_launch_shape_builds_the_window_it_names` x10,
   `test_app_theme_paint.py` x5, `test_badges.py` x1). **Those are not the leaking tests.**
2. **Allocation sites.** With `PYTHONTRACEMALLOC=25`, all 20 tracebacks are
   `store/project.py:596 sqlite3.connect` <- `open_project` <- `app.py:92 open_folder`
   <- `app.py:151 build_window`, called from exactly three test sites:
   - 5 x `tests/ui/test_app_opens_chapter.py:223` (`_build`), from tests that build a
     Workspace and never close it: `test_the_window_is_returned_not_shown` (its loop
     reassigns `window`), `test_a_folder_with_a_project_opens_the_review_workspace`,
     `test_the_chapters_pages_are_listed_by_filename_in_ordinal_order`,
     `test_the_first_page_is_current_and_shown_with_its_own_rows`,
     `test_a_relative_folder_argument_is_resolved`.
   - 2 x `tests/ui/test_app_theme_paint.py:468` (`_built`, the `"Workspace"` kind of
     `WINDOW_KINDS`).
   - 13 x `tests/ui/test_app_theme_paint.py:946` (`_workspace_with_rows`).
3. **Mechanism (probed).** `app.open_folder` hands ownership of the project to the
   Workspace: `window.closed.connect(lambda: project.__exit__(None, None, None))`
   (`src/mangatl/app.py:101`). `closed` is emitted only from `Workspace.closeEvent`
   (`src/mangatl/ui/workspace.py` ~659). `close()` on a never-shown window does deliver
   `closeEvent` (probed). But pytest-qt's `qtbot.addWidget` holds only a **weakref**;
   its teardown does `w = w(); if w is not None: w.close()`. The test function's locals
   are released when it returns, before fixture teardown, so PySide destroys the
   parentless Workspace first, qtbot finds a dead weakref, and closes nothing. Probe:
   events after teardown = `['destroyed']`, never `'closed'`, then `ResourceWarning:
   unclosed database`. **`qtbot.addWidget(window)` in `_build` reads as a close
   guarantee and is not one.**
4. **Production does not leak under its contract.** `main` shows the window and runs
   `app.exec()`; the user closing the last window delivers `closeEvent` -> `closed` ->
   project closed. `MainWindow._hand_over` (`src/mangatl/ui/main_window.py` ~190-203)
   shows the Workspace, keeps a strong reference in `self.opened`, then closes the
   intake. No production path builds a Workspace and drops it unclosed. MT-054 C-4 (the
   window `build_window` made closes its project on close) is already pinned by
   `test_closing_the_app_window_closes_its_project` and
   `test_the_project_stays_open_while_the_window_is_open`. **This is a test-teardown
   leak, not a production one.**
5. **Deterministic reproduction.** `-W error::ResourceWarning` alone does not fail the
   run: a warning raised in `__del__` is unraisable and pytest re-reports it as
   `PytestUnraisableExceptionWarning` ("22 passed, 5 warnings"). With both flags it
   fails, and without coverage:

       uv run pytest -q tests/ui/test_app_opens_chapter.py tests/ui/test_app_theme_paint.py -p no:cacheprovider -W error::ResourceWarning -W error::pytest.PytestUnraisableExceptionWarning

   Lead PO's own run, 2026-10-06, this worktree at 738a48f:

       FAILED tests/ui/test_app_opens_chapter.py::test_the_first_page_is_current_and_shown_with_its_own_rows
       FAILED tests/ui/test_app_opens_chapter.py::test_closing_the_app_window_closes_its_project
       FAILED tests/ui/test_app_theme_paint.py::test_each_summary_part_has_its_type_and_text_colour[summary-first]
       3 failed, 84 passed in 7.75s

   The failures land on whichever test GC ran in, so the **names** are not stable; the
   **non-zero count** is what the reproduction shows.

### Why `chore`, not `fix`

`story-authoring` defines `fix` as a bug whose criteria reproduce it, and `chore` as
work with **no behaviour change**. No production behaviour changes here (evidence 4);
the defect is in test teardown. A `fix` would promise a production regression test for
a production bug, and there is none. The story still carries a reproducing criterion
(AC-1) and a GC-independent regression check (AC-2), because that discipline is what
makes the change worth anything.

It runs **PLANNED -> RED -> GREEN -> GATES -> REVIEW**, *not* under SCAFFOLD: every
write this story needs is a test file, so RED is the phase that permits exactly that,
and the phase lock then *enforces* the "no production change" claim (source is frozen
in RED). SCAFFOLD would permit source writes this story must not make. GREEN is
expected to be a **no-op**, verified by the orchestrator rather than dispatched.
`check-boundaries.sh` demands a `## Handoff` only for `feature|fix`; this story fills it
anyway (see Contract).

### Gates

The required gates that fail if this story's artifact breaks: `unit` (AC-2's teardown
check runs under it permanently and does not depend on GC timing) and `coverage` (AC-3).
No optional gate is involved, so `required_gates` stays empty.

## Acceptance criteria

- **AC-1** - Given the suite after this story, when `uv run pytest -q
  tests/ui/test_app_opens_chapter.py tests/ui/test_app_theme_paint.py -p
  no:cacheprovider -W error::ResourceWarning -W
  error::pytest.PytestUnraisableExceptionWarning` is run, then it exits 0 with no
  failures. (Before: 3 failed, 84 passed - evidence 5.)
- **AC-2** - Given any test in `tests/ui/test_app_opens_chapter.py` or
  `tests/ui/test_app_theme_paint.py` that obtains a Project through `build_window` /
  `open_folder`, when that test's teardown has finished, then every Project opened during
  the test is closed (its connection refuses a query with `sqlite3.ProgrammingError`).
  This is checked by an assertion in the suite that runs under the plain `unit` gate and
  does **not** depend on garbage collection; before the fix it fails, deterministically,
  on every leaking test named in evidence 2.
  *Negative controls:* (a) with the story's shared close mechanism disabled, the AC-2
  check fails on each of those leaking tests; (b) with `src/mangatl/app.py:101`'s
  `closed.connect(...)` mutated to a no-op via `scripts/mutate.sh`, the AC-2 check fails
  on every test that builds a Workspace.
- **AC-3** - Given the full `coverage` gate command from `project.conf`, when it is
  run, then its output contains no `unclosed database` and no
  `PytestUnraisableExceptionWarning`, and the passed count is not lower than the
  pre-change run (both recorded in the handoff).

## Contract

**RED may amend any block in place with a reason; GREEN builds what the amended block
says** (here: GREEN changes nothing).

**Writes:** `tests/ui/test_app_opens_chapter.py`, `tests/ui/test_app_theme_paint.py`, `tests/ui/conftest.py`

- **Files that may change:** `tests/ui/test_app_opens_chapter.py`,
  `tests/ui/test_app_theme_paint.py`, and optionally a new `tests/ui/conftest.py` if the
  Test Developer judges one mechanism shared by both files cleaner than one per file. No
  file under `src/`, no `pyproject.toml`, no `project.conf`.
- **Shared mechanism, not ad-hoc closes.** Each file gets **one** mechanism by which
  every window it builds is closed at teardown while still alive - e.g. the `_build` /
  `_built` / `_workspace_with_rows` helpers holding a strong reference and registering
  `request.addfinalizer(window.close)`, or a fixture that collects built windows and
  closes them. Not a `window.close()` sprinkled into individual test bodies. The exact
  shape is the Test Developer's choice; the handoff names it.
- **AC-2 check.** A GC-independent assertion that every Project opened during a test is
  closed after the close mechanism has run. Suggested shape (amendable): spy on
  `mangatl.app.open_project` (monkeypatch a wrapper that records each returned Project
  and returns it unchanged), and at teardown - **ordered after** the close mechanism -
  assert each recorded Project's connection raises `sqlite3.ProgrammingError` on a
  trivial query. Holding the Project in the spy does not keep the Workspace alive, so
  before the fix the Workspace still dies unclosed and the check fails
  deterministically. The check must not call `gc.collect()` or otherwise rely on
  collection. The finalizer ordering is load-bearing; state it in the handoff.
- **Do not weaken or delete any existing assertion** in either file. Tests that already
  close their window explicitly (`test_closing_the_app_window_closes_its_project`,
  `test_the_project_stays_open_while_the_window_is_open`) keep their semantics; the
  latter asserts the project is **open while** the window is open, so the close
  mechanism runs at teardown, never earlier.
- **No suppression anywhere:** no `filterwarnings` (pyproject, conftest, `pytestmark`,
  `@pytest.mark.filterwarnings`), no `warnings.simplefilter`, no
  `-p no:unraisableexception`, no `-W ignore`.
- **Other `build_window` callers** (`test_app_theme_startup.py`,
  `test_chapter_summary.py`, `test_cost_estimate.py`, `test_folder_drop.py`,
  `test_folder_intake.py`, `test_intake_errors.py`, `test_start_button.py`,
  `test_start_run.py`) did not appear among the tracemalloc allocation sites
  (evidence 2). They are not in scope; if AC-3's run shows one of them leaking, RED
  stops and reports rather than widening silently.
- **Callers of changed signatures:** none in production. Test helper signatures may
  change; all their callers are inside the same file.
- **Oracle partition:** all three ACs are **mechanical** - exit codes, exception types,
  the absence of a string. Pin exactly; nothing to calibrate.

### How "watched to fail" applies to a test-only change

The production behaviour already exists, so RED runs in this order and pastes each
output into `## Handoff`:

1. **Before any edit**, run the AC-1 command; paste the failing output (the leak
   reproduced).
2. Write the **AC-2 check first**, with no close mechanism yet; run the two files under
   plain `uv run pytest -q ... -p no:cacheprovider`; paste the deterministic red - one
   failure per leaking test. This is the assertion being watched to fail.
3. Add the shared close mechanism; paste AC-2 green and AC-1 green.
4. Negative controls: (a) disable the close mechanism (a one-line edit to test code,
   reverted) -> AC-2 red; (b) `bash scripts/mutate.sh src/mangatl/app.py '<sed
   expression turning the closed.connect line into a no-op>' -- uv run pytest -q
   tests/ui/test_app_opens_chapter.py tests/ui/test_app_theme_paint.py -p
   no:cacheprovider` -> AC-2 red, file restored and verified by `mutate.sh`. Paste both,
   with the sed expression used.
5. Record the `coverage` gate's pre-change passed count and `unclosed database` count,
   for AC-3.

Then the orchestrator verifies `git diff --stat` touches no `src/` file, moves through a
no-op GREEN, and runs `bash scripts/gates.sh` in GATES; the `coverage` gate log is
grepped for `unclosed database` and `PytestUnraisableExceptionWarning` (AC-3).

## Out of scope

- **Any production change**, including making `Workspace` guarantee the release of its
  project on destruction (e.g. `weakref.finalize`, or a `destroyed` hook in `app.py`).
  Production meets its contract (evidence 4): every production path shows the window and
  closes it through `closeEvent`. A destruction-time release would be a *design change*
  to the ownership MT-054 C-4 decided (closing the window closes the project), and it
  would also mask exactly the kind of test leak this story fixes. If wanted, it is a
  separate `feature` story with its own criteria.
- **Making `ResourceWarning` / `PytestUnraisableExceptionWarning` an error suite-wide**
  (`filterwarnings = ["error::ResourceWarning", ...]` in pyproject). It would be a
  strengthening, but (a) it is GC-timing dependent: the plain `unit` run showed **0**
  warnings, so on its own it would not have caught this leak; (b) other leaks may exist
  elsewhere in `tests/core` / `tests/ui` under it and would turn this story into a
  sweep. A follow-up candidate, to be put to the user. AC-2's GC-independent check is the
  durable guard for this story's leak.
- **The other `build_window` callers** listed in the Contract, unless AC-3 shows one
  leaking (then RED stops and reports).
- **Unrelated, a separate issue, not planned here:** in the same `coverage` +
  `PYTHONTRACEMALLOC=25` investigation run,
  `tests/core/test_cv2_lost_completion_port.py::test_erase_mask_and_letterbox_on_the_main_thread_survive_a_closed_completion_port`
  failed (AssertionError at line 368); it passed under plain `unit`. Possibly
  tracemalloc/coverage overhead, possibly an MT-069 flake. It was not re-run in
  isolation, and needs its own investigation (a `spike`, or a `fix` once reproduced).
