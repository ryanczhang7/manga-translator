## Context

Filed by the MT-068 spike. Read `docs/wiki/audits/MT-068-cv2-parallel-failure.md`,
`## Decided` 2 and 4 and evidence E7, E8 and E10, before anything else.

**The defect.** `onnxruntime/capi/_pybind_state.py:14` calls `platform.system()`.
On CPython 3.12.14 (pinned by `stack.md` §2) that runs a WMI query on a worker
thread created by `_wmi.exec_query`.

- The worker is given a pointer to a struct on the calling thread's stack.
- If the WMI connection is slow, the caller gives up after about 200 ms and
  returns, and the worker keeps that pointer.
- When the worker finishes, it calls `CloseHandle` with whatever value now sits in
  the dead stack slot.
- In the audit's probes that value was `0x20`, the default thread pool's I/O
  completion port, and closing it breaks every later parallel cv2 call (MT-069's
  state). Other times it was `0x0`, or the current-thread pseudo-handle.
- Upstream fixed this in GH-134313 (gh-130727). The fix is in the 3.13 and 3.14
  branches and not in 3.12.14 (audit E7).

**Why this story is first.** This is the trigger of the gate failures recorded in
MT-068. It runs at import in the gates, on CI's `windows-latest` and in the
shipped app. A stray `CloseHandle` can close any handle, so containing cv2
(MT-069) does not make it safe.

The required gate that fails if this story's artifact breaks is `unit`, which
runs `tests/core`.

## Acceptance criteria

- **AC-1** - Given a fresh Python process in which CPython's `_wmi` worker thread
  is held for 400 ms inside its connect step, so that the query's caller times
  out, when `mangatl.detect.session` is imported (which imports `onnxruntime`) and
  that worker has run to completion, then no handle the worker did not create has
  been closed by it.
- **AC-2** - Given the same process with the worker *not* held (the negative
  control), when the same import completes, then the import succeeds and
  `platform.system()` returns `"Windows"`, both before and after the fix.

## Contract

- **The inducing step,** re-derived from audit recipe B and not copied from
  `spikes/`:
  - redirect `_wmi.pyd`'s import-table entries for `SetEvent` and `CloseHandle`;
  - hold the worker's second `SetEvent` (the `connectEvent`) for 400 ms, once;
  - record every `CloseHandle` the worker thread makes, with the handle's object
    type *before* the close.

  "Did not create" means anything other than the write end of the pipe
  `_wmi.exec_query` created for that query.
- **RED's expected failure (measured, audit E8):**
  - on the current code, with the query reached through `import onnxruntime` and a
    hold of 300 ms or more, the worker closed a handle that was not its pipe in
    21 of 21 runs (`0x0`, or the pool's `0x20`);
  - with the main thread idle after the timeout, it closed its own pipe, 2 of 2.

  So the import must follow the induced timeout, as AC-1 says.
- **Vacuity guard.** If the fix stops the WMI query from running at all, AC-1
  holds because no worker exists. That is a legitimate fix. The test must then
  prove it is not vacuous by another route: the hook installed, and either a
  worker observed or the query observed not to run. A test that passes because
  its hook silently failed to install is the failure mode to rule out.
- **Oracle partition.** AC-1 is **mechanical**: the set of worker closes outside
  its own pipe is empty. AC-2 is **mechanical**, and it is the negative control.
- **Layer:** production start-up, wherever `onnxruntime` is first imported
  (`detect`, `ocr`, `clean`, per the import contract), **or** the interpreter pin
  that `stack.md` §2 owns. The story chooses at planning.
  - A pin change is a stack decision: amend `stack.md` and re-verify the wheel
    availability concern recorded there.
  - If the pin route is chosen, split it out as its own story before RED.
  - The implementation is not chosen here.
- **Platform.** Windows-only mechanism, so `skipif(sys.platform != "win32")` is
  correct. CI runs on `windows-latest`.
