## Context

Found by MT-146's diff review (`docs/backlog/stories/MT-146.md`, `## Diff
review`, finding 1, rated "Should fix"; MT-146 shipped without it by the
orchestrator's disposition). EPIC-02 owns the project file (MT-005); this is a
defect in how that file is upgraded on open.

**The defect.** `open_project` upgrades an older file in place through
`_migrate_to_current` (`src/mangatl/store/project.py`, 746-797), which runs
each step of `_MIGRATIONS` with its own `connection.executescript(script)` and
only *after the whole chain* sets `chapter.schema_version`, `PRAGMA
user_version` and commits. `executescript` commits any pending transaction
before it starts and the scripts contain no `BEGIN`, so **every statement of
every step autocommits**. An exception part way through a step leaves the file
half-upgraded at its old `user_version`, and the next open re-runs the chain
from the old version against a file that no longer looks like it:

- **A table rebuild interrupted at the copy** keeps its aside table. Five
  steps are rebuilds that rename a table aside, create the new one, copy and
  drop: `_MIGRATE_TO_V3` (`llm_call_v2`), `_MIGRATE_TO_V4` (`chapter_v3`),
  `_MIGRATE_TO_V10` (`llm_call_v9`), `_MIGRATE_TO_V11` (`batch_job_v10`) and
  `_MIGRATE_TO_V13` (`region_v12`). The review named four; `_MIGRATE_TO_V3` is
  the same recipe (project.py 351-366). Every later open dies on the rename:
  the reviewer reproduced it on the shipped code with
  `tests/core/test_schema_v13.py`'s `_build_v12_file`, the rename and the
  create applied, then `open_project`: `OperationalError there is already
  another table or index with this name: region_v12`, tables
  `[('region_v12',), ('region',)]`, version 12. No row is lost; the project
  never opens again and nothing says why.
- **The gap is not only the rebuilds' (the PO's own reading, 2026-11-10).**
  Because the version is written once at the end, a file more than one version
  behind that fails in a *later* step has its *earlier* steps committed. A v11
  file interrupted in the v12 -> v13 rebuild has already committed
  `_MIGRATE_TO_V12`'s `ALTER TABLE chapter ADD COLUMN`; the next open re-runs it
  at version 11 and dies on `duplicate column name` - the very failure the
  `_MIGRATIONS` comment (614-622) says the chain exists to prevent. So the
  unit that must be atomic is **the whole chain**, not each rebuild.

The most likely trigger is the newest step: `_MIGRATE_TO_V13` copies every
`mask_blob`, the largest column in the file, so it is the step most likely to
run out of disk. A killed process is covered by the same fix: SQLite's journal
rolls back an uncommitted transaction on the next open, and that is SQLite's
guarantee rather than one this story tests.

**Measured, 2026-11-10, sqlite3 under CPython 3.13.15** (scratch script, a
parent/child pair at `user_version` 12): one `executescript` of
`PRAGMA foreign_keys = OFF; PRAGMA legacy_alter_table = ON; BEGIN;` + an
`ADD COLUMN` + rename-create-copy + a failing statement + drop +
`PRAGMA user_version = 13; COMMIT;` raised `no such table: __interrupted__`
with `in_transaction: True`; after `connection.rollback()` the file read
`user_version` 12, its original two tables with their original `sql`, the
child row intact, the `ADD COLUMN` undone. The same script without the failing
statement then upgraded it to 13 with `foreign_key_check` empty. So
`user_version` is transactional, DDL is, and the pragmas set before `BEGIN`
take effect. Note the `in_transaction: True`: without an explicit rollback the
connection is left holding the open transaction.

Finding 2 of the same review is folded in because it is three comments in the
files this story already reads: since MT-146 there are **three** exclusion
reasons (`watermark`, `user`, `art`), and three places still say two -

**Required gate:** `unit` - the interruption tests in AC-1..AC-4 fail on

## Acceptance criteria

- **AC-1** — Given a project file at version 2, 3, 9, 10 or 12 (the version
  just before each of the five table rebuilds: v3, v4, v10, v11, v13), when
  `open_project` runs that rebuild and the step fails after its copy and before
  its aside table is dropped, then `open_project` raises, and the file on disk
  afterwards has its original `PRAGMA user_version`, no aside table
  (`llm_call_v2`, `chapter_v3`, `llm_call_v9`, `batch_job_v10`, `region_v12`),
  the same `sqlite_master` (`type`, `name`, `sql`) as before the open, and the
  same rows in every table.
- **AC-2** — Given a file left by AC-1's failure, when `open_project` is
  called again with nothing failing, then it opens, the file is at
  `SCHEMA_VERSION`, and its tables and rows are those an uninterrupted upgrade
  of an identical file produces.
- **AC-3** — Given a file at version 11, when the upgrade fails in the
  v12 -> v13 rebuild (after `_MIGRATE_TO_V12` has run in the same open), then
  the file is left at version 11 with `chapter` as it was (no
  `consistency_run_id` column), and the next `open_project` with nothing
  failing opens it at `SCHEMA_VERSION` - not `duplicate column name`.
- **AC-4** — When `open_project` raises because an upgrade failed, then the
  exception is the one the failing statement raised (same type, same message),
  and the file's handle is released: the project file can be renamed straight
  afterwards.
- **AC-5** — A successful upgrade is unchanged: every existing
  `tests/core/test_schema_v*.py` and migration test in `tests/core/` passes
  with no edit, and after a successful upgrade the connection
  `open_project` returns reads `foreign_keys = 1`, `legacy_alter_table = 0`
  and is not in a transaction.
- **AC-6** — The three comments name all three exclusion reasons:
  `schema.py`'s `region.excluded` note says `watermark`, `user` or `art` and no
  longer claims `_MIGRATE_TO_V8`'s words; `region.py`'s `excluded` comment names
  `art` with the story that added it (MT-146); `architecture.md`'s `region`
  row reads `NULL, 'watermark', 'user' or 'art'` with schema v13. (Docs and
  comments; checked by reading, not by a test.)

## Contract

**Writes:** `src/mangatl/store/project.py`, `src/mangatl/store/schema.py`, `src/mangatl/domain/region.py`, `docs/wiki/architecture.md`, `tests/core/test_migration_atomic.py`

**No signature changes.** `open_project(project_dir: Path) -> Project` and
`_migrate_to_current(connection, found) -> None` keep their signatures, so no
caller changes (callers: `app.py:161`, `cli.py:222,263`, `ui/bake.py:76`,
`ui/run.py:203`, `bench/{acceptance,cost,s2,seed,__main__}.py`).

**The chain is one transaction (the design; AC-3 is why).** `_migrate_to_current`
builds **one** script and runs it with **one** `executescript`:
`PRAGMA foreign_keys = OFF; PRAGMA legacy_alter_table = ON;` (outside any
transaction - set inside one they are silent no-ops, module docstring item 1 and
`_MIGRATE_TO_V4`'s note), then `BEGIN;`, then every step whose version exceeds
`found`, in order, then `UPDATE chapter SET schema_version = <N>;` and
`PRAGMA user_version = <N>;` (both formatted from `SCHEMA_VERSION:d`, the
existing reason they cannot be bound), then `COMMIT;`. One `executescript` per
step does **not** work: each call commits the transaction the previous one
opened. Consequently:

- the two pragma lines leave `_MIGRATE_TO_V4` and `_MIGRATE_TO_V13` (inside the
  transaction they would be no-ops) and become the chain's prologue, so they
  apply to every step. That is safe only if `legacy_alter_table = ON` changes
  nothing for the child-table renames (V3, V10, V11): it governs how `RENAME`
  rewrites *other* schema objects' references, and those tables are referenced
  by nothing (V10 drops `llm_call`'s triggers first). **RED checks whether a v2
  `llm_call` carries triggers** that V3's rename would interact with; the
  existing per-version suites, which compare migrated declarations to fresh
  ones, are the guard (AC-5). The two notes that say "first statements inside
  the script" are reworded to say where the pragmas now are.
- the restores after the commit (`foreign_keys = ON`, `legacy_alter_table =
  OFF`) stay, after the commit, for the measured reason in the docstring.
- a file already at `SCHEMA_VERSION` runs no script (today it runs the
  `UPDATE` and two no-op pragmas; either is fine, AC-5 does not pin it).

**The failure path.** If the script raises, the connection is rolled back
(`connection.rollback()` - `in_transaction` is True, measured), closed, and the
original exception re-raised unchanged (`raise`, not wrapped). Where it lives -
in `_migrate_to_current` or around its call in `open_project` - is GREEN's
choice; closing is `open_project`'s existing reason for the `SchemaTooNew`
branch (an abandoned handle on Windows locks a file the user may want to move).

**The test seam: `_MIGRATIONS`, monkeypatched, read at call time.** The tests
interrupt a step by `monkeypatch.setattr(project, "_MIGRATIONS", ...)` with that
one step's script altered: `INSERT INTO __interrupted__ VALUES (1);` inserted
immediately before its `DROP TABLE <aside>;`, so the rename, the create and the
copy have run and the drop has not. So:

- `_migrate_to_current` keeps reading the module-level `_MIGRATIONS` when
  called (it does today), and each rebuild's script keeps its `DROP TABLE
  llm_call_v2;` / `chapter_v3;` / `llm_call_v9;` / `batch_job_v10;` /
  `region_v12;` as a literal substring.
- **the test asserts its replace changed the script** (the altered string
  differs from the original and contains `__interrupted__` exactly once) - a
  `str.replace` that matches nothing interrupts nothing and the test would pass
  against any code, the needle rule in `rules.md`.
- AC-2's "an uninterrupted upgrade of an identical file" is a second file built
  by the same builder and opened without the patch; compare `sqlite_master`
  (`type`, `name`, `sql`) and each table's rows ordered by `rowid`/`id`.
  AC-1's "as before" is a snapshot of the same queries taken before the open.

**Builders.** The per-version builders exist: `_build_v9_file`
(`test_schema_v10.py`), `_build_v10_file` (`test_schema_v11.py`),
`_build_v11_file` (`test_schema_v12.py`), `_build_v12_file`
(`test_schema_v13.py`), `_build_v3_file(..., ceiling_usd=)` (`test_schema_v4.py`);
the v2 file for V3 is in `tests/core/test_ledger.py` or `test_project.py` (RED
finds it). Import them or move them to a shared helper under `tests/` - RED's
choice; a builder moved is a test-file change, allowed in RED. Each builder
must give the rebuilt table at least one row, or the copy has nothing to
interrupt and AC-1's row check is vacuous.

**Oracle partition.** All mechanical: version numbers, table names and
`sqlite_master` rows are pinned exactly. No thresholds, no negative controls
beyond the replace-changed-something check above.

**Test-only dependencies:** none (pytest's `monkeypatch`, stdlib `sqlite3`).

## Out of scope

- **Repairing a file already broken by the defect** (an aside table left at an
  old version). No recovery path, no detection message: MT-146 merged on
  2026-11-10, and the defect needs an upgrade to fail part way. If one is ever
  reported, it is its own story.
- **Testing a killed process or a real disk-full.** The interruption is an
  injected failing statement; process death is covered by SQLite's journal
  rolling back the same transaction, which is SQLite's guarantee.
- **A user-facing message for a failed upgrade.** `open_project` raises the
  original error as today; how `app.py`/`cli.py` present it is unchanged.
- **Backing the file up before upgrading**, or any change to which steps exist,
  what they convert, or `SCHEMA_VERSION` (stays 13; no new migration step).
- **The `ADD COLUMN` steps' own text** (V2, V5-V9, V12): they become atomic by
  joining the chain's transaction, not by being edited.
- Any other stale comment beyond the three AC-6 names.
