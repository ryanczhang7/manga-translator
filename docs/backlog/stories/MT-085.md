## Context

Filed by the EPIC-04 mutation audit,
`docs/wiki/audits/EPIC-04-2026-10-13.md`: survivors PJ2 and SC3
(`## Decided` item 6, `## Evidence` E-2). **This is the audit's lowest
priority.** Neither survivor is reachable as a silent fault through today's
pipeline. Both are stated contracts of `store/project.py` that no test holds.

- **PJ2.** `Project.write_proposed` (`store/project.py:892`) documents that
  "an index outside the page's reading indices raises `ValueError` naming it,
  with nothing written". Drop the `0 <=` half of the check and every test
  stays green: only `7` and "one past the end" are tested. `-1` then writes to
  `region_ids[-1]`, the page's **last bubble**, which is exactly the failure
  `parse.py`'s docstring warns about. Today `parse_lines_text` rejects
  negatives first (P1 is killed), so the pipeline cannot reach this, but the
  store's own guard is unpinned.
- **SC3.** The v3->v4 migration (`store/project.py:359`) converts a REAL
  ceiling with `CAST(ROUND(x * 1000000) AS INTEGER)`. Without the `ROUND`,
  every test stays green, because `test_schema_v4.py:122-127` deliberately
  chose 1.5, which is exactly representable. In SQLite 3.53.1, 10 of the 500
  whole-cent ceilings from $0.01 to $5.00 truncate one micro-dollar low: 2.01,
  2.03, 2.05, 2.07, 2.09, 4.02, 4.06, 4.10, 4.14 and 4.18. That errs in the
  safe direction, and only for files created before MT-044.

**Settled:** both are unprotected, and the code is correct. **Evidence, to
verify:** the list of affected ceilings, which was measured on SQLite 3.53.1
only.

## Acceptance criteria

- **AC-1 (PJ2)**: Given a page with regions, when `write_proposed` is handed a
  **negative** reading index (`-1`), then it raises `ValueError` naming the
  index, and no row of the page changes; in particular the last region's
  proposal is unchanged. Fails under PJ2.
- **AC-2 (SC3)**: Given a version-3 project file whose stored REAL ceiling is
  one that truncation gets wrong (for example `2.01`), when it is opened and
  migrated, then `budget_ceiling()` is exactly `Usd.from_micro(2_010_000)`.
  Fails under SC3, where it reads 2,009,999.
