## Context

**Filed 2026-10-01 by the Lead PO**, from an ordering artifact recorded in
[[MT-062]]'s GATES (`## Deferred verifications`, "Ordering artifact, not a
catch").

[[MT-006]] AC-9 ("the run is headless") is checked by two mechanisms its
`## Contract` PO-3 names. **Mechanism 1** is
`tests/core/test_pipeline.py::test_a_whole_run_executes_with_no_qt_application_in_existence`
(line 1186 at `e5454f0`): an *in-process* whole run asserting
`QApplication.instance() is None` before the run, at each stage invocation, and
after. **Mechanism 2** is
`test_a_fresh_interpreter_importing_the_runner_loads_no_pyside_module`
(line 1220): one subprocess that imports `mangatl.pipeline.runner` and counts
`PySide6` modules.

Mechanism 1 is **order-dependent**, and MT-006's RED measured and wrote that down
(PO-3, "RE-MEASURED AND AMENDED BY RED"): pytest-qt's `QApplication` outlives the
`tests/ui` test that built it, so if any `tests/ui` test runs earlier in the same
pytest process, the first assertion fails - on correct code. Every gate in
`project.conf` runs `tests/core` before `tests/ui`, so no gate sees it today; but
a reordered command, `-p randomly`, or a combined command such as a
`scripts/mutate.sh` run that names a UI file first turns it red for reasons that
have nothing to do with the code. MT-062's GATES hit exactly that.

**Reproduced by the Lead PO at PLANNED, 2026-10-01, unmutated tree at `e5454f0`**
(`bash scripts/mutate.sh --check`: no stranded mutation):

### Decision (the user, 2026-10-01)

Four options were put to the user:

- **(a)** run the whole-run assertion in a subprocess;
- **(b)** assert "no QApplication was *created by* the run" - the instance is
  unchanged before, during and after;
- **(c)** a conftest hook enforcing `tests/core`-before-`tests/ui` ordering;
- **(d)** the subprocess, plus the in-process test kept under a conditional skip.

**The user chose (a): a subprocess.** Reasons, as given:

- (b) is a **weakening**: if an application already exists, a pipeline that
  silently relies on it still passes, so the test would no longer prove the
  pipeline never needs Qt. (Control M3 in `## Contract` C-4 is that pipeline.)
- (c) hides the coupling rather than removing it, and breaks under
  `-p randomly`.
- (d) adds a skip, which the harness counts as a weakening (`rules.md`,
  Non-negotiables).

So: a whole pipeline run executes in a **fresh interpreter**, where pytest-qt is
not loaded; inside it, no Qt application object exists before the run, at every
page's stage invocation, or after it; and the run reaches `RUN_FINISHED` with the
pinned event projection. The in-process, order-dependent version is **replaced**,
not kept behind a skip. The claim "the pipeline never needs Qt" is not weakened
in any way.

### Why `fix` and not `chore`

The type was decided deliberately. A `chore` is "no behaviour change" and may use
SCAFFOLD, under which nothing forces a test to be earned - and this story's
entire content *is* a test whose value depends on being earned. It also has an
observable failure (`1 failed` above) that the criteria reproduce, and the
corrected test becomes the permanent regression test for it, which is the
definition of a `fix` (`story-authoring`, Types). The defect being in the test
suite rather than in `src/` does not change that: [[MT-060]] was the same shape
(a test-only correction of a test that failed on correct code) and was a `fix`.
It runs the ordinary PLANNED → RED → GREEN → GATES → REVIEW → DONE path, with
GREEN expected to be a no-op (`## Contract` C-6).

## Acceptance criteria

- **AC-1** — Given a pytest process in which a `tests/ui` test has already
  constructed a `QApplication`, when the whole-run headless check runs, then it
  passes: `uv run pytest -q -p no:cacheprovider tests/ui/test_run_thumbnail.py
  tests/core/test_pipeline.py` reports no failure (it reports `1 failed` on
  `e5454f0`), and so do the reverse order and the check run alone.
- **AC-2** — Given a whole run of the four-page fixture chapter with one stage,
  executed in a fresh Python interpreter in which pytest-qt is not loaded, when
  it executes, then no Qt application object exists before the run, at any of the
  four stage invocations, or after it, and the run emits exactly the pinned
  one-stage event projection and ends with outcome `finished`.
  *Controls (`## Contract` C-4):* a runner that constructs a Qt application at
  the start of `run_chapter` (M1) fails it; and a runner that **requires** an
  existing application (M3) fails it even when the parent pytest process already
  holds a `QApplication` - the case option (b) would have let through.
- **AC-3** — Given a runner that merely imports PySide6 at module level without
  constructing an application (MT-006 DV-3's mutation, M2), when the
  `tests/core/test_pipeline.py` suite runs, then the fresh-interpreter import check
  (Mechanism 2) fails and the whole-run check passes - the two remain separate
  checks of separate claims ("imports no Qt" and "constructs and needs no Qt
  application"), and Mechanism 2's assertion is unchanged.

   `[type name, ordinal or null, stage or null]` - `_projected`'s shape),
   `"outcome"` (`RunOutcome.outcome`). The child asserts nothing itself: every
   judgement is made by the parent, so a failure reads as a pytest assertion
   with a message rather than as a child traceback.

**Why `QCoreApplication.instance()` and not `QApplication.instance()`:** it is the
base-class accessor and returns *any* application object - `QCoreApplication`,
`QGuiApplication` or `QApplication` - so it is at least as strong as what the
in-process test checked, and it does not import `QtWidgets` into the child.
**RED verifies this once, outside the framework**, and records it in the handoff:
in a scratch interpreter with `QT_QPA_PLATFORM=offscreen`, after constructing
each of `QApplication([])`, `QGuiApplication([])` and `QCoreApplication([])`
(one per interpreter), `QCoreApplication.instance()` is not `None`. If any one
of them reads `None`, amend this block to check that accessor as well.

**The parent asserts, each with a message naming what it means:**

| Assertion | Meaning |
|---|---|
| `result.returncode == 0` (message carries `result.stderr`) | the run itself did not crash - this is what fires under M3 |
| `report["pytestqt_loaded"] is False` | precondition: the interpreter really is fresh. Guards against a future "simplification" to `python -m pytest` in the child, which would reload the plugin and reintroduce the coupling |
| `report["before"] is True` | no application before the run (true by construction in a fresh interpreter; asserted so the report is complete) |
| `report["seen"] == [True] * _PAGE_COUNT` | no application at **any** of the four stage invocations; the length pins that the stage ran four times, so an empty list cannot pass vacuously |
| `report["after"] is True` | the run did not leave one behind |
| `[tuple(p) for p in report["projection"]] == _ONE_STAGE_PROJECTION` | AC-9's "emits its full event stream", the settled projection |
| `report["outcome"] == RUN_FINISHED` | AC-9's "it completes" |

The report is parsed from `result.stdout.strip().splitlines()[-1]`; if stdout is
empty, the returncode assertion has already failed with stderr in its message.
