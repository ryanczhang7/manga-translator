## Context

**Filed 2026-09-29 by the Lead PO**, from a finding made 2026-09-28 during
[[MT-046]] RED and left out of that story's scope. Same lineage of harness
corrections as [[MT-031]]..[[MT-034]], [[MT-037]], [[MT-039]]..[[MT-043]] and
[[MT-046]]. Epic: [[EPIC-01]].

**The bug.** `scripts/gates.sh` is documented, in three places, as refusing to
run behind a stranded mutation *before any gate runs*:

- `scripts/gates.sh`'s own comment above the check (main `22cc8a3`, `:736-744`):
  "Refused before any gate runs, because a run behind a stranded mutation is
  minutes spent producing a number that must be thrown away."
- `.claude/harness/rules.md:176-177`: "`gates.sh` runs it before any gate".
- `.claude/state/README.md:122`: "`scripts/gates.sh` runs that before it runs
  any gate, and refuses with exit 2".

The code does not. The gate loop is top-level code, not a function called later:
`while IFS= read -r line; do` at `:329` through `done < "$CONF"` at `:651`,
which evaluates each gate command at `:521-523` (`=== gate:` header, `eval
"$cmd"`, `tee "$LOGDIR/$id.log"`) and, since MT-046, writes
`$LOGDIR/$id.failed.log` at `:648` for any non-pass. The `mutate.sh --check`
call is at `:750`, after the loop, after `[ "$LIST" = 1 ] && exit 0` (`:653`)
and after the `--audit` block's `exit` (`:722-727`). So behind a stranded mutation
every selected gate executes in full, writes its logs, and only then is the run
refused with exit 2. The refusal does protect the gate *record* - it exits
before `record_in_story` (`:951`) and before `last-gate-run` is written
(`:886-898`) - but not the minutes, not the side effects of the gate commands,
and not `.claude/state/gate-logs/`.

**Was the placement deliberate?** No. `git log -L` on the block shows one
commit, `a0b43a2` (2026-09-22, "harness: a mutation in flight says so, and the
gates refuse to run behind one"), and its message says "gates.sh runs it before
any gate". The only placement reason it gives - and the comment's second
paragraph repeats - is "placed after --list and --audit, which read the manifest
and never look at the tree". That is a reason to *skip* the check for those two
modes, not to put it after the loop: the loop is also where --list and --audit
do their work, so "after --list/--audit exit" was read as "before the gates",
and it is not. Nothing the check needs is computed in the loop (it reads only
`$ROOT`).

**Reproduced by the Lead PO, 2026-09-29, against main `22cc8a3`**, independently
of the existing test: a `make_project_fixture` with one gate whose command is
`touch gate-ran.marker; printf 'Tests  47 passed (47)\n'`, a hand-written
sentinel `printf 'pid\t999999\nfile\tsrc/main.ts\n' >
.claude/state/mutations/x.active`, and an emptied `gate-logs/`:

```
== mode=''            rc=2 marker=PRESENT header=1 logs=unit.log
== mode='--fast'      rc=2 marker=PRESENT header=1 logs=unit.log
== mode='--gate unit' rc=2 marker=PRESENT header=1 logs=unit.log
== control (sentinel removed) rc=0 marker=PRESENT
```

Exit 2 in every mode - the refusal fires - but the gate command ran, its
`=== gate:` header was printed and `unit.log` was written, in all three.
`[MEASURED - 2026-09-29, Lead PO]`

**Why the existing test did not catch it.** `.claude/tests/gates.test.sh:1027`
asserts `assert_not_contains "and no gate ran" "PASS         unit" "$out"`.
`PASS` lines are printed only in the summary, which the refusal pre-empts, so
that assertion holds whether or not the gate ran. It is a test of the summary,
named as a test of execution. This story replaces it with one that observes
execution directly.

**The required gate that would fail if this broke:** none in `project.conf`;
the judge is CI's `Harness self-test` step (`bash scripts/selftest.sh`), same
as MT-043 and MT-046. See PO-3.

## Acceptance criteria

In every criterion, "a stranded mutation" means at least one `*.active` file
under the fixture's `.claude/state/mutations/` for which `bash
scripts/mutate.sh --check` exits non-zero; "the marker gate" is a required gate
whose command creates a marker file in the fixture before printing output that
matches its evidence line. The criteria hold regardless of which log files a
gate run writes (`<id>.log`, and since MT-046 `<id>.failed.log`).

- **AC-1** - Given a stranded mutation and the marker gate, when `bash
  scripts/gates.sh` is run with no arguments, then it exits 2, its combined
  output contains no `=== gate:` line, the marker file does not exist
  afterwards, and no file under `.claude/state/gate-logs/` was created or
  modified by the run.
- **AC-2** - Given the same state, when `bash scripts/gates.sh --fast` is run,
  then the same four observations as AC-1 hold.
- **AC-3** - Given the same state, when `bash scripts/gates.sh --gate <id>` is
  run naming the marker gate, then the same four observations as AC-1 hold.
- **AC-4** - Given the same state with a story active in the fixture (a story
  file with a `## Gate results` section, and `current-story.env` naming it),
  when `bash scripts/gates.sh` is run, then the story file is byte-identical
  afterwards and `.claude/state/last-gate-run` was not created or modified.
- **AC-5** - Given the same state, when `bash scripts/gates.sh --list` and
  `bash scripts/gates.sh --audit` are each run, then each exits 0 and prints
  the marker gate's id, and neither creates the marker file. (The refusal does
  not gag the modes that read only the manifest.)
- **AC-6** - Given the same fixture with the sentinel removed (the negative
  control for AC-1..AC-4), when `bash scripts/gates.sh` is run, then it exits 0,
  prints an `=== gate:` line for the marker gate, and the marker file exists
  afterwards. Without this, a gates.sh that refused unconditionally, or a test
  whose marker could never be written, would satisfy every criterion above.
- **AC-7** - The prose is true of the code: the comment above the check in
  `scripts/gates.sh`, `.claude/harness/rules.md` ("`gates.sh` runs it before any
  gate") and `.claude/state/README.md` ("runs that before it runs any gate")
  each still state that the check precedes every gate, and none of them is
  reworded to describe the old placement. The comment's paragraph about
  `--list` and `--audit` says those modes are *skipped* by the check, not that
  the check is placed after them.
