## Context

**Filed 2026-09-13 out of MT-031's corrective RED, by the orchestrator.** The
test-developer escalated it rather than resolving it quietly, which was the right
call: pinning it either way inside MT-031 would have frozen a behaviour nobody had
decided on, or contradicted a contract clause MT-031 had already pinned.

**This is pre-existing, not a regression from MT-031.** The old extractor took
`awk '{print $NF}'` for `cp|mv` too, so `mv src/main.ts docs/gone.md` yielded
`docs/gone.md` and was allowed. MT-031 replaced that with a real operand parse and
kept the same per-command semantics (its C-3: `cp`/`mv` judge the **last** operand,
the destination). So MT-031 neither introduced this nor fixed it, and nothing
merged needs re-auditing on its account.

### The hole

`mv` does not only write its destination — it **removes its source**. The guard
judges the destination and says nothing about the operand that is about to
disappear. Measured against the `_lib.sh` fixture with the shipped guard, on
MT-031's branch:

```
=== RED: source is frozen ===
mv src/main.ts docs/gone.md          ALLOWED     <- a frozen file leaves its path
mv src/main.ts src/renamed.ts        BLOCKED  src/renamed.ts
cp src/main.ts docs/copy.md          ALLOWED     <- correct: cp is a pure read
rm src/main.ts                       BLOCKED  src/main.ts          (control)
mv docs/notes.md src/main.ts         BLOCKED  src/main.ts          (control)

=== GREEN: tests are frozen ===
mv tests/main.test.ts docs/gone.md   ALLOWED     <- A FROZEN TEST, IN GREEN
mv tests/main.test.ts tests/renamed.test.ts  BLOCKED  tests/renamed.test.ts
rm tests/main.test.ts                BLOCKED  tests/main.test.ts   (control)

=== and a command the guard has never heard of ===
git mv src/main.ts docs/gone.md      ALLOWED
```
`[MEASURED — 2026-09-13, orchestrator's own fixture]`

**Three findings, and the second and third are not in the escalation.**

1. **`mv` out of a frozen path is unjudged.** The escalation's finding.
2. **It applies in GREEN to tests, not only in RED to source.** `mv
   tests/main.test.ts docs/gone.md` makes a frozen test disappear during GREEN.
   That is the same law-2 territory as MT-031's fourth bypass, by a different
   route, and it is the more serious direction because GREEN is the phase where
   an agent has a motive to make a test stop failing.
3. **A rename *within* a frozen category is caught only by accident** — because
   the destination happens to be frozen too, not because the source was judged.
   `mv src/main.ts docs/gone.md` proves the source is never looked at.
4. **`git mv` is not in the extractor's command list at all**, so it is unjudged
   in both directions. Neither is `install`, and `ln -f` can replace a path
   without naming it as a destination the current rules recognise.

### Why it was not folded into MT-031

A numbered PO decision, recorded so the reasoning survives:

- **No MT-031 acceptance criterion covers it.** MT-031's ACs are about operand
  *parsing* — prose read as a path, a redirect hiding an operand, a capture group
  truncating a match. This is about operand *semantics*: which operands of a
  command constitute a write.
- **Fixing it contradicts a clause MT-031 pinned.** MT-031's C-3 says `cp`/`mv`
  judge the last operand, and MT-031's own `## Regressions` R-1 added six
  assertions pinning exactly that. Changing it is a contract amendment, new tests,
  new source work and another GREEN/GATES cycle on a story that had already
  bounced once and carries 185 assertions.
- **`story-authoring`'s sizing rule**: one story is one RED→GREEN cycle. This is
  its own cycle.

## Acceptance criteria

- **AC-1** — Given `mv FROZEN PERMITTED` in a phase that freezes the source
  operand's category, when the guard runs, then it is **blocked**, and the
  reported `path:` is the **source** operand. Measured allowed today, in RED for
  `source` and in GREEN for `test`.
- **AC-2** — Given `cp FROZEN PERMITTED`, when the guard runs in any phase, then
  it is **permitted**. `cp` does not modify its source; this is the criterion that
  stops AC-1 being satisfied by judging every operand of both commands, which is
  the false positive MT-031's PO-11 exists to prevent.
- **AC-3** — Given `mv PERMITTED FROZEN` and `mv FROZEN FROZEN`, when the guard
  runs, then both are still blocked, naming a frozen path. The existing
  destination rule must survive.
- **AC-4** — Given `git mv FROZEN PERMITTED`, when the guard runs, then it is
  **blocked** naming the source operand. ~~Today `git mv` is not a command the
  extractor recognises at all.~~ **Struck in PLANNED, 2026-09-14, by the
  orchestrator: measured false — see PO-2.** `git mv PERMITTED FROZEN` is blocked
  today on the destination, because the parser recognises a command name in any
  word position and `mv` is one. The criterion itself is unchanged and still
  real; only the sentence explaining *why* it fails was wrong.
- **AC-5** — Given `cp a b c` with three arguments and `b` frozen, when the guard
  runs, then it is **permitted** — MT-031's C-3 and its R-1 assertions, which this
  story must not regress. **Clarified in PLANNED, 2026-09-14, by the orchestrator
  — see PO-1.** This criterion is about **`cp` only**. MT-031's suite also asserts
  the same shape for `mv` (`mv docs/notes.md src/main.ts docs/other.md` ALLOWED,
  `.claude/tests/phase-guard.test.sh:550`), and that assertion is **measurably
  wrong about real `mv`** and directly contradicts AC-1: `mv f1 f2 d/` removes
  both `f1` and `f2`. That one assertion is this story's to correct, in RED, with
  a reason recorded under `## Regressions`. Every *other* case in MT-031's suite
  is the rest of this criterion and must stay green.
- **AC-6** — The reported `path:` distinguishes *which* operand was refused, so a
  denial on the source of an `mv` is legible as such rather than looking like a
  denial on the destination.

### C-2 The defect, stated exactly

`.claude/hooks/lib.sh`, `write_candidates`, the `flushcmd()` dispatch:

```awk
else if (cmd == "cp" || cmd == "mv") { FLAG = 1; lastop() }
```

`lastop()` emits the last non-option operand and nothing else. For `cp` that is
right — `cp` does not modify its sources. For `mv` it is wrong, because `mv`
**removes** every operand that is not the destination. So the guard judges the one
operand `mv` creates and says nothing about the one-or-more it destroys.

The header comment's per-command table says the same wrong thing in prose
(`cp, mv   the LAST non-option argument`), and MT-031 C-3 pinned it. Both are this
story's to change.

### C-3 Per-command operand semantics, as this story leaves them

Only the `cp`/`mv` row changes. Every other row is MT-031 C-3 verbatim and must
survive.

| Command | Operand(s) the guard must judge |
|---|---|
| `sed -i` / `sed -i.bak` / `sed --in-place` | every non-option argument, minus the first when no `-e`/`--expression`/`-f`/`--file` supplied the script |
| `tee` / `tee -a` | every non-option argument |
| `cp` | the **last** non-option argument only — the destination. Sources are reads. **Unchanged.** |
| `mv` | **every** non-option argument: the last because it is created, the rest because they are removed |
| `rm` / `touch` | every non-option argument |
| redirect `>` `>>` `>\|` | the single word following it |
| `<` `<<` | a READ; names no write target |

**Measured, GNU coreutils 8.32, 2026-09-14, in a scratch directory:**

```
$ echo a > f1; echo b > f2; mkdir d; mv f1 f2 d/
$ ls -1            ->  d                 (f1 and f2 are GONE)
$ ls -1 d          ->  f1  f2
$ echo c > g1; echo d > g2; mkdir e; cp g1 g2 e/
$ ls -1            ->  d  e  g1  g2      (g1 and g2 remain)
$ ls -1 e          ->  g1  g2
```

That is the whole asymmetry, and it is why AC-2 and AC-5 are not satisfied by
"judge every operand of both commands".

### C-4 `git mv` needs no new command name, and adding one would be wrong

**Measured 2026-09-14 against the `_lib.sh` fixture, on `main` at `b1583d5`:**

```
RED:    git mv src/main.ts docs/gone.md     ALLOWED
RED:    git mv docs/notes.md src/main.ts    BLOCKED  src/main.ts
```

The parser recognises a command name **in any word position** (MT-031's own
"things a reviewer should look at sceptically", item 1 — `xargs rm`,
`echo x | tee f` and the `mutate.sh ... --` payload all depend on it).
`git mv a b` therefore already parses as `cmd=mv` with operands `a b`, which is
why the destination direction blocks today.

So **AC-4 is discharged by the `mv` rule in C-3 and by nothing else.** Do not add
`git` to `isname()`, and do not add a `git mv` special case: `git` is not a
write-capable command, and naming it would make `git` at a real token boundary
start a command context, which is a false-positive generator across every
`git commit -m` in the repository.

The story's Context finding 4 says `git mv` "is not in the extractor's command
list at all, so it is unjudged in both directions". The first half is true and the
second half is false; see PO-2.

### C-5 The shape of the denial (AC-6)

The deny message today is:

```
  story:    MT-033
  phase:    RED
  path:     src/main.ts
  category: source
```

AC-6 requires that a denial on an `mv` **source** be legible as such. Pin: the
message gains **one line, after `path:`**, naming the role the refused token
played in the command. Vocabulary, fixed here so the tests can assert on it:

| role line | when |
|---|---|
| `operand:  source of mv (removed by the move)` | a non-final `mv` operand |
| `operand:  destination of mv` | the final `mv` operand |
| `operand:  destination of cp` | the final `cp` operand |
| *(line absent)* | every other candidate — redirects, `rm`, `touch`, `tee`, `sed -i`. Their role is not ambiguous and inventing one for them is churn. |

`path:` keeps its exact current spelling and position — `assert_blocked` in
`.claude/tests/_lib.sh` matches `path:     <expected>` followed by a space or end
of string, and ~110 existing assertions depend on it. **The new line goes after
`path:`, never before it, and never inside it.**

**The mechanism is GREEN's choice, with two constraints.**

1. **The candidate filter in `phase-guard.sh` is the hazard.** It is
   `tr -d quotes | grep -vE '^\s*$|^-|\*|^/dev/' | sort -u`, and every one of
   those anchors assumes the line **is** the bare path. If `write_candidates`
   starts emitting a role alongside the target, that filter, the `$EXEMPT`
   membership test and the `resolve_vars` call all have to be updated together.
   A role-prefixed line that slips past `^/dev/` is a new false positive on
   `cmd > /dev/null`, which is the most common command shape in the repository.

   > **AMENDED IN RED, 2026-09-14 — the instruction stands, the worked example
   > is wrong.** "The filter, the `$EXEMPT` membership test and `resolve_vars`
   > all have to be updated together" is correct and unchanged. But the

   > positive on `cmd > /dev/null`. Measured by removing that anchor under

**Shape of the problem, covered.**

- *Zero*: `mv` with no operands at all — a write-capable name with nothing to
  judge stays allowed (and MT-031 AC-8's `no-candidate` trace is what records it).
- *One*: `mv src/main.ts` — a single operand is still a candidate. Real `mv`
  errors on this; the guard does not consult the world and must not start.
- *Many*: `mv src/main.ts docs/a.md docs/b/` and the `cp` mirror of it.
- *Boundaries*: the **first** operand (source), a **middle** operand (the
  corrected 550 case), and the **last** operand (destination) of the same
  three-argument command, each asserted separately for both the path and the
  role. That is what makes the role track position rather than command name.
- *Options*: `mv -f`, `mv -v`, `cp -t` — an option must be skipped, must not
  shift which operand is read, and must never itself become a candidate.
- *Errors / fail-open*: `mv $UNSET_THING docs/gone.md` must stay a **decline**,
  not become a block. The classifier's default for an unrecognised string is the
  most restrictive category, so an unresolved variable reaching `check_path` is a
  hard block on a path that does not exist — MT-031 Symptom A, from the new side.
- *Out of scope, pinned cheaply*: `cp -t src/ docs/notes.md` is a **real** hole
  (PO-3) and is asserted at its current permissive behaviour, so GREEN cannot
  silently "fix" it on the way past, untested.

**False-positive controls, which are half the suite.** AC-2, AC-5 and C-6 exist
to stop AC-1 being satisfied by "judge every operand of both commands". The `cp`
block (5) and the C-6 block (12), plus the three `assert_allowed` cases inside
the GREEN block, are those controls: `cp` out of a frozen path in RED and in
GREEN, a `cp` source in a variable, `mv` between permitted paths in three
phases, an option, prose, a read, `echo x > /dev/null`, `git diff > /dev/null`.
Two of those last are aimed directly at C-5's hazard: the candidate filter drops
lines that are empty, start with `-`, contain a glob or start with `/dev/`, and
every one of those anchors assumes the line **is** the bare path.

**Helpers added to the test file** (not to `_lib.sh`, which this story does not
own): `assert_role`, `assert_no_role`, `assert_blocked_on_either`. The first two
are AC-6's oracle — `assert_blocked` reads only the `path:` line, so without them
no assertion could read the role line and AC-6 would be untested. The third
exists because `mv FROZEN FROZEN` has two correct answers and AC-3 asks only for
"a frozen path"; pinning one of them would freeze a candidate ordering that no
criterion and no contract clause fixes.

**The denial message.** `check_path` in `.claude/hooks/phase-guard.sh` must emit,
in this order and with this spelling:


  position. 79 `assert_blocked` call sites in this one file match

  line land after `category:` where it reads as a different field.
- The three role strings, verbatim, are the only ones any assertion accepts:
  `source of mv (removed by the move)`, `destination of mv`, `destination of cp`.
- The line is **absent** for every other candidate: redirects, `rm`, `touch`,
  `tee`, `sed -i`. Assertions #39–43 fail if it is present.

**`write_candidates`** keeps its name, its single masked-command argument, and
its output contract as `phase-guard.sh` reads it today: a first line that is `W`
or `-`, then zero or more lines. Nothing asserts on it directly — it is reached
only through the hook — so **how** the role travels from the parser to
`check_path` is entirely GREEN's choice.

**What is NOT constrained, and should stay the implementer's:**

- The order in which candidates are judged. `mv FROZEN FROZEN` is asserted with

  not frozen by this story.
- Whether the role travels inline with the candidate, in a parallel stream, or is
  recomputed lazily in the deny branch. C-5's constraint is one `awk` pass and no
  extra process per candidate, and a lazy lookup in the branch that is about to
  deny is explicitly allowed.
- The `-` / `W` verdict line's meaning, MT-031 AC-8's `no-candidate` trace, and
  the `decline` log format. Untouched by any new assertion.
- `cp -t` / `mv -t` (PO-3), `install`, `ln -f`, `rsync`, `dd`. Out of scope; `cp
  -t` is pinned at its current permissive behaviour so it is not fixed by
  accident.
