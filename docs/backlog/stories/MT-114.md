## Context

EPIC-09 PO-6: the consistency pass is text-only and returns **only the lines
it would change**, each with a reason, never the full text. This story is
the request and its parse - the `translate` half, testable with a fake
client. Applying corrections to the store is MT-115.

Why corrections-only is a hard constraint and not a preference: the epic's
cost case (EPIC-09 `## Why now`) puts a full-rewrite pass at ~$5.50 for 200
pages against ~$3.60 with corrections only; the pass would cost more than the
batch saved. The schema enforces it: every item is a changed line, and a
response item whose `corrected_en` equals the line's current English is a
**defect of the pass**, counted and dropped by the parse, never applied.

**Chunking.** A volume's text (Japanese + English + glossary) for 200 pages
is ~200 x (500 + 700) tokens plus the glossary, around 250k - over the 200k
tier (MT-101 D-12, measured on the whole prompt). The pass is chunked at page boundaries so each request's
estimated input stays under `CONSISTENCY_MAX_INPUT_TOKENS`; each chunk is one
request and one ledger row. A chunk is a contiguous run of pages, so a
correction's cross-page evidence is as local as the chunk.

Required gates: `unit`, `coverage`.

## Acceptance criteria

- **AC-1** - `consistency_text(pages, glossary_block)` renders the glossary
  block first, then every page under `Page {n}:` with each line as
  `[{reading_index}] {ja}` / `    {en}`, skipping lines with no English, in
  page then reading order; byte-identical on identical input.
- **AC-2** - `CORRECTIONS_SCHEMA` requires a `corrections` array whose items
  require exactly `page` (integer), `reading_index` (integer), `corrected_en`
  (string), `reason` (string) with no additional properties at either level;
  no property of the schema can carry a full page.
- **AC-3** - `parse_corrections(text, current)` where `current` maps
  `(page, reading_index)` to the current English returns `ProposedCorrection`s
  for the items whose `corrected_en` differs from `current`, in response
  order; items equal to `current` are dropped and counted in the result's
  `unchanged_returned`; an item whose `(page, reading_index)` is not in
  `current` raises `UnknownLine` naming both numbers.
- **AC-4** - `chunk_pages(pages, glossary_block, max_tokens)` returns contiguous, ordered,
  non-overlapping chunks covering every page exactly once, each with
  `estimate_tokens(consistency_text(chunk, glossary)) <= max_tokens`; a
  single page over the limit raises `PageTooLarge` naming it; for a fixture
  of 200 pages x 20 lines whose text estimates over the default limit (the
  Context's ~1,200 tokens a page) it returns more than one chunk under the
  **default** `max_tokens`.
- **AC-5** - Given a fake client, `run_consistency(client, chunk_text)`
  sends one `generate_content` with `contents == [chunk_text]` (no image),
  `system_instruction == CONSISTENCY_PROMPT`, the JSON mime type,
  `CORRECTIONS_SCHEMA`, `ThinkingLevel.MEDIUM`, `max_output_tokens ==
  CONSISTENCY_MAX_OUTPUT_TOKENS`, and returns a `ConsistencyResult` with the
  raw text, usage (thinking added to output) and `CallInfo`.

## Contract

**Writes:** `src/mangatl/translate/consistency.py`, `src/mangatl/translate/gemini.py`, `src/mangatl/domain/correction.py`, `tests/core/test_consistency_pass.py`, `tests/core/test_gemini_consistency.py`

```python
# domain/correction.py (MT-103's module)
@dataclass(frozen=True)
class ProposedCorrection:
    page_ordinal: int        # 0-based; the prompt shows 1-based `Page {n}` and the parse converts
    reading_index: int
    corrected_en: str
    reason: str
@dataclass(frozen=True)
class ParsedCorrections:
    corrections: tuple[ProposedCorrection, ...]
    unchanged_returned: int
@dataclass(frozen=True)
class ConsistencyResult:
    text: str
    usage: TokenUsage
    call: CallInfo

# translate/consistency.py - SDK-free
CONSISTENCY_PROMPT: str                         # "return only lines you would change; never restate a line you keep"
CORRECTIONS_SCHEMA: dict[str, Any]
CONSISTENCY_MAX_INPUT_TOKENS: int = 180_000     # MT-101 D-12: 200k measured on the prompt; 20k headroom for the system prompt, as MT-104
CONSISTENCY_MAX_OUTPUT_TOKENS: int = 8_192
@dataclass(frozen=True)
class PageLines:
    ordinal: int
    lines: tuple[tuple[int, str, str | None], ...]   # (reading_index, ja, en or None)
class UnknownLine(Exception): ...
class PageTooLarge(Exception): ...
def consistency_text(pages: Sequence[PageLines], glossary_block: str) -> str
def chunk_pages(pages: Sequence[PageLines], glossary_block: str, max_tokens: int = CONSISTENCY_MAX_INPUT_TOKENS) -> list[tuple[PageLines, ...]]
def parse_corrections(text: str, current: Mapping[tuple[int, int], str]) -> ParsedCorrections

# translate/gemini.py
def run_consistency(client: Client, chunk_text: str) -> ConsistencyResult
```

Oracle partition: all **mechanical**. No new dependency.

**Semantics, pinned at PLANNED (2026-11-05, lead-po).** RED may amend a
block in place with a reason, in this section; GREEN builds what the
amended block says.

- **The text (AC-1), exact bytes.** `consistency_text` is `glossary_block`,
  then one blank line, then the page blocks separated by one blank line; no
  preamble, no trailing newline. When `glossary_block == ""` the first page
  block starts at byte 0 (no leading blank line). A page block is
  `Page {ordinal + 1}:` then, for each `(reading_index, ja, en)` with
  `en is not None`, the two lines `[{reading_index}] {ja}` and
  `    {en}` (four spaces). Lines are in the order the tuple holds them
  (reading order is the caller's). A page with no line that has English is
  dropped, header and all, and the pages after it keep their own
  `ordinal`-based number (a gap, not a renumbering) - MT-104's rule, for the
  same reason. Pages are rendered in the order given. `estimate_tokens` is
  `domain.glossary`'s.
- **Numbering.** The prompt and the response speak 1-based `page`
  (`Page {n}`, `n = ordinal + 1`); the domain speaks 0-based
  `page_ordinal` (`store.corrections` keys `(page_ordinal, reading_index)`).
  `parse_corrections` converts: `page_ordinal = page - 1`. `current` is
  keyed by **0-based** `(page_ordinal, reading_index)`, the store's key, so
  MT-115 builds it straight from the store. `UnknownLine`'s message carries
  `page` and `reading_index` **as the response wrote them** (1-based page),
  as plain integers.
- **The parse (AC-3).** `json.loads` errors propagate. A body with no
  `corrections` key raises `ValueError` naming the key (MT-104's rule). An
  item missing one of the four keys, or with a value of the wrong type,
  raises `ValueError` - **not skipped** (PO-1 in `## Notes`). Equality with
  `current` is exact string equality, no normalisation. Order of
  `corrections` is response order; `unchanged_returned` counts dropped
  items. A line in the text with `en is None` is never in `current`, so a
  correction to it is `UnknownLine`.
- **Chunking (AC-4).** Greedy and deterministic: starting at the first
  page, each chunk takes pages in order while
  `estimate_tokens(consistency_text(chunk, glossary_block)) <= max_tokens`
  still holds with the next page added; the first page that would push it
  over starts the next chunk. Every chunk's text carries the glossary block
  (it is in the estimate). A page whose one-page chunk estimates over
  `max_tokens` raises `PageTooLarge` with the page's `ordinal`, the
  estimate and the limit in the message, as plain or comma-grouped
  integers; nothing is returned for the pages before it. `pages == ()`
  returns `[]`. Each chunk is a `tuple[PageLines, ...]` of the caller's
  objects (identity preserved).
- **The request (AC-5).** `run_consistency` makes **one**
  `client.models.generate_content(model=MODEL_ID, contents=[chunk_text],
  config=...)` call, keyword-only, exactly those three kwargs; `contents` is
  a one-element list holding the plain `str`. It performs **no** input-limit
  check (`chunk_pages` already did; a chunk is sent as given) and no retry.
  `text` is `response.text or ""` - raw, unparsed, because the ledger row
  and the parse are MT-115's and the caller may want the body on a parse
  failure. `usage` is `_usage_of(response.usage_metadata)`; `call` is
  `CallInfo(response.response_id or "", response.model_version or MODEL_ID)`,
  as `propose_glossary` records them.
- **Exceptions.** `UnknownLine` and `PageTooLarge` derive from `Exception`
  directly, not `ValueError` (MT-104's reason: a refusal is not a malformed
  answer).
- **SDK-free** means importing `translate.consistency` does not load
  `google.genai` (the `test_glossary_pass.py` subprocess check).
- **Domain additions** go in `domain/correction.py`, beside `Correction`,
  and are **branch-free** frozen dataclasses (`coverage-core` holds
  `domain/**` at 100% with branch coverage; `CallInfo`'s docstring has the
  rule). `ConsistencyResult` imports `TokenUsage` and `CallInfo` from
  `domain.translation`.

**Callers of changed signatures:** none. Every name in the block is new;
no existing export changes shape. `rg "run_consistency|consistency_text|parse_corrections|chunk_pages|ProposedCorrection|ConsistencyResult|ParsedCorrections" src tests` on 2026-11-05 finds nothing outside this story.

## Notes

- **PO-1 (2026-11-05, PLANNED -> RED).** A malformed correction item (a
  missing key, a wrong type) makes `parse_corrections` **raise**, where
  MT-014 C-4 has `parse_terms_text` skip a malformed term and keep its
  neighbours. The difference is what the answer does: a term is merged into
  a glossary the user reviews, a correction overwrites a proposal the user
  has not touched (PO-7). Half-reading an answer whose shape the schema
  already forbids and applying the rest would silently apply corrections
  from a response the model mis-shaped; refusing the whole chunk costs one
  re-run. The user may overrule before GREEN.
