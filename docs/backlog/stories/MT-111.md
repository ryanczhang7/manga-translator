## Context

EPIC-09 PO-5 (as amended 2026-11-03), and D6 applied to a batch: **the guard judges the whole volume
before it is submitted**, and a refused batch submits nothing and spends
nothing. This story is the pipeline's submit half: after detect, clean and
OCR have run for every page (the existing per-page stages, with no translate
stage) and the glossary pre-pass has run (MT-105's `ChapterStep`), build
every page's request in `neighbours` context (MT-107), project the batch,
check it, submit it through the bound submitter (MT-110), persist the job
(MT-103), and say so.

**The projection.** A batch of `n` pages is one decision about `n x
page_estimate(model, pricing="batch")` - MT-100's per-page figure at the
batch tier (MT-102). `Budget.check(spent, projection)` compares
`spent + next_call` to the ceiling inclusively; for a batch `next_call` is
the whole batch. The $2.00 default ceiling against a 200-page volume at
~$0.015 a page is $3.00: **a volume is refused under the default ceiling**,
and that is correct - the ceiling is per chapter, the volume is ten chapters,
and raising or scoping the ceiling is out of this epic (EPIC-09 "Deliberately
not"). The user sets the stored ceiling (MT-044) for a volume; the refusal
names the three numbers so they know what to set.

`pipeline` may not import `translate`: the submitter is a `Callable` bound by
`compose`, and the page input type lives in `domain`.

Required gates: `unit`, `coverage`, `coverage-core` (`domain/budget.py`, `domain/batch.py`, `domain/events.py` are under its 100 % branch floor; `pipeline/` and `compose.py` under `coverage`). All `required`; a broken split or guard fails `unit`.

## Acceptance criteria

*Rewritten 2026-11-03 at PLANNED for PO-1 (several jobs per volume); the
one-job criteria they replace are in git history (commit `f5c3052` and
before). The job-row half of PO-1 is MT-137, which this story depends on.*

- **AC-1** - `page_estimate("gemini-3.1-pro-preview", pricing="batch")` is
  the design-A token profile priced at the batch row (`domain.rates.price(...,
  pricing="batch")`), rounded up to the cent exactly as the standard figure
  is; `pricing` defaults to `"standard"`, so every value MT-100 pins is
  unchanged, and an id absent from the batch table raises `UnknownModel`.
- **AC-2** - `Budget.project_batch(pages, page_estimate)` returns
  `Projection(next_call = pages x page_estimate, remaining_chapter = the same,
  basis="estimate", sample_count=0)`; for 0 pages both are `$0.00`.
- **AC-3** - `plan_batches(sizes, limit)` splits page request sizes (bytes,
  in ordinal order) into consecutive runs whose sum stays `<= limit`, greedily
  from the first page: `[5, 5, 5], 10 -> [(0, 1), (2, 2)]`; `[10], 10 -> [(0,
  0)]` (at the limit fits); `[] -> []`; a single size over the limit raises
  `ValueError` naming the ordinal, its size and the limit, before any range
  is returned. `INLINE_REQUEST_LIMIT_BYTES == 20_000_000` (MT-101 D-9's 20 MB,
  decimal, the smaller reading).
- **AC-4** - Given a project with OCR done on three pages, a glossary
  proposed, a stored ceiling of `$0.06`, a fake submitter, and a request-size
  function that lets all three fit one job: `submit_volume` calls the
  submitter **once** with three `BatchPageInput`s in ordinal order whose
  contexts are the `neighbours` contexts (`build_prompt_context(project, n,
  mode="neighbours")`) and whose OCR is the stored lines; one `batch_job` row
  exists, over `0..2`, with the submitter's job name and the given model id;
  `BatchSubmitted(run_id, job_ids=(row,), page_count=3, projection)` is
  emitted; the return value is `(row,)`.
- **AC-5** - The same with a request-size function that makes pages 0-1 fill
  a job and page 2 another: the submitter is called **twice**, with inputs
  `[0, 1]` then `[2]`; two rows exist, `0..1` and `2..2`, in that order in
  `pending_jobs`; the guard was consulted **once**, on the whole volume -
  `BatchSubmitted.projection.next_call == 3 x page_estimate` and the
  submitter's first call happens after the decision (a spy records order);
  one `BatchSubmitted` with both ids.
- **AC-6** - The same as AC-4 with a stored ceiling of `$0.05`: the submitter
  is **not** called, no `batch_job` row exists, and exactly two events are
  emitted, in this order: `CallPriced(ordinal=None, spent=chapter_total,
  ceiling=$0.05, projection=project_batch(3, page_estimate))` - the decision's
  three numbers, carried the way a per-page run's cost readout already reads
  them - then `RunAborted(reason=BUDGET, ordinal=None)` with `reason ==
  "budget"` **exactly**, the string the window's over-budget state matches
  (`ui/progress.py`). The ledger is unchanged and the return value is `()`.
- **AC-7** - With the submitter raising on its second call (job 2 of 2):
  job 1's row exists and is pending, no row exists for job 2,
  `RunAborted(reason, ordinal=None)` is emitted whose text names `job 2 of 2`
  and carries the exception's message, and the return value is the one id
  recorded. Nothing is retried.
- **AC-8** - With a pending job already covering any page of the volume
  (MT-137's `pending_jobs`), `submit_volume` calls the submitter zero times,
  consults no guard, and emits `RunAborted` naming the pending job's provider
  id; a pending job over pages the volume does not have does not block.
- **AC-9** - A page whose OCR has not run (no stored lines) makes
  `submit_volume` refuse before the guard and before any submit, with
  `RunAborted` naming the ordinal: a batch is built from finished OCR or not
  at all.
- **AC-10** - `compose` binds, for a Gemini selection, a submitter that turns
  `BatchPageInput`s into `BatchPage`s, builds the requests with
  `build_batch_requests` and submits them with `submit_batch(client, ...,
  display_name)` against the same `GeminiClient` the translator holds; a
  request-size function equal to `len(InlinedRequest.model_dump_json(
  exclude_none=True).encode())` of the page's built request; and
  `page_estimate(model_id, pricing="batch")`. For an Anthropic selection the
  binding is `None` (no batch).
