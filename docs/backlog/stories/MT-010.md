## Context

Open question **O6**, the other half. `docs/wiki/stack.md` §5/O6 and §5/O3.

Japanese bubble text runs vertically. The decision recorded in the stack
document is that this is handled by **model choice** — `manga-ocr` is trained on
manga crops in their native orientation and reads vertical columns directly —
and that the failure mode is a *helpful* pre-processing step: a deskew or a
rotate-to-horizontal that turns readable input into garbage. So the criteria
below are as much about what the pre-processing must **not** do as about what it
must do.

Read `docs/wiki/audits/MT-002-model-runtime.md`: its `## Decided` section
settles which OCR model and export are used. Its `## Evidence` numbers are to be
re-verified here, not assumed.

`required_gates: [integration]` is set for AC-6 and AC-7, which need the real
model. Everything else runs against a fake session.

**`depends_on` gained MT-035** in PLANNED (PO-4). MT-035 shipped `DetectStage`
and the injected-collaborator pattern this story's AC-9 follows; without it AC-9
would be inventing a second one.

## Acceptance criteria

- **AC-1** — Given a region and its page, when a crop is prepared, then the crop
  covers the region's polygon bounding box plus `CROP_PADDING_PX`, clipped to
  the page, with the region's orientation **unchanged** — no rotation, no
  deskew, no transpose.
- **AC-2** — Given a crop, when it is prepared for the model, then it is resized
  to the model's documented input size of 224×224 **as its own
  `preprocessor_config.json` specifies** — a `ViTImageProcessor` with
  `do_resize` and an explicit height and width, which does **not** preserve
  aspect ratio — and normalised with that config's `image_mean` and `image_std`.
  *Amended in RED; see `## Amendments` A-1. As filed this criterion required
  padding rather than stretching.*
- **AC-3** — Given a fake session returning a known token sequence, when decode
  post-processing runs, then it produces the expected Japanese string with the
  model's special tokens stripped, the half-width forms the audit measured
  normalised to full-width, and no trailing whitespace.
- **AC-4** — Given a fake session returning an empty sequence, when decode runs,
  then the region's text is the empty string and the region is flagged as
  `ocr_empty` rather than silently carrying `""` as if it were read.
  *Control:* a fake returning a sequence of **special tokens only** decodes to
  `""` and is **not** flagged `ocr_empty` — the flag means "the model emitted no
  tokens", and a flag that were merely `text == ""` restated would carry no
  information and could not fail.
- **AC-5** — Given a page's ordered regions, when OCR runs over them, then each
  region's text is stored against its own region id and the reading order from
  MT-009 is unchanged.
- **AC-6** — *(integration)* Given the real OCR model and a fixture crop of
  **vertical** Japanese, when it runs, then the transcription matches the
  hand-annotated ground truth by character-level accuracy of at least
  `OCR_MIN_ACCURACY`.
  *Control:* the **same crop rotated 90°** must score materially worse — below
  half that accuracy. If rotating the input does not hurt, the test is not
  measuring transcription of vertical text and AC-1's "do not rotate" rule is
  unverified.
- **AC-7** — *(integration)* Given a fixture crop whose main column carries
  furigana that MT-008 did not strip, when OCR runs, then the ruby characters do
  **not** appear in the transcription.
  *Control:* a crop of the ruby column **alone** must transcribe to the ruby
  characters — otherwise AC-7 passes because the model outputs nothing.
- **AC-8** — Given a fake decoder step that emits a known logit sequence, when
  greedy generation runs, then it stops at the first `EOS_TOKEN_ID` and returns
  the tokens before it; and given a decoder step that never emits EOS, it stops
  at `MAX_NEW_TOKENS` rather than running forever.
- **AC-9** — Given a page with stored regions and an injected transcriber, when
  `OcrStage.run` executes, then it writes one line per region positionally
  against `reading_index`, in one write at the end, and `is_done` reports true
  only when that page already has lines.
- **AC-10** — Given a project file written at schema version 1, when it is
  opened by this build, then it is migrated to version 2 in place, its existing
  rows survive, and `write_lines`/`read_lines` round-trip through it — including
  the `ocr_empty` flag.

### C-2 — `crop_for_region` must not rotate. Ever.

`manga-ocr` was trained on vertical crops; presenting it a rotated crop is
presenting out-of-distribution input. AC-6's control is the assertion that makes
this rule enforceable rather than a comment. AC-1 is assertable **without a
model**: the crop's pixel content equals the page's slice at the same
orientation, so a transpose or a flip is caught by `np.array_equal` against a
hand-built page.

### C-3 — ~~Padding, not stretching~~ → **Stretch, as the export specifies** (AC-2) — escalated in RED, **RESOLVED by amendment A-1**

*The block as filed said:*

> A vertical column has an extreme aspect ratio, and a naive `resize(w, h)` to
> the model's input destroys the glyphs. Pad to the model's aspect ratio with
> `PAD_VALUE`, then resize — the same shape as
> `detect.postprocess.letterbox`, which is the precedent to read rather than
> re-derive. AC-2's mechanical test pins the *shape and the pad*; only AC-6
> catches the consequence.

**RED measured it and it does not hold. Padding is catastrophically worse than
stretching, and the worst cases are precisely the extreme aspect ratios this
block was written to protect.**

Method: the real `manga-ocr` export against the upstream author's own
ground-truth set (`spikes/MT-002/oracle/`, 12 images with
`expected_results.json`), greedy decode, C-7's normalisation applied to both
sides, scored by exact match and by mean character accuracy — i.e. MT-002 E5
Test 1 re-run with the geometry as the only variable. `CUDAExecutionProvider`,
`onnxruntime-gpu 1.30.0`, 2026-09-16:

| Geometry | Exact | Mean char accuracy | Worst crop |
|---|---|---|---|
| **resize straight to 224x224 (stretch)** | **10 / 12** | **0.9743** | 0.737 |
| pad to square with 255 (white), centred | 4 / 12 | 0.5936 | 0.000 |
| pad to square with 114 (grey), centred | 5 / 12 | 0.7084 | 0.167 |
| pad to square with 0 (black), centred | 4 / 12 | 0.7183 | 0.391 |
| pad to square with 255, top-left aligned | 5 / 12 | 0.5784 | 0.000 |

The stretch row reproduces MT-002 E5's 10/12 exactly. Four padding variants
were tried so that "you padded wrong" is not an available explanation.

The two crops that fail *hardest* under padding are the two most extreme
columns in the set — `06.jpg` at 69x313 and `08.jpg` at 49x247, aspect ratios
of 4.5:1 and 5:1. Stretched, both transcribe **perfectly**
(`ピンポーーン`, `ファイアパンチ`). Padded, both come back as unrelated
Japanese (`もしかして、`, `2008年`). So the premise is not merely unsupported;
it is inverted at exactly the input it names.

**Why.** The encoder is `facebook/deit-base-patch16-224` and the export ships
`preprocessor_config.json` with `"size": {"height": 224, "width": 224}` and
`"do_resize": true` — a `ViTImageProcessor`, which resizes to the target
**without preserving aspect ratio**. `manga-ocr` was trained that way, and
upstream's own `_preprocess` does `img.convert("L").convert("RGB")` and then
that resize. A stretched vertical column is therefore *in distribution*, and a
padded one is not. This is C-2's own argument — do not "help" the model with
pre-processing it was not trained on — arriving at the opposite conclusion from
the one this block reached. `detect.postprocess.letterbox` is the right
precedent for the **detector**, whose graph is a square-input YOLO trained on
letterboxed pages; it is the wrong precedent here.

**AC-2 is an acceptance criterion and RED has NOT amended it.** Criteria are
frozen once a story leaves PLANNED (`rules.md`); this needs a product-owner
decision and an `## Amendments` entry. **Escalated to the orchestrator at the end
of RED.**

### RESOLVED — amendment A-1, approved by the user 2026-09-16

The escalation was upheld **on its conclusion and not on its evidence**. The
orchestrator reproduced independently, on different inputs and its own code, and
found RED's magnitude does not generalise: on the detector's own regions across

See `## Amendments` A-1 for the full table. What carried the decision is the
documentary half of RED's own finding, which both parties reached separately:
the export ships a `ViTImageProcessor` with an explicit height and width, which
does not preserve aspect ratio.

So, as of A-1: AC-2 pins the stretch, `PAD_VALUE` is out of C-1, and deferred

move**. RED's remaining task on this block is the geometry assertion AC-2 now

### C-4 — The generation loop is pure, and it is not in `session.py`

The `manga-ocr` export is **encoder + decoder, two graphs, no KV cache**, and
MT-002 E5 decoded it greedily. So `run(crop) -> Sequence[int]` — the signature
the story was filed with — hides an autoregressive loop with an EOS test and a
length cap. `detect/session.py`'s docstring states the rule this breaks: *"This
module owns no arithmetic … it is only ever exercised by the `integration` gate
… a letterbox or a decode written here would be a letterbox no required gate
reads."* `integration` is `optional` and never runs on CI.

Therefore `generate.greedy_generate` takes a **`DecoderStep` callable**, not an
`OcrSession`, so `tests/core` can drive it with a hand-built logit table and the
`unit` and `coverage` gates read it. `generate.py` must import nothing from
`ocr.session` — a `TYPE_CHECKING` import of the protocol would still be an
import-linter edge.

`MAX_NEW_TOKENS` is a **termination guarantee**, not tuning: E5 measured no
score exposed by this export and no "no text here" output, so a decoder that
loops is a hung run with no error.

### C-5 — `ocr_empty` means "the model emitted no tokens"

Not "the text is empty". The two differ and the difference is what makes the
flag testable: a sequence of special tokens only decodes to `""` and is a
*successful* read of nothing printable, while an empty sequence is the model
declining to emit. `__post_init__` enforces the one direction that must hold
(`ocr_empty` implies `text == ""`) and not the converse. A flag enforced in both
directions is `text == ""` spelled twice and AC-4's control could not fail.

It persists (PO-3) because `## Context`'s reason for it — *the review screen
shows them differently* — is a claim about a reopened project. In the store the
three states are then distinguishable: **no `line` row** (OCR has not run),
**row with `ocr_empty = 1`** (the model emitted nothing), **row with
`source_ja` set** (read).

### C-6 — `CROP_PADDING_PX` is a pixel count and scales with scan resolution

Record the page width it was measured at, as `detect.columns.COLUMN_MAX_GAP_PX`
does — *"in page pixels at a scan width of 1125"* — and record in `## Notes`
that the corpus is single-resolution, rather than silently implying generality.

### C-7 — `decode` performs the half-width→full-width normalisation

MT-002 E5 is explicit: without `jaconv.h2z(ascii=True, digit=True)` and
`…`→`...`, the upstream ground-truth score is **6/12**; with it, **10/12**. All
four recovered files differed *only* in half-width vs full-width punctuation and
digits (`!!!` vs `！！！`, `?` vs `？`). The audit says the step "is required".
Omitting it makes `OCR_MIN_ACCURACY` absorb a known, fixable 33-point defect,
which is how a threshold stops being a threshold.

`jaconv` is a small pure-Python dependency and is the measured thing; a
hand-rolled codepoint offset is acceptable only if it is proved equivalent over
the ASCII and digit ranges in a test. GREEN adds whichever it uses to
`pyproject.toml` with the audit cited, as MT-007 did for the ONNX lines.

### C-8 — `OCR_MIN_ACCURACY` is not settled here

Character-level accuracy, 1 − normalised Levenshtein distance against the
annotation. **GREEN measures it** on the fixture set and records the
measurement, the fixture count, and the rotated-control figure in `## Notes`. A
threshold set to whatever the implementation scored is not a threshold — set it
below the measured value with stated headroom, and say how much.

Baselines RED may **read out rather than re-derive**, all from MT-002 `## Decided`
and E5:

| Quantity | Value | Where |
|---|---|---|
| Encoder / decoder / vocab SHA-256 and sizes | see the table | `## Decided` |
| Upstream ground truth, post-processed | 10 / 12 exact | E5 Test 1 |
| Real page `014.jpg`, detector boxes | 9 / 9 plausible | E5 Test 2 |
| Furigana case | box 02, 醜鬼 with ruby しゅうき, ruby dropped | E5 Test 2 |
| Mean OCR latency on CUDA | 26.7 ms/crop | E5 |
| Model hallucinates on text-free crops | `それは、` on white margin | E5 Test 3 |

That last row is a standing constraint, not trivia: **OCR cannot be used to
decide whether a region contains text.** Nothing in this story may add a
confidence threshold or a "no text here" branch on the model's output.

### C-9 — Fixtures come from the detector's own boxes (PO-5)

`fixtures/ocr/` does not exist and the crops are not redistributable. Derive
them at test time by running the real detector over
`spikes/MT-002/pages/014.jpg` and cropping its own boxes — reproducible, and it
avoids the trap E5 documented in its own method note: *"my rectangles had
clipped the text, not that the model failed … a bad crop is indistinguishable
from a bad model unless you look at the crop."*

The **ruby-alone control of AC-7 is the exception**: MT-008 measured that the
detector's dilation absorbs ruby columns, so no box isolates one. That crop is a
hand-picked rectangle, and its coordinates are transcribed into the test file as
constants with the page and scan size named, the way `_SFX_012` is in
`tests/integration/test_detector_session.py`.

Ground-truth strings are committed (they are text, not scans). The crops skip
cleanly without `spikes/**`, as every test in that directory already does.

### 0. READ THIS FIRST: AC-2 was amended mid-RED, and what its test does *not* prove

AC-2 was escalated during RED and **amended by A-1, approved by the user**. It
now specifies the resize the export's own `preprocessor_config.json` performs — a
`ViTImageProcessor` with `do_resize` and an explicit height *and* width, which

The geometry is pinned by
`test_a_twenty_by_four_hundred_column_is_stretched_to_fill_the_whole_input`.
Shape and dtype are identical under both geometries, so the discriminator is the
**absence of a constant-valued border** plus the four corners carrying the
crop's own corners. Verified outside pytest before the test was written, since
`mangatl.ocr.preprocess` does not exist:

| Candidate implementation | Border runs (top/bottom/left/right) | Corner misses | Verdict |
|---|---|---|---|
| stretch, PIL `BILINEAR` | 0 / 0 / 0 / 0 | none | **passes** |
| stretch, `cv2.INTER_LINEAR` | 0 / 0 / 0 / 0 | none | **passes** |
| stretch, `cv2.INTER_AREA` | 0 / 0 / 0 / 0 | none | **passes** |
| pad to square, 255, centred | 0 / 0 / **106** / **107** | 3 of 4 | fails |
| pad to square, 114, centred | 0 / 0 / **106** / **107** | 4 of 4 | fails |
| pad to square, 0, centred | 0 / 0 / **106** / **107** | 3 of 4 | fails |
| pad to square, 255, top-left | 0 / 0 / 0 / **213** | 1 of 4 | fails |

All three plausible stretch implementations return corners exact to four decimal
places, so the 0.10 tolerance is slack rather than load-bearing. The top-left
aligned pad is why the border check is a four-way dict and not "the first column
is not constant": it is the case that would slip past a one-sided check.

**What this test is NOT evidence of, and GREEN must not report it as such.** It
pins the geometry against the **export's shipped configuration**, which is what
A-1 decided on. It is *not* evidence that stretching transcribes this corpus
better. The orchestrator's independent reproduction measured **34 of 37** real
pipeline regions transcribing byte-identically under both geometries, and found
RED's stated mechanism ("padding breaks at extreme aspect ratio") failing at
ratios of 4.73 and 6.30 — above the upstream crops RED cited. RED's result holds
on tight crops and does not generalise to what MT-008's column merging actually
produces (corpus median ratio 1.74, only 3 of 37 at or above 4.0).

Consequence for GATES: **deferred verification 2 is inverted and may legitimately
not move.** The block says so. Record both numbers either way, and if they are
