## Context

**Filed 2026-11-04 by the Lead PO (Claude Fable 5.1)**, from
[[MT-112]] `## Notes` **PO-5** ("the `unit` gate's Qt abort: cause not
found", commit `b1257b0` on `story/MT-112-collecting-a-finished-batch-into-the-sto`,
`docs/backlog/stories/MT-112.md` from line ~655). PO-5 is the record of the
incident and is not restated here; what this story needs from it:

- The `unit` gate (`uv run pytest -q tests/core tests/ui`,
  `.claude/harness/project.conf`) aborted the whole process three times on
  2026-11-04 on the Windows host: `Fatal Python error: Aborted`, exit code 3,
  no Qt and no Windows message. The aborts were at tests ~3357, ~3409 and
  ~3437, all inside one 108-test window (`tests/ui/test_canvas_high_contrast.py`
  then `tests/ui/test_canvas_keys.py`); the faulthandler stacks were
  `pytestqt/qtbot.py:861 __exit__` from `test_canvas_high_contrast.py:367
  _show` and `pytestqt/plugin.py:220 _process_events` during setup.
- Subsets passed meanwhile (`tests/ui` alone 2059; core+ui subsets 2149 and
  2122; a clean `origin/main` checkout 5030, one run), then 4/4 full runs and
  20/20 loops of the three canvas files passed on unchanged code. No handle,
  thread or memory growth per test. The machine was at **97 % physical memory
  in use** with the working set being trimmed mid-run - PO-5 calls that
  context, not a cause. The user found no Windows Event ID 1000 record; the
  newest is from 2026-10-31. A later full `gates.sh` passed and was recorded,
  not waived. MT-112 is open as PR #143.
- PO-5's recurrence recipe is a manual re-run, `uv run pytest -q -s -o
  qt_log=false tests/core tests/ui`, to let a Qt fatal message print. **This
  story's mechanism is meant to make that re-run unnecessary: the first abort
  already prints what Qt said, and its log is kept.**

**What this story measured before it was cut (2026-11-04, this host: Windows
11, CPython 3.13.15, PySide6/Qt 6.9.3, pytest 8.4.2, pytest-qt 4.5.0; the
runs and outputs are in `## Notes` PO-1).** Two findings bound the scope:

1. **Today a `qFatal` inside the suite prints nothing and keeps nothing.** A
   probe test calling `QtCore.qCritical(...)` then `QtCore.qFatal(...)`, run
   under `uv run pytest -q <probe>` with output redirected as `gates.sh` does
   (`2>&1 | tee`), produced **empty output and exit code 127**, in every
   configuration tried: pytest-qt capture on (the gate's), `--no-qt-log`,
   `-s`, `--no-qt-log` with `QT_FORCE_STDERR_LOGGING=1`, and PO-5's recipe.
   Two reasons, both read from the code: pytest-qt's capture handler
   (`pytestqt/logging.py`, `_QtMessageCapture._handle_with_context`) stores
   the message in a per-test list and **does not forward it to any other
   handler**, and the list is only ever printed in a test's failure report,
   which an aborting process never writes; and outside that capture Qt's
   default handler on Windows writes to the debugger, not to a redirected
   stderr (a plain `python -c` `qCritical` printed nothing until
   `QT_FORCE_STDERR_LOGGING=1` was set). PO-5's recipe does not reach the
   second reason. And `-o qt_log=false` sets an ini key pytest-qt does not
   read (its switch is the command-line option `--no-qt-log`).
2. **A `qFatal` does not produce the signature that was observed.** On this
   host Qt 6.9.3's `qFatal` ends the process with **exit code 127 and no
   SIGABRT** - faulthandler, enabled, printed nothing. `os.abort()` - the C
   runtime's `abort()` - produces **exactly** the observed signature: `Fatal
   Python error: Aborted`, a `Current thread` stack, exit code 3. So the
   three aborts were an `abort()` reached from C or C++ (a `std::terminate`
   from an uncaught C++ exception is one caller of `abort()`; there are
   others), **not** a Qt fatal message swallowed by `qt_log`. Which caller it
   was is not shown by anything we have, and this story does not guess.

So the story does two small things, both diagnostic, neither a fix:

- **Qt's last words reach the gate log.** `tests/conftest.py` tees every
  `QtFatalMsg` and `QtCriticalMsg` to the process's real stderr - the one
  `gates.sh` is reading - as it happens, unbuffered, naming the test it
  happened in, while pytest-qt's own capture and reports stay exactly as they
  are. A future `qFatal` is then explained by its own message, and a
  `qCritical` that precedes an `abort()` is on record. Warnings are not teed
  (PO-2).
- **The log of an abort is kept.** `keep-when` lines (MT-053's mechanism:
  `.claude/harness/project.conf`, the `# Format:  keep-when` block) for the
  observed line, `Fatal Python error`, and for the tee's fatal line, on the
  four gates that run pytest over Qt code. `Fatal Python error` is
  faulthandler's prefix for every fatal signal it reports, so the signature
  also covers a segmentation fault; the three aborts of 2026-11-04 left no
  kept log precisely because the only signatures were MT-053's two.

**Which required gate would fail if this story's artifact broke?** `unit`
and `coverage` (both required) run `tests/ui`, where the story's test runs
the probes in a child pytest and reads the real output; a tee that stops
writing fails AC-1 there (DV-1). The `keep-when` lines are read by
`gates.sh` alone, which no required gate judges (MT-053 PO-3); their pin is
AC-4's test over the shipped file, probed against the real line in DV-2.

**Type and phase path - the user's decision (PO-3).** Every file this story
writes classifies as `test` (`tests/conftest.py`, the test module, the
probes: `bash scripts/classify.sh`), `harness` (`project.conf`) or `docs`.
There is no `source` or `config` path, so the RED/GREEN split has nothing
for GREEN to write: the mechanism lives in a `test`-classified file that
GREEN freezes. It is cut as a `chore` under **SCAFFOLD**, where the Lead PO

### The tee (`tests/conftest.py`)

Module-level, beside the existing docstring and `appdata` fixture; one
docstring paragraph cites this story and MT-112 PO-5.

- `_LAST_WORDS_FD: int | None = None`. Set in `pytest_configure(config)` to
  `os.dup(sys.stderr.fileno())` (falling back to `sys.__stderr__.fileno()`
  if `sys.stderr` has no fd) - the same move `_pytest/faulthandler.py` makes
  in its own `pytest_configure`, and for the same reason: at configure time
  pytest's capture is not active, so fd 2 is the process's real stderr, the
  one `gates.sh`'s `2>&1 | tee` reads; during a test fd 2 is redirected into
  a capture file that an aborting process never reports. Closed in
  `pytest_unconfigure`. That faulthandler's stacks reached the terminal in
  MT-112 PO-5 is the evidence this route works.
- `_CURRENT_NODEID: str | None`. Set by `pytest_runtest_logstart(nodeid,
  location)`, cleared by `pytest_runtest_logfinish`. Outside those, the tee
  line says `no test`.
- `_tee(msg_type, context, message) -> None`. `QtMsgType.QtFatalMsg` ->
  `FATAL`, `QtMsgType.QtCriticalMsg` -> `CRITICAL`; every other type returns
  without writing (PO-2). Writes **one** `os.write(_LAST_WORDS_FD, line)`
  with the line encoded UTF-8, `errors="replace"`, newline-terminated;
  unbuffered and a single syscall, so it is on disk before the `abort()` or
  `exit` that follows a `qFatal`. Never raises: `OSError` and a `None` fd
  are swallowed, because an exception inside a Qt message handler is
  undefined behaviour and this handler runs inside the thing being
  diagnosed. `message` is written as Qt hands it; `context` is not written
  (for a message from Python it carries nothing useful - measured, PO-1 run
  7: the default handler prints `[A qFatal() call was made from Python
  code]`).
- **Installation, two layers, both needed:**
  1. `pytest_configure`: `QtCore.qInstallMessageHandler(_tee)`. Holds the
     handler slot whenever pytest-qt's capture is not installed: collection,
     session fixtures, the gaps between tests. Qt's default handler is
     replaced there; on this host it was writing to the debugger, not to a
     redirected stderr (PO-1 run 6), so nothing that reached a log is lost.
  2. A class-level wrap of `pytestqt.logging._QtMessageCapture._handle_with_context`
     (pytest-qt **4.5.0**, pinned in `uv.lock`): the replacement calls `_tee`
     and then the original, so `records`, `qtlog`, `qt_log_level_fail`,
     `qt_log_ignore` and the `Captured Qt messages` report are unchanged
     (AC-3). Why not layer 1 alone: pytest-qt's `_start()` installs its own
     bound method for the span setup -> teardown of every test and its
     `_handle_with_context` **does not call the previous handler** (read in
     4.5.0), so a handler installed before it is bypassed for exactly the
     span in which every observed abort happened. The private name is pinned
     by the lock file; the conftest asserts the attribute exists at import,
     so a pytest-qt bump that renames it fails the whole run loudly rather
     than silently losing the tee.
- `pytest-qt` registers its logging plugin only when capture is on
  (`config.getoption("qt_log") and config.getoption("capture") != "no"`);
  under `-s` or `--no-qt-log` layer 2 is inert and layer 1 carries the tee.
  No AC pins those modes.

### The tee line

Exactly:

```
qt-message: <LEVEL> in <where>: <message>
```

`<LEVEL>` is `FATAL` or `CRITICAL`. `<where>` is pytest's nodeid of the
running test (forward slashes, relative to rootdir, e.g.
`tests/ui/__probe_qt_fatal.py::test_qfatal`) or the two words `no test`.
`<message>` is Qt's message text, one line as Qt gives it (a message with
embedded newlines is written as-is; none of the probes has one). The
`keep-when` regex for the fatal case is the literal `qt-message: FATAL` -
there is no ERE metacharacter in it, and `re.search` and `grep -E` agree on
it (AC-4).
