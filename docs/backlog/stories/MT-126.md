## Context

EPIC-01. Three tests in two files prove that parallel cv2 survives a process
whose default Windows thread pool has lost its I/O completion port (audit
`docs/wiki/audits/MT-068-cv2-parallel-failure.md`, Decided 1 and 3; the tests
are MT-069's and MT-071's, and the containment they pin is
`cv2.setNumThreads(-1)` beside every `import cv2` in `src/mangatl`):

- `tests/core/test_cv2_lost_completion_port.py` - `..._on_the_main_thread_survive_a_closed_completion_port` (AC-1 of MT-069) and `..._on_a_thread_started_after_the_port_closed_survive` (AC-2 of MT-069)
- `tests/core/test_cv2_lost_completion_port_inpaint.py` - `test_clean_page_in_an_inpaint_only_process_survives_a_closed_completion_port` (MT-071)

Each spawns a *clean* and an *induced* fresh `sys.executable -c` child side by
side. The induced child walks handle values `4..0x8000`, asks `NtQueryObject`
for each one's type, and closes the **lowest-valued `IoCompletion` handle**
(audit recipe A, E5). After the production calls, each child runs a **vacuity
canary** on a fresh thread - `CreateThreadpoolWait` + `SetThreadpoolWait`, the
call ConcRT's attach makes - and the parent fails the test as `VACUOUS` when
the induced child's canary *succeeds*, because then the port was never lost and
"induced == clean" proves nothing (MT-069 C-4 as amended in RED).

**The defect this story removes.** That `VACUOUS` failure fires without any
change to the code under test, in roughly one full gate run in ten, and every
time it has cost a full ~20-minute rerun. The record, from the story files
(`grep -n VACUOUS docs/backlog/stories/*.md`):

| Where | Gate | Test | Alone afterwards |
|---|---|---|---|
| MT-053 PO-19, 2026-10-15, local | `coverage-core` (`--fast`) | main-thread | rerun green |
| MT-053 PO-22, **CI windows-latest** | `coverage`; `unit` passed in the same job | inpaint | - |
| MT-077, local, twice | `unit`; not in `coverage` of the same run | inpaint | `1 passed` |
| MT-075 PO-5, local | `unit`; `coverage` passed in the same run | main-thread | 5/5 green |
| MT-083 RED, local | plain `pytest tests/core` over a mutated tree | main-thread | 3/3 green |
| MT-084, local | `coverage`; `unit` passed in the same run | thread-started-after | rerun green |
| MT-089, local | `unit` | thread-started-after | rerun green |
| MT-119 PO-R5, MT-124 PO-4, local | one gate of a full `gates.sh` | (reported by the dispatcher; the pasted text was not found in this worktree's copies of either story - see `## Notes`) | rerun green |

What the record shows, and only that: all three tests are affected; it
happens under coverage instrumentation and without it, locally and on CI; it
has never been seen when the file runs alone (13/13 solo runs green across
MT-075, MT-077, MT-083), and only ever in a run of the whole `tests/core` or
`tests/core tests/ui` suite. Every story that met it recorded **cause not
established**, and nothing in the failure output could establish it: the
assertion message is one sentence and discards the induced child's report, so
nobody knows which handle value the vacuous child closed, whether `CloseHandle`
returned true, or how many `IoCompletion` handles the child had.

**Cause not yet known.** One hypothesis is consistent with the evidence and is
*not* asserted here: the audit saw 3 `IoCompletion` handles in a fresh
interpreter and inferred (E5, `[INFERRED]`) that the lowest-valued one is the
default pool's port; it also saw the port at `0x24` or `0x28` in some probe
processes (audit, "What else could explain it"). If handle values are ever
allocated in a different order - under the load of a parent that has run four
thousand tests, with another child starting beside it - the lowest `IoCompletion`
could be some other object's, the close would succeed, the pool would be
intact, and the canary would succeed: exactly the observed signature. The story
does not depend on this being right. It makes the failure carry the evidence
that would confirm or refute it, and it stops one non-taking induction from
costing a gate run.

**The decision: option (a), a bounded re-spawn, plus diagnostics - not a
skip, not an in-process retry.** The governing criterion is that the test
stays meaningful:

- A `pytest.skip` (option b) would hide a real regression: a `skip` in a
  4,000-test gate log is a line nobody reads, and a canary that stopped firing
  for a *systematic* reason (a Windows update that changed handle allocation, a
  child that no longer closes anything) would turn every one of these tests
  into a permanent skip with the gates green. Rejected.
- A retry **inside one child** (close the next `IoCompletion` handle and
  canary again) runs the production calls in a process that has already closed
  a handle it did not own; the audit's E5 shows closing other handles leaves
  cv2 working but says nothing about what else breaks, and MT-068 PO-7 fixes
  the discipline that nothing of the test's own runs after the close. A
  partially-induced process is not a process whose result can be compared to
  the clean one. Rejected.
- A **fresh induced child per attempt**, at most 3 attempts, retried **only
  when the induced child's canary succeeded** - never when it raised, never
  when a production call raised - keeps every property the tests have today:
  each child is a clean derivation (inputs before the close, no RNG after),
  the clean reference runs once, a real `cv2.error` fails on the first
  attempt exactly as now, and the canary stays binding. If every attempt is
  vacuous the test fails as it does today, louder: the message names each
  attempt's closed handle, `CloseHandle` result and the full list of
  `IoCompletion` handle values it found. If a later attempt takes, the test
  passes and emits one **pytest warning** carrying the same facts for the
  vacuous attempts, so the gate log keeps a take-rate record without anyone
  running anything. With the observed per-run rate p ~ 0.1 per *full run* -
  far lower per child - three independent children put a false `VACUOUS`
  below p^3.
- Option (c), fixing the mechanism: nothing in the evidence identifies the
  mechanism, and inventing one would be the failure `rules.md` names. The
  diagnostics above are the measurement that lets a later story do (c) on
  evidence; `## Deferred verifications` DV-2 records the take-rate this story
  can measure.

**Why `fix`, and what the phase lock means for it.** The defect is in a
test's own precondition handling, and the criteria reproduce it (AC-2, AC-4),
so the type is `fix`. Everything it writes is under `tests/`, which is
category `test` - writable in RED, frozen in GREEN and GATES. So RED is the
whole of the work and **GREEN is expected to be a verified no-op**, exactly as
MT-083 (tests only) ran: the orchestrator checks `git diff --stat HEAD --
src/` is empty and dispatches no feature-developer. A real RED exists: the
retry helper is a new module, its tests are written first and fail at import,
and because that failure runs no assertion, each assertion is then **earned
by a mutation of the helper** with `scripts/mutate.sh` inside RED (the law's
second case, `rules.md` "Non-negotiables"), with the output in `## Handoff`.

Required gates that fail if this breaks: `unit`, `coverage`, `coverage-core`
all run `tests/core`, so all three collect the helper's tests and the three
changed tests (Windows only; `skipif` elsewhere, as today).

## Acceptance criteria

The retry policy is a pure function over child *reports* (the JSON dict each
child already prints), so it is tested with a fake spawner and no subprocess.
AC-1 to AC-3 are about the helper; AC-4 and AC-5 are about the two test files
using it.

- **AC-1** - Given a spawner whose first `k` reports (0 <= k < 3) have
  `canary.ok == True` and whose next report has `canary.ok == False` with
  `winerror == 0xC000070A`, when the induction is run with 3 attempts, then
  the result is that last report, the spawner was called exactly `k + 1`
  times, and the result's list of attempts holds all `k + 1` reports in order.
  For `k == 0` the spawner is called exactly once (a taking induction costs
  nothing extra).

- **AC-2** - Given a spawner whose every report has `canary.ok == True`, when
  the induction is run with 3 attempts, then the spawner was called exactly 3
  times, the result says the induction did not take, and its message (a) starts
  with `VACUOUS:`, (b) says `3 attempts`, and (c) for *each* attempt names
  the attempt number, the `closed_handle` as hex, the `close_ok` value and the
  `io_completion_handles` list as hex. *Control:* the spawner raises if called
  a 4th time, so a helper with the bound removed fails this test rather than
  hanging.

- **AC-3** - A report is never retried unless its canary *succeeded*. Given a
  spawner whose first report has `canary.ok == False` and (i) `winerror ==
  0xC000070A` with a production call failed (`ok: False`), or (ii) a
  `winerror` that is not `0xC000070A`, or (iii) `close_ok == False`, when the
  induction is run, then the spawner was called exactly once and that report
  is returned unchanged - the test's own checks then fail on it as they do
  today. A real regression is never retried away.

- **AC-4** - Given `tests/core/test_cv2_lost_completion_port.py` and
  `tests/core/test_cv2_lost_completion_port_inpaint.py` with the induced
  child's close made impossible (the type-name needle `"IoCompletion"` mutated
  so no handle matches), when each test runs, then it **fails**, its failure
  message contains `VACUOUS:` and `3 attempts`, and names three attempts each
  with its `io_completion_handles` list - that is, the induced child was
  spawned three times and the clean child once. (Observed through DV-1 with
  `scripts/mutate.sh`; it cannot run inside the suite, since the suite cannot
  make its own induction fail on demand - see `## Notes`.)

- **AC-5** - Given a run in which the first induced attempt was vacuous and a
  later one took, when the test passes, then it emits exactly one
  `InductionRetried` warning (a `UserWarning` subclass exported by the helper)
  whose text names each vacuous attempt as AC-2's message does; a run whose
  first attempt took emits no warning. Tested at the helper level with the
  fake spawner (`pytest.warns`, and `warnings.catch_warnings` with
  `simplefilter("error")` for the no-warning case).

- **AC-6** - Each induced child's report carries `io_completion_handles`: the
  ascending list of every handle value in `4..0x8000` whose type is
  `IoCompletion`, found by the same walk that chooses the one to close, and
  `closed_handle` is its first element. The clean child reports the same list
  (it walks, closes nothing). Pinned by reading the reports back in the existing
  tests: a non-empty list in both children, and `closed_handle ==
  io_completion_handles[0]` in the induced one.

## Contract

**Writes:** `tests/core/_lost_port.py`, `tests/core/test_lost_port_induction.py`, `tests/core/test_cv2_lost_completion_port.py`, `tests/core/test_cv2_lost_completion_port_inpaint.py`

Every path is category `test`. No source, config or manifest file is written.
No new dependency: `warnings`, `dataclasses` and `pytest.warns` are enough.

**C-1. The helper,** `tests/core/_lost_port.py` (leading underscore, the house
style of the other shared test modules in `tests/core/`; pytest does not
collect it). Exports exactly:

```python
INDUCTION_ATTEMPTS: int = 3
THREADPOOL_HANDLE_EXCEPTION: int = 0xC000070A   # the two test files may read it from here or keep their own

class InductionRetried(UserWarning): ...

@dataclass(frozen=True)
class Induction:
    report: dict[str, Any]              # the last report spawned
    attempts: tuple[dict[str, Any], ...]  # every report, in order; attempts[-1] is report
    @property
    def took(self) -> bool: ...          # report["canary"]["ok"] is not True
    def vacuous_message(self) -> str: ...  # AC-2 (a)-(c); defined for any Induction

def run_induced(spawn: Callable[[int], dict[str, Any]], attempts: int = INDUCTION_ATTEMPTS) -> Induction: ...
def warn_if_retried(induction: Induction) -> None: ...
```

Semantics behind each number and rule:

- `attempts` is the **maximum number of induced children spawned**, 3 by
  default. The one controlled measurement is that solo runs take 13/13 and
  full runs fail about 1 in 10; three fresh children is the smallest bound
  that puts a false `VACUOUS` far below the single-run rate without hiding a
  systematic failure (three vacuous children in a row is reported, loudly).
  `attempts < 1` raises `ValueError`.
- `spawn(n)` is called with the 1-based attempt number, so the caller can name
  files per attempt; it returns the induced child's report dict. **The helper
  calls it again only when the report's `canary["ok"] is True`.** Any other
  report - canary raised with the right or wrong `winerror`, close failed, a
  production call failed - is returned after that one call (AC-3). The helper
  never inspects production-call fields; the test files keep every check they
  have today.
- `vacuous_message()` is one string whose first line is `VACUOUS: the canary
  SetThreadpoolWait on a fresh thread succeeded in the induced child in N of N
  attempts, so the default thread pool's completion port was never lost`
  (keep the existing needle `VACUOUS: the canary SetThreadpoolWait on a fresh
  thread succeeded in the induced child`, which the record above greps for),
  followed by one line per attempt: `attempt i/N: closed 0x20 (close_ok True),
  IoCompletion handles [0x20, 0x44, 0x5c]`. Hex is `f"{v:#x}"`; a `None`
  handle prints `none`; a missing `io_completion_handles` key prints
  `unreported` rather than raising, so an old-shaped report still produces a
  message.
- `warn_if_retried(induction)` does nothing when `len(attempts) == 1`;
  otherwise it issues exactly one `InductionRetried` whose message is the
  per-attempt lines for the vacuous attempts, prefixed `MT-126: the lost-port
  induction took on attempt k/N;`. `warnings.warn(..., stacklevel=2)`. The
  test files call it after the induction and before their checks, so the
  warning is emitted whether the test then passes or fails. `pyproject.toml`
  has no `filterwarnings`, so pytest prints it in the warnings summary of a
  `-q` run - that summary line in a gate log is the take-rate record.

**C-2. The helper's tests,** `tests/core/test_lost_port_induction.py`. Fake
spawner: a closure over a list of scripted reports that records its calls and
raises `AssertionError("spawned more than scripted")` when the list is
exhausted (AC-2's control). Reports are minimal dicts with the keys the helper
reads (`canary`, `closed_handle`, `close_ok`, `io_completion_handles`) plus
whatever AC-3 needs (`calls`/`call`). No `skipif`: the helper is pure Python
and these tests run on every platform. This file is the only one that would
exist before the helper, so it is the one that fails at import; see C-5.

**C-3. The two test files.** The minimal change, and nothing else moves:

- The child script (both files) gathers `io_completion_handles` in its handle
  walk and reports it (AC-6). The **clean** child performs the walk too and
  reports the list; it closes nothing. The walk is the same `NtQueryObject`
  loop already there, so the clean child gains ~tens of ms, not a new
  mechanism. Each child report gains one key; no key is removed or renamed.
- The parent runs the clean child and the first induced child side by side
  exactly as today, then hands the induced report to `run_induced` with a
  `spawn` that, for attempt `n >= 2`, starts **one** fresh induced child alone
  with the same argv (its `.npz` written to `induced-{where}-{n}.npz` or
  `induced-{n}.npz`, and the comparison reads the *last* attempt's file).
  Attempt 1 is the report already in hand - `spawn(1)` returns it without
  spawning again, so the side-by-side structure and the clean-reference
  timing are unchanged in the common case.
- The `VACUOUS` check becomes `if not induction.took: problems.append(induction.vacuous_message())`, followed by `warn_if_retried(induction)` before it. The `elif canary["winerror"] != ...` check, the close check, the production-call checks and the array comparisons stay word for word.
- Docstrings: one paragraph added to each module docstring saying the
  induction is retried on a fresh child up to `INDUCTION_ATTEMPTS` times and
  why, citing this story. `_CHILD_TIMEOUT_S` is per child and unchanged; three
  attempts are bounded by 3 x 60 s.
- MT-071's "re-derive, do not import from MT-069's file" rule is about the
  *child script* and the evidence each file carries on its own; a shared retry
  policy does not weaken that, and the two files still share no child code.

**C-4. Oracle partition.**

- *Mechanical* (pin exactly): AC-1, AC-2, AC-3, AC-5 - call counts, the
  returned object, the message's needles, one warning.
- *Settled* (read out, do not re-derive): the needle string `VACUOUS: the
  canary SetThreadpoolWait on a fresh thread succeeded in the induced child`;
  `0xC000070A`; `INDUCTION_ATTEMPTS = 3`; the audit's handle facts (3
  `IoCompletion` handles in a fresh interpreter, the port at `0x20` in every
  gate-shaped process observed, `0x24`/`0x28` in a few probes).
- *Oracle-free*: none. The take-rate is a measurement (DV-2), not a criterion;
  the story deliberately sets no threshold on it because the record cannot
  support one.

**C-5. What RED must earn, and how.** `test_lost_port_induction.py` fails at
import until `_lost_port.py` exists, which runs no assertion. RED writes the
helper in the same phase (it is a test path) and then earns each test with
`bash scripts/mutate.sh tests/core/_lost_port.py '<expr>' -- uv run pytest -q
tests/core/test_lost_port_induction.py`, one mutation per claim, output pasted
