## Context

*Cut 2026-11-03 by lead-po (Claude Fable 5.1) out of MT-111, under MT-111
PO-1 (the user's decision): a volume is submitted as **several** inline
Gemini jobs, because 200 capped pages are ~24 MB of base64 against the
Batch API's 20 MB inline limit (MT-101 D-9).*

MT-103's `batch_job` table was built for one job per volume: `record_submission`
refuses while **any** job is pending, and a row does not say which pages it
holds, because "all of them" was the answer. Neither survives the split.
MT-112 has to collect job 2 of 3 into exactly its pages, and MT-111 has to
record three pending rows for one run. So:

- a `batch_job` row carries `first_ordinal` and `last_ordinal` - the
  consecutive run of pages it holds (MT-111 splits a volume into consecutive
  runs, so a range is the whole truth and no join table is needed);
- "at most one pending job" becomes "**no two pending jobs share a page**":
  `record_submission` refuses a range that overlaps a pending row and accepts
  one that does not, so the double bill MT-103 guarded against is still
  impossible while a volume's several jobs can all be in flight;
- `pending_job` (one or none) becomes `pending_jobs` (every pending row, in
  page order), because a resume collects each of them.

Schema v11, one migration, same discipline as v10: the table is rebuilt from
the fresh DDL so `sqlite_master.sql` agrees between a fresh file and a
migrated one, and the one pre-v11 row shape - a job that could only ever have
held the whole chapter - is copied as `0 .. page_count - 1`.

Required gates: `unit`, `coverage`, `coverage-core` (`domain/batch.py` is
under its 100 % floor; `store/` is under `coverage`).

## Acceptance criteria

- **AC-1** - `SCHEMA_VERSION == 11`; a fresh project's `batch_job` has the
  columns `id, run_id, provider_job_id, model_id, state, submitted_at,
  collected_at, failure, first_ordinal, last_ordinal`, the last two `INTEGER
  NOT NULL` with `CHECK (first_ordinal >= 0 AND first_ordinal <=
  last_ordinal)`; a fresh file and a v10 file migrated to 11 store the same
  `sqlite_master.sql` for `batch_job` (whitespace collapsed), and the v11 step
  changes no object outside `batch_job`.
- **AC-2** - A v10 file holding one `submitted` job over a 4-page chapter
  opens, reads `user_version` 11, and that job reads back with
  `first_ordinal 0, last_ordinal 3`, every other column unchanged.
- **AC-3** - `record_submission(project, run_id, provider_job_id, model_id,
  first_ordinal, last_ordinal)` returns the new row's id and
  `pending_jobs(project)` reads it back as a `BatchJob` carrying both
  ordinals; `BatchJob.ordinals` is `range(first_ordinal, last_ordinal + 1)`.
- **AC-4** - Two submissions with disjoint ranges (`0..1` then `2..2`) both
  succeed; `pending_jobs` returns both, ordered by `first_ordinal` regardless
  of insertion order, and an empty tuple on a project with no jobs.
- **AC-5** - A submission whose range shares **any** page with a pending row
  (`1..1` against pending `0..1`; `2..3` against pending `0..2`; `0..5`
  around pending `2..2`) raises `BatchPending` naming the pending job's id and
  provider id and writes no row; after `mark_collected` (or `mark_failed`)
  of the pending row the same range is accepted.
- **AC-6** - `record_submission` with `first_ordinal > last_ordinal` or
  `first_ordinal < 0` raises `ValueError` naming both numbers before any
  write - a `ValueError`, not the CHECK's `IntegrityError`.
- **AC-7** - `pending_job` no longer exists: `store.batch.__all__` is exactly
  `["BatchPending", "mark_collected", "mark_failed", "pending_jobs",
  "record_submission"]`; `mark_collected` / `mark_failed` still touch only
  their own row (MT-103's tests, re-pointed).

```sql
-- schema.py: BATCH_JOB_DDL becomes the v11 shape (one definition, shared by the
-- fresh DDL and the migration, as v10 did):
CREATE TABLE batch_job (
    id              INTEGER PRIMARY KEY,
    run_id          INTEGER NOT NULL REFERENCES run(id),
    provider_job_id TEXT    NOT NULL,
    model_id        TEXT    NOT NULL,
    state           TEXT    NOT NULL CHECK (state IN ('submitted', 'collected', 'failed')),
    submitted_at    TEXT    NOT NULL,
    collected_at    TEXT,
    failure         TEXT,
    first_ordinal   INTEGER NOT NULL,
    last_ordinal    INTEGER NOT NULL,
    CHECK (first_ordinal >= 0 AND first_ordinal <= last_ordinal)
);

-- project.py: SCHEMA_VERSION = 11; _MIGRATE_TO_V11 appended to _MIGRATIONS as (11, _MIGRATE_TO_V11):
ALTER TABLE batch_job RENAME TO batch_job_v10;
<BATCH_JOB_DDL>
INSERT INTO batch_job (id, run_id, provider_job_id, model_id, state, submitted_at, collected_at, failure,
                       first_ordinal, last_ordinal)
SELECT id, run_id, provider_job_id, model_id, state, submitted_at, collected_at, failure,
       0, (SELECT COUNT(*) - 1 FROM page)
FROM batch_job_v10;
DROP TABLE batch_job_v10;
```

```python
# domain/batch.py - branch-free (coverage-core 100 %)
@dataclass(frozen=True)
class BatchJob:
    id: int; run_id: int; provider_job_id: str; model_id: str
    state: BatchState; submitted_at: str; collected_at: str | None; failure: str | None
    first_ordinal: int
    last_ordinal: int
    @property
    def ordinals(self) -> range: return range(self.first_ordinal, self.last_ordinal + 1)

# store/batch.py
__all__ = ["BatchPending", "mark_collected", "mark_failed", "pending_jobs", "record_submission"]
def record_submission(project: Project, run_id: int, provider_job_id: str, model_id: str,
                      first_ordinal: int, last_ordinal: int) -> int
    # ValueError(f"... {first_ordinal} .. {last_ordinal} ...") before the transaction when
    # first_ordinal < 0 or first_ordinal > last_ordinal.
    # In ONE transaction: SELECT the pending rows whose range overlaps
    #   (first_ordinal <= p.last_ordinal AND last_ordinal >= p.first_ordinal);

    #   {first}..{last}; collect it or mark it failed before submitting pages {new first}..{new last}")
    #   none -> INSERT, return lastrowid.
def pending_jobs(project: Project) -> tuple[BatchJob, ...]
    # SELECT ... WHERE state = 'submitted' ORDER BY first_ordinal, id   (no transaction: Project.select)
def mark_collected(project, job_id) / mark_failed(project, job_id, failure)   # unchanged
```
