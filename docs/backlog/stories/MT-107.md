## Context

EPIC-09 PO-3: a page's context should depend on nothing another page's
translation produced. Today `build_prompt_context` (`pipeline/continuity.py`,
MT-014 C-8) gives page `n` the glossary and page `n-1`'s **proposed
English**, so page `n`'s request cannot be built until page `n-1` has
answered - a call-order dependency a batch cannot have.

This story adds a second mode, `neighbours`: the glossary block plus the
previous and next pages' **Japanese OCR**, which exists for every page before
any call. It is **selectable per run and the default stays `rolling`**: the
two modes are measured against each other on the benchmark chapter in MT-108,
and only MT-109 moves the default, if the measurement says so. The batch path
(MT-111) always uses `neighbours`, because it is the only order-free mode.

Page 1 today gets `EMPTY_CONTEXT` (MT-014 AC-5). In `neighbours` mode page 1
has a next page, so it gets the glossary block (empty on a fresh chapter)
and the next page's Japanese; the last page gets the previous page only.
Both blocks are capped at `MAX_ROLLING_TOKENS` together, previous page first,
so the request size stays what the cost model assumed.

Required gates: `unit`, `coverage`, `coverage-core` (`domain/glossary.py`).

## Acceptance criteria

- **AC-1** - `render_neighbours(previous, next, max_tokens)` renders
  `Previous page, Japanese:` over the previous page's lines and `Next page,
  Japanese:` over the next page's, in that order, omits a header whose list is
  empty, and returns `""` when both are empty; truncation under `max_tokens`
  drops lines from the **end of the next page first**, then the end of the
  previous page, never mid-line.
- **AC-2** - `build_prompt_context(project, 0, mode="neighbours")` on a
  three-page project returns the glossary block and page 2's Japanese;
  ordinal 1 returns pages 1 and 3; ordinal 2 returns page 2 only; no
  proposed English appears in any of them, even when every page has a
  proposal stored.
- **AC-3** - `build_prompt_context(project, n)` with no `mode`, and with
  `mode="rolling"`, is byte-identical to its output before this story for
  every ordinal (page 0 is `EMPTY_CONTEXT`; later pages carry the previous
  page's proposed English) - the existing continuity tests pass unchanged.
- **AC-4** - `TranslateStage(..., context_mode="neighbours")` builds page
  `n`'s request from a context that does not change when page `n-1`'s
  proposal is rewritten between two runs of the stage; in `rolling` mode it
  does.
- **AC-5** - `mangatl-run FOLDER --context neighbours` and
  `MANGATL_CONTEXT_MODE=neighbours` select the mode (flag beats variable, as
  `--provider` does), any other value is refused in one line naming the two
  modes before any weight loads, and unset means `rolling`. The window reads
  the variable the same way.

**Pinned at PLANNED (2026-11-02), against the tree as it is after MT-105:**

- `render_neighbours` accounting mirrors `render_rolling`: the cap is
  `estimate_tokens` of the **whole** rendered text, headers included. Each
  section is `_with_header(header, lines)` - no header over an empty list -
  and the two sections are joined by `"\n\n"`. Truncation pops from the
  **end** of `next` until it is empty, then from the end of `previous`;
  `""` when nothing fits. Headers: `Previous page, Japanese:` and
  `Next page, Japanese:`.
- `PromptContext` is unchanged: the neighbours text travels in
  `rolling_block` (a historical name; `translate/page_prompt.py:182` joins the
  two blocks and knows nothing about modes). Renaming the field is out of
  scope.
- `build_prompt_context(..., mode="neighbours")`: `prev_ja` is `[]` for
  ordinal 0 and `next_ja` is `[]` for the last ordinal (`len(project.pages())
  - 1`); the glossary block is rendered for every ordinal, page 0 included.
- `TranslateStage.run` calls `build_prompt_context(ctx.project,
  ctx.page.ordinal, mode=self.context_mode)`; `build_stages` passes its
  `context_mode` to `TranslateStage`; `build_pipeline` passes it to
  `build_stages`.
- CLI refusal shapes (AC-5): the **flag** is `choices=CONTEXT_MODES`, so a
  bad value gets argparse's usual `invalid choice` exit (2), as `--provider`
  does; the **variable** is resolved with `context_mode(os.environ.get(
  CONTEXT_MODE_VAR))` **before `select_provider`**, and `UnknownContextMode`
  goes through `_fail(str(error))` - exit `_FAILED`, one stderr line naming
  the value and both modes. Both happen before `read_chapter` and
  `build_pipeline`, so no weight loads and no `.mtproj` is left behind.
- The window (AC-5 "reads the variable the same way"): `app.build_stages`
  resolves `context_mode(os.environ.get(CONTEXT_MODE_VAR))` before
  `select_provider`, so a bad value raises before any weight loads; both UI
  callers of `setup.build_stages` - Start in `ui/main_window.py:144` and the
  re-run in `ui/workspace.py:1431` - catch `UnknownContextMode` beside
  `ProviderError` and show its message the same way (`show_error` / `_say`).
  `UnknownContextMode` stays a `ValueError` in `domain`; it is not a
  `ProviderError` (that would make `domain` import `translate`).
- `ContextMode`, `CONTEXT_MODES`, `CONTEXT_MODE_VAR`, `UnknownContextMode`,
  `context_mode` and `render_neighbours` join `domain/glossary.py`'s
  `__all__` (an existing test pins that list's contents; RED updates it).

  pin that the message is shown and nothing is created or run.
- **PO-3 - the epic's done-when.** EPIC-09 PO-3 (order-free context) is
  delivered by this story's `neighbours` mode plus MT-111 selecting it for
  the batch; whether it becomes the synchronous default is MT-108/MT-109's.
  Nothing promised between MT-105 and here is left undelivered.

  story's central claim. No test here is written against code that already
