## Context

`docs/wiki/design/components.md` §4.7 is normative. It binds `Up`/`Down` ("move
selection to the previous / next ordinal on this page") and `Home`/`End` ("select
ordinal 1 / the last ordinal") in **either pane, column or canvas**.
`accessibility.md` A-07 makes `Up`/`Down` one of the bindings that "must never
regress", and A-05 names this path as *the* guaranteed way to reach a bubble too small
to click.

MT-016 built `Up`/`Down` in the column only (its AC-9) and deferred the rest (MT-016
PO-5). This story builds the canvas half and pins `Home`/`End` in the column, which
`QListWidget` probably already provides but no test covers.

There is a trap, and it is why AC-5 exists. `PageCanvas` is a `QGraphicsView`, and a
scroll area's default key handling **scrolls the view** on the arrow keys. An
implementation that selects and then calls `super().keyPressEvent` moves the selection
correctly and also pans the art by a scroll step. That breaks §4.5, under which
selection pans only by the minimum needed to bring the region in, and only if the region
is not already visible. It would pass every "the selection moved" test.

**Which required gate would fail if this story's artifact broke:** `unit`
(`tests/ui/`, offscreen).

## Acceptance criteria

- **AC-1** — Given the canvas has keyboard focus and ordinal *k* is selected, with
  1 < *k* < *n*, when `Down` is pressed, then ordinal *k*+1 is selected. When `Up` is
  pressed, ordinal *k*−1 is selected. In both cases the selection is conveyed as any
  selection is: the row becomes current in the column, and the live region announces
  "Bubble {n} of {total} selected. …".
- **AC-2** — Given the canvas has focus, when `Up` is pressed with ordinal 1 selected,
  or `Down` with the last ordinal selected, then the selection does not change and
  nothing is announced. The canvas does not wrap, matching the column, which does not
  wrap either (§4.7 gives both panes one row of the table).
- **AC-3** — Given the canvas has focus and any ordinal is selected, when `Home` is
  pressed, then ordinal 1 is selected; when `End` is pressed, then the last ordinal is
  selected. The same holds with focus in the translation column.
- **AC-4** — Given the canvas has focus, when any of `Up`/`Down`/`Home`/`End` changes
  the selection, then keyboard focus is still on the canvas afterwards. It is not on the
  list or on a row's editor, so a user can keep pressing the keys. (`Enter` is still what
  moves focus to the editor, per MT-016 AC-9.)
- **AC-5** — Given the canvas has focus, when one of these keys selects a region that
  is **already entirely inside the viewport**, then both of the canvas's scroll values
  and its whole `transform()` are exactly unchanged. When it selects a region that is
  **outside** the viewport, then the view ends where MT-016's `reveal` puts it: the
  region is contained with ≥ 24 px margin, and `transform().m11()`/`m22()` are
  unchanged.
  *Control:* a handler that selects and then passes the key to
  `QGraphicsView.keyPressEvent` must fail the first half. RED measures and records the
  scroll delta that the default handling produces offscreen.
- **AC-6** — Given a page with no regions (an empty page, or a page that failed to
  decode), when any of the four keys is pressed on the canvas, then nothing is selected,
  nothing is announced, and no exception is raised.

## Contract

**This is a sketch only. The Lead PO pins it at PLANNED → RED. After that, RED may
amend any block in place with a one-line reason, and GREEN builds what the amended block
says.**

```
src/mangatl/ui/canvas.py  (PageCanvas)
    selectionStepRequested = Signal(str)   # sketch: "previous" | "next" | "first" | "last"
                                           # - or four signals, or one Signal(int)
                                           # carrying a target id. RED pins the shape.
    # keyPressEvent: Key_Up / Key_Down / Key_Home / Key_End with no modifier other than
    # KeypadModifier are ACCEPTED and never reach QGraphicsView.keyPressEvent (AC-5).
    # Enter/Return are unchanged (MT-016).
src/mangatl/ui/workspace.py  (Workspace)
    # Resolves the step against link.state and the page's region count, and calls
    # link.select(target). It does not wrap, and it does nothing when there are no
    # regions. The existing selectionChanged wiring then restyles the markers, reveals
    # the region, selects the row and announces the change. None of that is duplicated.
```

- **Where the arithmetic lives is GREEN's choice**, provided the canvas does not own
  the selection (§4.1: neither pane owns it; `LinkController` does). A canvas that
  calls `link.select` directly would need a reference to the controller that it does
  not have today.
- **Focus:** the tests need the window active (MT-016 handoff quirk 6: `activateWindow`
  plus `waitUntil(isActiveWindow)`), and they assert with
  `QApplication.focusWidget()`, not `hasFocus()`.
- **Column `Home`/`End`** are expected to pass on arrival, because `QListWidget`'s own
  cursor movement feeds `_on_current_row_changed`. Under `rules.md` a test written
  against behaviour that already exists has to be earned: RED mutates
  `Workspace._on_current_row_changed` with `bash scripts/mutate.sh` so that it ignores
  the row, watches the column `Home`/`End` assertions go red, and pastes the output into
  `## Handoff`.
- **No existing signature changes.** `PageCanvas.keyPressEvent` gains cases, and
  `Workspace` gains a connection. On 2026-09-29, `rg "keyPressEvent" src tests` found
  only `canvas.py:226`.

## Deferred verifications

- *Falsifiable condition 1:* with the canvas's handling of these keys made to fall
  through to `super().keyPressEvent` after selecting, AC-5's already-visible case
  **must** fail.
- *Falsifiable condition 2 (a wrong value):* with `End` selecting the second-to-last
  ordinal (an off-by-one in the "last" target), AC-3 **must** fail.
- *Falsifiable condition 3:* with `Up` at ordinal 1 wrapping to the last ordinal, AC-2
  **must** fail.
- **Owner: GATES.** Run the three mutations with `bash scripts/mutate.sh`. RED cannot
  run them, because the handler does not exist until GREEN.

## Model guidance

- **RED and GREEN models:** record the resolved model of each dispatch by name at the
  time of dispatch. The agent definitions declare `opus`.
- **Oracle partition:** put the table above into the RED dispatch prompt verbatim.
- **Success condition, falsifiable:** the RED suite contains an AC-5 test that selects
  an already-visible region by keyboard and asserts that the scroll values and transform
  are **exactly** unchanged, and RED records the non-zero scroll delta measured under the
  control (the fall-through handler). If RED cannot show that the control moves the
  view, the AC-5 test is blind to the trap it exists for, and RED has failed.
- **Verdict:** *to be recorded when RED ends.*

## Out of scope

- Every other binding in §4.7: `Ctrl+9` (MT-052), `Ctrl+0`/`Ctrl+1`/`Ctrl+=`/`Ctrl+-`,
  `PageUp`/`PageDown`, `Ctrl+J`, `Tab`/`F6` pane movement, and `?`.
- Modified variants (`Shift+Up`, `Ctrl+Home` and so on). There is no multi-select
  (§4.1), and they are unassigned. Do not give them meaning.
- `Left`/`Right` on the canvas. §4.7 does not bind them, and this story does not claim
  or change what they do today.
- The state of a non-empty page with nothing selected. `Workspace.set_regions` always
  selects ordinal 1 on a non-empty page and nothing deselects, so that state cannot be
  reached. It is not specified and not tested.
- Animation of the resulting pan (MT-016 PO-4). The rows' visual focus ring (A-04) is
  also out of scope.
- Any change to column `Up`/`Down` (MT-016 AC-9, already green).
