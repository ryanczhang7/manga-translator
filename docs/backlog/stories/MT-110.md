## Context

EPIC-09 PO-1: one request per page, submitted together as one batch. This
story is the Gemini **adapter** for a batch - the SDK-facing half - with the
request and result shapes MT-101 `## Decided` fixed (D-5..D-8 for `client.batches.*`,
the job states, per-request errors). Everything is testable with a fake
client; no money is spent in `tests/core`.

A batch request is the per-page request `translate/gemini.py:build_request`
builds today - same image cap, same system prompt, same schema (without
`glossary`, MT-106), same thinking config - with the context from
`neighbours` mode (MT-107), because that is the only context that exists
before any answer. The adapter does not know about modes: it receives
`PromptContext`s already built.

A finished batch answers one item per request, in order. Each item is either
an answer (parsed exactly as `translate_page` parses one) or an error; the
adapter returns both kinds and lets the pipeline decide (MT-112 marks the
page's lines `failed`).

Required gates: `unit`, `coverage` (both `required`, both cover `src/mangatl/**`; `coverage-core` does not read `translate/`). A broken adapter fails `unit`.

## Acceptance criteria

- **AC-1** - `build_batch_requests(pages)` for three `BatchPage`s (given in
  any order) returns three `types.InlinedRequest`s sorted by ordinal, each
  carrying `contents` and `config` equal to `build_request(page_image,
  ocr_results, context)`'s for that page, `metadata == {"key":
  str(ordinal)}` (MT-101 D-5, D-7) and `model is None`; two calls on the same
  pages compare equal; two pages sharing an ordinal raise `ValueError` naming
  it. Nothing is skipped: an all-`ocr_empty` page gets a request like any
  other (PO-2).
- **AC-2** - `submit_batch(client, requests, display_name)` makes exactly one
  `client.batches.create(model=MODEL_ID, src=list(requests),
  config=types.CreateBatchJobConfig(display_name=display_name))` call and
  returns the `.name` the returned job carries; a client that raises (MT-101
  D-4's create-time `400`) propagates that very exception, unwrapped, after
  exactly one call.
- **AC-3** - `batch_state(client, job_name)` makes one
  `client.batches.get(name=job_name)` call and maps the job's `state.name`:
  `JOB_STATE_PENDING` and `JOB_STATE_RUNNING` to `"pending"`,
  `JOB_STATE_SUCCEEDED` / `JOB_STATE_FAILED` / `JOB_STATE_CANCELLED` /
  `JOB_STATE_EXPIRED` to `"succeeded"` / `"failed"` / `"cancelled"` /
  `"expired"` (MT-101 D-6); any other name (the SDK's six Vertex-only
  members, `JOB_STATE_QUEUED` among them) and a `None` state raise
  `UnknownBatchState` naming the state, never `"pending"`.
- **AC-4** - `collect_batch(client, job_name, pages)` on a succeeded job
  reads `job.dest.inlined_responses` and pairs each item to a page by
  `metadata["key"] == str(ordinal)`, never by position (MT-101 D-7): with the
  items in reverse order the result is unchanged. Per ordinal it returns a
  `TranslationResult` whose `lines` are `parse_lines_text(text,
  range(len(ocr_results)))`, `proposed_terms` are `parse_terms_text(text)`,
  `usage` is `_usage_of(response.usage_metadata)` (thinking added to output)
  and `call == CallInfo(f"{job_name}#{ordinal}", response.model_version or
  MODEL_ID)`. An item carrying `.error` returns `BatchItemError(ordinal,
  error.message)`; an item whose parse raises (`UnknownRegionIndex` on MT-101
  D-14's verbatim probe response with its extra key `"3"`, invalid JSON,
  missing usage) returns `BatchItemError(ordinal, f"{type(exc).__name__}:
  {exc}")` and the other pages still parse. A response whose item count
  differs from the page count (fewer **or** more), an item with no key, a
  key no page has, or two items with one key raise `BatchShapeError` naming
  both counts, or the key.
- **AC-5** - `collect_batch` on a job whose `batch_state` is not
  `"succeeded"` raises `BatchNotFinished` naming the mapped state
  (`"pending"`, `"failed"`, ...), reads no item, and parses nothing - a
  `pending` job carrying a stale `dest` is still refused.

## PO decisions (2026-11-03, lead-po on Claude Fable 5.1)

- **PO-1 - a volume does not fit one inline job, and no story owns that
  yet.** MT-101 D-9: 200 capped pages are ~24 MB base64 against the 20 MB
  inline limit. This story stays **inline, one job** (the shape the live
  probe verified); the epic's done-when ("a 200-page volume ... Start once")
  therefore needs **MT-111 to split a volume into as many inline jobs as fit
  under 20 MB**, guarded once on the whole projection (PO-5's "submitted
  once" becomes "guarded once, submitted as few jobs as fit"), or to use
  file input instead. Recommended: split in MT-111 - it reuses this adapter
  unchanged and the job table (MT-103) already holds one row per job.
  **Reported to the user before GREEN; MT-111's contract records the answer.**
- **PO-2 - an all-`ocr_empty` page is the caller's to leave out.**
  `translate_page` returns the empty result without a call; the adapter has
  no such branch, because deciding which pages a batch holds is MT-111's
  (it must also ledger the page as a no-call). `build_batch_requests` builds
  what it is given.
- **PO-3 - D-14's open probe (`response_schema` vs `response_json_schema`)
  is not run here.** The request stays byte-equal to `build_request`'s
  (AC-1), the parser is the defence (AC-4), and a live probe is the user's
  to run (EPIC-09 Q-1). If it is ever run and `response_schema` is
  enforced, that is a change to `build_request`, not to this adapter.
- **PO-4 - pairing is by key, not position** (MT-101 D-7: order NOT FOUND).
  AC-4 pins it with a reversed-order case; the count check is kept as well,
  because a job that answers more items than it was asked is a shape error
  whatever its keys say.
