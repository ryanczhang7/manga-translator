## Context

**Urgent.** A required gate on this machine fails intermittently, and CI runs the
same `bash scripts/gates.sh` on `windows-latest` (`.github/workflows/gates.yml:16,65`),
so it can fail any PR's checks as well as any story's recorded local run. This is the
fourth recorded recurrence of one signature:

| When | Gate | Counts | Where recorded |
|---|---|---|---|
| 2026-09-28 | `coverage-core` | 34 failed | `docs/wiki/audits/opencv-unknown-exception-2026-09-28.md` |
| 2026-09-29 | `unit` | 34 failed (25 + 9 detect) | same audit, two addenda (E1-E9, W0-W11) |
| 2026-10-02 | `coverage-core` | 93 failed, 925 passed | `MT-065.md` GATES note |
| 2026-10-04/05 | `coverage`, then `unit` | **135 failed, 2405 passed, 30 errors**, twice | `MT-067.md` P-8 and PO-5 |

Every failure is `cv2.error: Unknown C++ exception from OpenCV code`. Two prior
investigations ran roughly 100 suite runs and 17,000 direct calls, and none
reproduced it. They failed for one reason: the failing log was overwritten before
anyone read it (audit W0). **This time the log survived**, and it changes what is
known. See `## Evidence already in hand` below.

The audit's prior `## Decided` points stand unless this spike's evidence overturns
them. The ones this story leans on are: "Unknown" means a Windows structured exception;
FP-control-word state is refuted (W6); commit exhaustion is refuted (W3, W4). Its
numbers are evidence, to be re-checked where this spike depends on them, not assumed.

**Why a spike and not a `fix`.** A `fix` needs a failing test that reproduces the
bug. Nobody has reproduced it on demand. The one repeatable thing, two identical
counts, does **not** imply a deterministic test-order trigger (see E-c below). So a
RED cannot be planned: it would have nothing to make fail. The spike's job is to find
a reproduction that runs on demand. If it finds one, the fix story it files
carries that reproduction as its AC. If it does not, the spike decides what happens
instead, in writing.

**What breaks if this is wrong:** the `unit`, `coverage` and `coverage-core`
required gates, on any branch, on this machine and possibly on CI. It may also break
the shipped app. `src/mangatl/clean/mask.py:61` (`erase_mask`, `cv2.dilate`),
`src/mangatl/clean/inpaint.py:83` and `src/mangatl/detect/postprocess.py:164,256,340`
are production call sites that failed in the same process. The app imports
`onnxruntime` before it calls them, just as the suite does.

## Hypotheses to test

Listed so the spike starts with something to falsify, not as conclusions. Each says
what would refute it.

- **H1. A broken thread-pool or scheduler state persists for the process
  lifetime.** Something leaves the Windows thread pool, or the ConcRT scheduler that
  OpenCV's `parallel_for_` uses, in a state where every later parallel dispatch raises
  `0xC000070A`. The candidates are a resource failure at process level (the same one
  E-a sees as `E_OUTOFMEMORY`) or a handle in the pool that has gone bad. *Refuted
  if* the spike can make the scheduler's first use fail and every later call still
  succeeds, or if `0xC000070A` turns out to name something unrelated to thread
  pools.
- **H2. The trigger is a transient resource failure early in the process, and
  whatever process is running then is the one that breaks.** That would explain why
  concurrent load (run 1) and quiet runs (run 2) both fail, and why the next process
  is clean. *Refuted if* failing runs show no early fault (the WMI line absent),
  since run 2's log has not been read.
- **H3. The `onnxruntime-gpu` import, with CUDA, cuDNN and TensorRT provider DLLs,
  is what consumes or corrupts the resource.** Audit W7 lists what it loads. *Refuted
  if* a process that never imports `onnxruntime` shows the signature, or if forcing
  the import to fail early (W3's harness) never yields `0xC000070A`.
- **H4. Machine-level state outside the repository is the trigger.** Candidates are
  Defender's in-process AMSI provider (W7) and the Game Bar capture DCOM churn (W11).
  *Refuted if* the trigger reproduces with those excluded or quiet.
- **H5 (the orchestrator's original framing). A specific earlier test or fixture
  leaves cv2 broken.** *Refuted if* E-c's all-or-nothing reading holds, meaning the
  failing set equals the full set of parallel-cv2-reaching tests minus a fixed
  survivor set, whatever the order. E-g already weakens it.

- **AC-3** — The document records every reproduction attempt as a recipe, a run
  count and an outcome, including those that produced nothing. It ends in exactly one
  of two states:

    *negative control*: the same subprocess without the inducing step succeeds in

    hypotheses H1-H5 they refute or leave standing.
- **AC-4** — The document ends with a `## Decided` section that does all of these:

    - a gate-side mitigation;
    - an explicit decision to do nothing, with the cost of that decision stated.
  - In both states, it says whether the **shipped app** is exposed. The app imports

## Notes

### PO-1 - spike, not fix (decided 2026-10-05, lead-po, at planning)

The dispatch asked for a `fix` story whose criteria reproduce the bug, "or, if the
cause is unknown enough that one cycle cannot be planned, make it a spike and say
why". It is a spike for three reasons.

- **Nobody has a reproduction.** About 100 runs and 17,526 direct calls failed to
  produce one (audit E1-E4, W5, W9), and a `fix` RED would have no assertion it
  could watch fail. Law 1 makes that a non-starter, not a formality.
- **The orchestrator's lead does not survive the log.** The lead was "identical
  counts suggest a deterministic order trigger, find a minimal failing order". The
  log (E-b, E-c) says the failing set is every parallel cv2 call in the process,
  across files from `test_bake` to `test_detect_postprocess`, both test helpers and
  production code. The identical count is the size of that set, not the position of
  a trigger. A minimal *test order* probably does not exist (H5). A minimal *process
  state* might, and finding it is investigation, not one RED→GREEN cycle.
- **There is now evidence worth a timeboxed look.** E-a and E-b are the first
  in-process record of both the early fault and the per-call SEH code. The audit
  named exactly these as the two things that "would narrow the mechanism at once".

### PO-2 - urgency and timebox

  gates on `windows-latest`. It has struck four times in eight days, and it has twice
